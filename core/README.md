# Ядро, модули и обёртки

`core/jarvis/` — единственный в репозитории исходник ядра. Он не модуль и в
наборе модулей не лежит: набор для шеринга состоит только из модулей, все
одного вида. Копию ядра установщик кладёт внутрь папки каждого модуля, поэтому
модуль самодостаточен и едет к коллеге голой папкой.

Устройство системы живёт в Craft, разделы «Архитектура», «Библиотека»,
«Обёртка и события». Здесь — только то, что решено кодом.

## Раскладка

В репозитории:

```
core/jarvis/                     ядро: хранилище, режим, автономия, след,
                                 подтверждение, поиск соседей
core/jarvis/wrappers/claude.py   обёртка Claude
core/jarvis/wrappers/codex.py    обёртка Codex (пока только старт и сжатие)
modules/‹slug›/module.toml       шапка модуля
modules/‹slug›/hooks/module.py   точка входа: её и запускает харнес
modules/‹slug›/lib/              библиотечная часть, её зовут соседи по slug
modules/‹slug›/data/             данные модуля
modules/‹slug›/skill/ agents/ rules/   части, которые читает харнес
modules/modules.json             конфиг режимов источника (необязательный)
```

После раскладки — только модули, у каждого своё ядро внутри:

```
‹каталог модулей›/‹slug›/_core/jarvis/   копия ядра этого модуля
‹каталог модулей›/‹slug›/hooks/module.py
‹каталог модулей›/‹slug›/…
```

Папка ядра внутри модуля называется `_core`, с подчёркивания. Подчёркивания в
slug быть не может, поэтому имя ядра и имя модуля не столкнутся, и списка
запрещённых имён не нужно.

Разные модули одного набора могут нести разные версии ядра — это допустимо:
модуль самодостаточен.

Тесты без харнеса: `python3 -m unittest discover -s tests -t .`

## Как модуль находит ядро и соседей

Харнес всегда запускает файл модуля, и путь к себе у этого файла есть. Ядро —
в собственной папке модуля, одной строкой от этого пути. Соседей по `requires`
и адаптеров по `for` библиотека ищет в каталоге модулей рядом с папкой модуля.
Ни аргумента «корень установки», ни записи установщика для этого не нужно, и
рабочий каталог процесса ни на что не влияет.

Точка входа модуля — `hooks/module.py`, класс `Module`:

```python
sys.path.insert(0, str(Path(__file__).resolve().parents[1] / '_core'))

import jarvis
from jarvis.wrappers import claude


class Module(jarvis.Module):
    def handle(self, event, runtime):
        return jarvis.Silence()


if __name__ == '__main__':
    sys.exit(claude.run_hook(__file__, Module))
```

## Единый формат события

Поля — `jarvis.Event` ([jarvis/event.py](jarvis/event.py)), snake_case:

| Поле | Что несёт |
| --- | --- |
| `event` | единое имя события из каталога `jarvis.events` |
| `session_id` | идентификатор сессии из события харнеса |
| `tool_name` | имя инструмента — на `pre-tool`, `post-tool`, `tool-error` |
| `tool_input` | вход инструмента — там же |
| `tool_result` | результат вызова — на `post-tool` |
| `error` | текст ошибки вызова — на `tool-error` |
| `prompt_text` | текст реплики — на `prompt` |
| `human_answer` | ответ человека на вопрос — на `post-tool` |
| `cwd` | рабочий каталог |
| `harness` | харнес-источник |
| `raw` | сырое событие харнеса как есть |

Событие неизменяемо: модуль его не правит, а отвечает.

## Единый ответ модуля

Восемь форм — [jarvis/response.py](jarvis/response.py): молчание, контекст,
разрешить, спросить, запретить, изменённый вход, блок, вопрос человеку.

## Шапка модуля

`module.toml` в корне папки модуля, шесть полей. TOML взят потому, что его
читает стандартная библиотека (`tomllib`), а зависимостей нет. Разбор и
проверка — в [jarvis/manifest.py](jarvis/manifest.py).

| Поле | Что задаёт | У кого есть |
| --- | --- | --- |
| `slug` | имя модуля; от имени папки не зависит, по набору уникально | у всех |
| `for` | чему модуль служит: slug'и и маски семейств | только у адаптеров |
| `events` | на каких событиях модуль стоит | только у хуков |
| `requires` | что модулю нужно: slug или маска | у всех |
| `harness` | харнес, только для которого модуль существует | необязательное |
| `copies` | сколько копий ставит установщик, по умолчанию одна | только у хуков |

`for` — список строк; одна строка принимается как список из одной. Модуль без
`harness` ставится во все харнесы. `copies` — целое не меньше единицы и только
у модуля с `events`: копируется строка хука, а её без событий нет.

Slug — только строчные латинские буквы, цифры и дефис: он становится именем
папки, а на macOS файловая система регистронезависима. Проверяется на границе
разбора.

Семейство — общее имя группы модулей, маска — имя семейства и `-*`. Адаптер в
`for` и зависимый в `requires` пишут одну и ту же маску, и требование ищется
ровно так, как записано: голый slug — по slug, маска — по slug любого модуля
семейства и по адаптеру, у которого в `for` стоит то же требование.

Обратный ход — «адаптеры базы», `manifest.adapters_of` и `registry.adapters`:
база называет свой slug и получает соседей, у которых какая-то строка `for`
совпадает с этим slug'ом точно или накрывает его маской. Порядок — по slug,
чтобы склейка была повторяемой. Это единственное, что общего у баз стартового
контекста, и потому оно здесь, а не в модуле.

## Копии модуля

`copies = N` — установщик кладёт N папок, и копия получает slug с номером на
конце: `start-context-claude-1` … `-12`. В шапке копии переписывается только
slug, всё остальное едет как в источнике, поэтому копия читает из своей шапки и
свой номер (`manifest.copy_index`), и общее число копий. Одна копия — slug без
номера. Уменьшили `copies` — лишние копии уходят обычной уборкой: копия для
журнала установки такой же модуль, как любой другой.

## Куда установщик ставит части

| Часть | Куда | Кто её читает |
| --- | --- | --- |
| `hooks` | `‹настройки›/jarvis/modules/‹slug›/hooks/` | харнес запускает файл |
| `lib` | `‹настройки›/jarvis/modules/‹slug›/lib/` | соседи по slug |
| `data` | `‹настройки›/jarvis/modules/‹slug›/data/` | сам модуль |
| `skill` | `‹настройки›/skills/‹slug›/` | харнес |
| `agents` | `‹настройки›/agents/‹slug›/` | харнес |
| `rules` | Claude: `~/.claude/rules/‹slug›/`; Codex: `~/.codex/AGENTS.md` между метками `<!-- jarvis:‹slug› -->` | харнес |

Каталога правил у Codex нет, поэтому части `rules` склеиваются в его общий
`AGENTS.md` между метками модуля. Снаружи меток файл чужой и не трогается, а
потолком контекста глобальный `AGENTS.md` не режется.

Копия ядра ложится в `‹slug›/_core/`. Установщик только раскладывает и
регистрирует: библиотеку не собирает, путей модулю не сообщает, ничего не
чинит. Переустановка убирает то, чего в источнике больше нет: части и снятые
модули целиком. Отличить своё от чужого позволяет журнал установки
`‹настройки›/jarvis/installed.json` — его пишет и читает только установщик,
библиотека в него не ходит.

## Плейсхолдеры путей

Пути харнеса модуль пишет плейсхолдером, подставляет установщик:
`{{JARVIS_CORE}}`, `{{JARVIS_MODULES}}`, `{{JARVIS_MODULE}}`,
`{{JARVIS_STATE}}`, `{{HARNESS_SETTINGS}}`, `{{HARNESS_PROJECT_DIR}}`.
Последний у Claude разворачивается в его собственный `${CLAUDE_PROJECT_DIR}`.

## Три источника режима

По старшинству, решает первый, кто говорит про этот slug:

1. сессия — `‹состояние›/‹session_id›/modes.json`;
2. личный конфиг — `~/.config/jarvis/modules.json`;
3. конфиг источника — `modules.json` в каталоге модулей.

Все три — плоский JSON «slug → включён». Значение только настоящее `true` или
`false`: строка `"false"` и ноль отклоняются с ошибкой, иначе написанное рукой
`"false"` молча оставило бы замок включённым. Молчат все — модуль включён.

## Хранилище и след

Каталог состояния один: `~/.local/state/jarvis`. Постоянная зона — сам
каталог, зона сессии — подкаталог по `session_id`. След — `trace.jsonl` в зоне
сессии, по строке на модуль на каждом его событии, молчание тоже строкой.
В поле `module_class` — имя класса, в `module` — slug. Ответ не той формы и
падение внутри модуля пишут строку следа до проброса ошибки: иначе такое
событие по следу неотличимо от хука, который вовсе не запускался.

## Строки хуков

Строка пишется на копию и на событие харнеса, а не на единое событие: одно имя
события харнеса может нести несколько единых. У Claude SessionStart — это и
старт сессии, и «после сжатия», поэтому строка одна и она называет оба единых
имени (`--event session-start --event after-compact`), а какое пришло, решает
обёртка по полю `source`. Строка соседнего события молчит и выходит с нулём:
модуль на этом событии не стоит, и хода у него не было.

У Claude строки живут в `settings.json`, у Codex — в `config.toml` между
метками `# jarvis:begin` и `# jarvis:end`, таблицами `[[hooks.‹событие›]]` и
`[[hooks.‹событие›.hooks]]` с полями `type`, `command`, `timeout` и
`additionalContextLimit = 0`.

Поле `timeout` установщик пишет всегда и одинаковым у обоих харнесов — 600 с
(дока: у command-хука оно в секундах). Минуты по умолчанию мало: модуль на
старте сессии может ходить в сеть, и убитый на полпути хук отдаёт в контекст
огрызок вместо текста. Сколько ждать своего соседа, модуль решает сам; общий
предел на ход — этот `timeout`, и он один для всех. Хук без доверия Codex молча не исполняет, поэтому
установщик после записи зовёт `codex app-server` по JSON-RPC (initialize →
initialized → hooks/list → config/value/write) и проставляет по хешу
определения `hooks.state."‹путь config.toml›:‹событие›:‹i›:‹j›".trusted_hash` и
`.enabled`. Хеш считает сам Codex — установщик его не выдумывает; правка
определения хука доверие обнуляет.

## Чего Claude не умеет

Таблица форм по событиям — `SUPPORTED` в
[jarvis/wrappers/claude.py](jarvis/wrappers/claude.py), причины отказа —
`UNSUPPORTED_NOTE` там же. Обёртка не подменяет форму соседней: чего харнес не
принимает, она называет в stderr и оставляет в следе полем
`not_delivered_reason`.

## Факты о Claude и их источники

Источник каждого факта помечен в коде: «дока» — страница hooks на
code.claude.com, снятая 17.09.2026; «замер» — проверено прогоном в этом
окружении.

Замеры (Claude Code 2.1.274, контейнер облачной сессии, 16–17.09.2026):

- вывод хука режется на 10 000 знаков на каждый процесс, в знаках;
- куски нескольких хуков ложатся в порядке завершения процессов;
- SessionStart с `source=compact` приходит после сжатия;

- форма «контекст» на событии `prompt` доходит до модели: модель повторила
  слово, которое положил модуль, и ниоткуда больше взять его не могла;
- `JARVIS_AUTONOMOUS=1` доходит до процесса хука через `claude -p` и попадает
  в след;
- в контейнере облачной сессии `claude -p` наследует `CLAUDE_CODE_SESSION_ID`
  родительской сессии, и вложенный прогон пишет след в её зону сессии.

## Факты о Codex и их источники

Обёртка Codex этапа 3 несёт только старт сессии и «после сжатия»; полная —
этап 7. Источники помечены так же: «дока» — схема протокола app-server,
снятая `codex app-server generate-json-schema`; «замер» — прогон в этом
окружении.

Замеры (codex-cli 0.154.0, контейнер облачной сессии, 17.09.2026):

- на stdin хуку приходит JSON тех же полей, что у Claude: `hook_event_name`,
  `session_id`, `cwd`, `source`;
- stdout хука старта доходит до модели нулевым ходом;
- хук без доверия молча не исполняется: строка в конфиге есть, процесса нет;
- `command` в строке хука — одна строка, Codex разбирает её как оболочка, так
  что аргументы едут в ней кавычками;
- поле таймаута в TOML называется `timeout`, а в ответе `hooks/list` —
  `timeoutSec`;
- после сжатия Codex текста хука не принимает вовсе: на `[[hooks.PostCompact]]`
  app-server отвечает «ignoring additionalContextLimit … this event cannot emit
  additionalContext». Строка там всё равно ставится, но ответ модуля обёртка
  помечает недоставленным и называет причину в следе — подменять форму она не
  умеет по устройству.
