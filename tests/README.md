# tests/ — регресс-тесты слоя хуков

Тест-набор для хуков в `.claude/hooks/`: подаёт заготовленное событие на вход
хука и проверяет исход. Защищает хуки от регресса.

Зависимостей три: `node` (слой хуков), `python3` (пакеты) и `shfmt` (разбор
команды оболочки — на нём стоят цели записи, доказанное чтение и цели чтения, то
есть план-гейт, гвард якоря сессии и гвард необратимого). Без `shfmt` слой не
гадает: он отвечает `unsupported` с именем, и кейсы про разбор честно краснеют.
Ставится он `brew install shfmt` на маке и `bash tools/install-shfmt.sh` на
линуксе (бинарник с проверкой контрольной суммы).

## Запуск

    node tests/run.js                 # кейсы хуков и пакетов
    node --test tests/unit/*.test.mjs # ядро слоя (пути, ответы, уступка вызову)
    python3 -m unittest discover -s modules -p 'test_*.py'    # кейсы модулей
    python3 -m unittest discover -s tests/pylib -p 'test_*.py' # pylib и установщик

Exit 0 — все кейсы зелёные и каждый исход каждого хука покрыт. Exit 1 — падение
или непокрытый исход (детали печатаются). Exit 2 — нет файлов кейсов.
CI гоняет это на push и pull_request (`.github/workflows/hooks-tests.yml`).

Git-логика синка системы и хранения метрик проверяется на временных
репозиториях без сети: `bash tests/sync-system-git.sh`,
`bash tests/metrics-store-git.sh`.

## Пакеты

Кейсы пакетов лежат в `tests/hooks/package.jsonl` (путь события целиком) и
`tests/hooks/guard-irreversible.jsonl` (гвард необратимого) и гоняются тем же
раннером:
он зовёт пакет ровно так, как его зовёт харнес, — `python3
modules/<имя>/dist/claude/hook.py` со своим stdin. Сборку раннер делает сам
перед прогоном (`jarvis install` во ВРЕМЕННЫЙ дом — настоящие `~/.claude` и
список корней прогон не трогает); не собралось — это смоук-провал с причиной, а
не тихо пропущенные кейсы.

Обход `unittest` МОЛЧИТ, когда ничего не нашёл: «Ran 0 tests ... OK» выглядит
зелёным прогоном. Поэтому шаг CI объявляет пустой обход провалом, а каталог
пакета и его `tests/` несут пустые `__init__.py` — без них обход внутрь не
заходит.

Сводка метрик собирается ПО ЖУРНАЛУ, а журнал наполняется каналом между хуками:
сорванный канал виден не падением, а тихо неполной сводкой. Это проверяет
`bash tools/metrics-fixture.sh . --self` (тоже в CI) — три сценария (ход
продолжился, сессия кончилась на блоке, канал оборван) и три утверждения: сводка
сложилась, событий без исхода нет, оборванный канал чисел НЕ меняет. Со вторым
аргументом-чекаутом тот же скрипт сравнивает две ветки — это делается руками, при
разборе изменений слоя.

Событие фикстура раздаёт ДВУМ адресатам, как его раздаёт харнес: цепочке
JS-хуков через диспетчера и каждому пакету — своей строкой. Без второй половины
отказ, переехавший из JS-хука в пакет, пропал бы из чисел молча, то есть ровно
тем способом, ради ловли которого фикстура и написана.

Отдельно CI проверяет дерево коммита гвардом `tools/no-snapshot-files.js`:
снимки живого Craft (`*router-context*`, `*incident-context*`,
`*craft-gate-exempt-scope*`, `*warm-cache*`) в git не лежат — кроме заглушек
в `tests/hooks/fixtures/warm-cache/` (`.claude/` и `.craft/`), и те только пока их
содержимое не похоже на настоящий снимок (шапка инжект-хука, заголовок памяти). Локально то же делает pre-commit из
`.githooks` (`install.sh` ставит `core.hooksPath`). Тест гварда —
`tests/unit/no-snapshot-files.test.mjs`.

## Проверка при утечке снимка

Смотреть ВСЮ историю, а не вершины веток, и в рабочей копии, которая объект
уже держала. Свежий клон вопрос не закрывает: по протоколу передаются только
рекламируемые сервером рефы, а коммит удалённой ветки ими не рекламируется —
`fetch` его не притянет, и локальному `fsck` нечего будет искать; чистый ответ
в свежем клоне значит «в рефах ничего нет», а не «утечки нет». Для уже удалённой
ветки годится копия, где объект остался (старый клон, воркри, машина, с которой
пушили), либо запрос по известному SHA (`git fetch origin <sha>` — сервер вправе
отказать), либо проверка на стороне сервера: на GitHub это поддержка.

В такой копии сперва притянуть серверные рефы целиком — дефолтный refspec берёт
только `refs/heads/*` и оставляет `refs/codex/*` и прочее:

    git fetch origin '+refs/*:refs/remotes/origin/*'

Список ревизий — ОДИН на оба захода, и в него входят недостижимые коммиты:
снимок с удалённой ветки или из снесённого воркри в `rev-list` не попадает, а
объект остаётся, и ради него всё и затевается.

    revs() { { git rev-list --all --reflog
               git fsck --unreachable --no-reflogs 2>/dev/null | awk '$2=="commit"{print $3}'
             } | sort -u; }

Первый заход — по маскам имён; он дешёвый и находит снимок, лежавший под своим
именем. `git log --all --reflog` для него не годится: он ходит по достижимым и
reflog, то есть слеп ровно к тем коммитам, ради которых пишется этот раздел.

    revs | xargs -r git show --name-only --format= -- | sort -u \
      | grep -iEf <(node -e 'const {MASKS}=require("./tools/no-snapshot-files.js");
                             console.log(MASKS.map(m=>m.source).join("\n"))')

Маски берутся ИЗ ГВАРДА, а не переписываются сюда: разъехавшись, список в
инструкции пропустит то, что гвард ловит. К коммитам СЛИЯНИЯ этот заход слеп:
`git show` печатает у них не файлы слияния, а комбинированный дифф — файл,
совпавший хотя бы с одним родителем, в список не попадёт. Их закрывает второй
заход, он смотрит ДЕРЕВО ревизии, а не её дифф.

Второй заход — по содержимому, гвардом, по тому же списку ревизий:

    revs | while read -r rev; do
        out="$(node tools/no-snapshot-files.js --tree "$rev" 2>&1)"
        case $? in 1) printf 'утечка: %s\n%s\n' "$rev" "$out";; 0) ;;
                   *) printf 'ошибка: %s\n%s\n' "$rev" "$out";; esac
      done

Вывод гварда НЕ выбрасывается: в нём имя сработавшего файла, а без него по одной
ревизии искать нечего. Коды различать обязательно: 1 — найденные снимки, 2 —
сбой запуска. Свалив их в одно «не ноль», получаешь битый объект под видом
утечки, а саму утечку — среди сотен чистых строк.

Чего эта проверка НЕ покрывает: болтающиеся блобы. `fsck` перечисляет их
отдельно (`dangling blob`, `unreachable blob`), в дереве они не лежат, и гвард,
который ходит по деревьям, до них не доберётся — снимок, попавший в индекс и
никогда не закоммиченный, останется незамеченным. Ищется он только по
содержимому самих блобов:

    git fsck --unreachable --dangling 2>/dev/null | awk '$2=="blob"{print $3}' \
      | while read -r oid; do
          git cat-file -p "$oid" | grep -qiE 'ИНЖЕКТ|Память для агента' && echo "блоб: $oid"
        done

Удаление веток утечку не выносит: объект остаётся, пока его не выбросит
сборщик мусора, а на GitHub — только поддержка. Удаление лишь прячет его от
клонов, и вместе с ним — возможность проверить снаружи.

## Формат кейса

`tests/hooks/<hook>.jsonl`, по одному JSON-объекту на строку:

    {"name":"…","hook":"detect-incident","expect":"inject","input":{"prompt":"…"}}

- `hook` — ключ из карты `SCRIPT` в `tests/run.js` (`guard-craft-markdown`,
  `guard-plan-hygiene`, `detect-incident`, `guard-plan-gate`, `guard-plan-critic`,
  `guard-plan-delta`, `fact-gate` и остальные) либо имя файла хука без расширения —
  незнакомый ключ раннер резолвит по имени файла.
- `input` — полный JSON события, как его подаёт Claude Code хуку на stdin.
- `expect` — что утверждает кейс. Одна строка либо СПИСОК строк: тогда обязаны
  выполниться все («запись есть И текста отказа в ней нет» одним утверждением не
  выражалось). Исходы: `deny` (stdout с `permissionDecision:"deny"`) · `ask` ·
  `block` · `allow` (хук не заблокировал) · `inject` (stdout с
  `СИГНАЛ ИНЦИДЕНТА`) · `silent` (пустой stdout) · `contains:<строка>` ·
  `not-contains:<строка>` · `err-contains:<строка>` (служебный поток) ·
  `file-contains:<строка>` и `file-not-contains:<строка>` (по файлу из
  `ASSERT_FILE`; второй требует НЕПУСТОГО файла) · `file-empty` (по тому же
  файлу — «не написано вовсе»).
  Исходы, утверждающие МОЛЧАНИЕ (`allow`, `silent`, `not-contains:`,
  `file-empty`, `file-not-contains:`), засчитываются только удавшемуся хуку: код
  возврата 0 и никакой строки диспетчера о падении. Упавший хук молчит так же, и
  без этой проверки поломка зеленила бы кейс.
- `env` (опц.) — переменные окружения для вызова, напр. `{"CRAFT_AUTONOMOUS":"1"}`.
- `setup` (опц.) — хуки, прогоняемые до целевого, чтобы выставить состояние: напр.
  `["plan-gate-approve"]` ставит метку одобренного плана, `["plan-gate-reset"]` гасит.
  Метка план-гейта у каждого кейса своя (временный файл) — кейсы герметичны.
- `setup_input` и `setup_env` (опц.) — своё событие и свои переменные для блока
  подготовки. Без них подготовке идёт то же, что целевому вызову; нужны связкам, где
  подготовка и цель обязаны отличаться (запись состояния одним входом, проверка другим).
  `setup_input` принимает и СПИСОК — тогда своё событие получает каждый шаг
  подготовки по порядку (`setup[i]` ← `setup_input[i]`), и шаги, которым событий
  не хватило, идут с входом целевого вызова.
- `repeat` (опц.) — подать тот же вход N раз; утверждение проверяется по последнему
  вызову. Для хуков с однократным отказом (факт-гейт, напоминание рутины).
- `args` (опц.) — аргументы командной строки хука, напр. `["universal"]` у
  диспетчера: им задаётся контур регистрации.
- `arm: true` (опц.) — предусловие «маркер взведён»: файл, путь которого хук берёт
  из переменной окружения, создаётся до вызова (напоминание о закрытии инцидента).
- `registry_seed` (опц.) — стартовое состояние реестра одобренного: массив целей,
  каждая ложится строкой JSONL в герметичный реестр прогона.
- `codex_seed` (опц.) — вход, уже лежащий в доме codex до вызова хука.
- `assert_no_model_call` / `assert_model_call` (опц.) — был ли вызван мок
  классификатора: след пишет `{CLASSTRACE}`.
- `assert_trace_contains` (опц.) — подстрока, которую кейс требует в промпте,
  ушедшем в мок классификатора.
- Подстановки в строках кейса: `{TESTS_DIR}` — каталог кейсов, `{REGISTRY}` —
  герметичный реестр одобренного, `{CLASSTRACE}` — след вызовов мока
  классификатора, `{CODEXHOME}` — дом codex, `{METRICS}` — журнал метрик прогона,
  `{METRICS_DEFAULT}` — путь, который хук строит сам, когда сессии нет и журнал
  не переопределён (по нему доказывается, что записи не было).

## Добавить кейс

Допиши строку в нужный `tests/hooks/<hook>.jsonl` и запусти `node tests/run.js`.
Что именно покрыто (включая пограничные случаи) — видно из полей `name` в этих
файлах; это единственный источник, здесь он не дублируется. Меняешь хук — сначала
обнови кейс, потом код.
