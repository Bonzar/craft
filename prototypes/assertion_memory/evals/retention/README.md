# Retention evals

Этот каталог проверяет, какие мысли стоит сохранять после одиночной реплики или батча. Он не открывает рабочую БД и ничего не выкладывает. Основная выборка — 300 вымышленных размеченных диалогов (D001–D300). В дополнение — десять анонимизированных обязательных регрессий (R001–R010), включая точное повторение предпочтения в одном батче. Это не утверждение, что 310 диалогов уже прошли реальную модель.

## Слепой A/B

Один и тот же набор, версия модели и настройки на обеих ветках. Эталонные ответы не передаются модели. Бэкенд — любая авторизованная локальная команда, принимающая промпт в stdin и выдающая JSON в stdout. Не подключайте рабочие инструменты, хостинг, реальную БД или платного провайдера без отдельной авторизации. Пример с локальным адаптером:

```sh
python3 eval_retention.py run --dialogue-py /path/to/baseline/dialogue.py --output out/old.json -- ./isolated-model-adapter
python3 eval_retention.py run --dialogue-py /path/to/candidate/dialogue.py --output out/new.json -- ./isolated-model-adapter
python3 eval_retention.py score --predictions out/old.json --output out/old-scored.json
python3 eval_retention.py score --predictions out/new.json --output out/new-scored.json
```

Перед подкомандой можно указать `--id R004 --id R009`. Для точного текста правила вместо `--dialogue-py` используйте `--rules-file`.

Артефакт фиксирует хеши датасета и точного правила, предсказания, ошибки бэкенда отдельно от ошибок качества. Счётчик semantic_review_pending не выдаёт наличие мысли за правильность. В неоднозначном кейсе, где нужно сохранить только часть или держать её внутри задачи, результат проверяется по expected_meaning. Для сохранения результата такой оценки передайте `--manual-review review.json`: объект ключей ID с полями `errors` (например, `missing_assertion`, `unwanted_assertion`, `misattribution`, `scope_distortion`) и `note`.

## Проверка движка

Слепой промпт-тест не тестирует очередь, проверяющего и транзакцию. Для обязательных R-кейсов с батчем в датасете есть отдельные native_expectations. Настоящий прогон использует отдельную временную SQLite на каждый кейс, обычный захват и обработку, один и тот же реальный генератор и проверяющий на сравниваемых ревизиях. Нужно проверить статус worker, число сырых записей, число Construct, содержимое мыслей и источники. Никакая вручную размеченная строка не доказывает прохождение этого прогона.

## Метрики сравнения

- Для каждой ветки зафиксируйте хеши набора и правила, ревизию кода, точные версии генератора и проверяющего, настройки моделей и число попыток. Сравнивайте одинаковые кейсы и показывайте отдельно одиночные реплики, батчи и обязательные регрессии.
- Показывайте лишние мысли среди эталонно пустых кейсов (с числителем и знаменателем), пропуски, ошибки источника, искажение смысла или области действия, число кейсов с незавершённой смысловой проверкой, сбои запуска и неполное покрытие. Наличие мысли и отсутствие автоматических ошибок ещё не означают, что мысль верна.
- Для прогона штатного движка собирайте число вызовов генератора и проверяющего, входные и выходные токены, время до пригодного результата (медиану и p95 с размером выборки), долю переиспользованных результатов, а также число исходных записей, Construct и сохранённых мыслей. Эти метрики должен передавать штатный движок или адаптер; промпт-раннер сам их не измеряет. Отсутствующее измерение помечайте «не измерено», а не нулём.
