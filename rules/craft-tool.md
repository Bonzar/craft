# Механика инструмента Craft

Правила про сам инструмент: как читать и писать блоки через Craft MCP. Правила про содержимое базы живут в Craft, в разделах сферы «Личное»: вход через «Сущность базы #раздел», «Сущность по шаблону #раздел» и «Текст базы #раздел».

## Команды

Команды Craft (`blocks get/add/update/move/delete`, `tasks add/update`, `search`, `documents …`, `collections …`) — это команды Craft MCP, не shell. Чтение выполняется read-capability, запись — write-capability, сама команда идёт аргументом. Через терминал их не запускают, отдельного CLI `craft` нет.

Точка с запятой внутри полезной нагрузки записи (`--markdown`/`--json`) сохраняется и в одиночной, и в батч-команде: парсер батча учитывает кавычки и не режет по «;» внутри строки.

Батч из нескольких команд через «;» не возвращает ID созданных блоков — нужны ID, пиши по одной команде или перечитывай страницу после батча.

## Чтение

Чтение базы — через markdown (`--depth -1`). Одиночная сущность (заметка, тема, задача, алгоритм, раздел) читается на `--depth -1` — целиком, с подстраницами. Крупные контейнеры (проект, сфера) на -1 не читаются — точечно по нужным секциям.

Read-before-write: прочитать целевой блок перед правкой, не править вслепую. Целевая страница читается сама (`blocks get` по её id): contentPreview родителя обрезан и состояние страницы не показывает. Страница с пагинацией дочитывается по `--cursor` до конца — выводы, Резюме и правки по недочитанной странице не делаются.

Для delete и move — включая положение блока сейчас (родитель и соседи) свежим чтением: конкурентные правки Влада перемещают блоки, ID не привязан к месту, знание «где он лежал» из истории диалога устаревает.

Состав этапов проекта читается со страницы проекта: `blocks get ПРОЕКТ --depth 2` выводит рядом этапы, живые задачи соседями и закрытые внутри этапов. Чтение `blocks get` по ID этапа показывает только закрытые — состав этапа так не судится.

Заметка дня читается по дате: `blocks get --date YYYY-MM-DD` (или `today`).

`search` индексируется с лагом: свежую правку проверять прямым `blocks get`, а не поиском.

Дата создания или изменения конкретного блока — только из его метаданных: `blocks get --fetchMetadata` даёт `createdAt` и `lastModifiedAt` на каждом блоке. `createdAt` из search-результата и из обычного чтения — дата корневого блока (документа), не вложенного: приписывать дату документа отдельному блоку нельзя.

Поиск входящих ссылок — `craft-sync --backlinks ‹block-ID›`: один вызов отдаёт все ссылающиеся блоки со страницами. Индекс живёт в Craft-доке «🔧 Служебный: кэши craft-sync» и дообновляется каждым вызовом по датам документов; видит только документы в scope connect-ссылки. Фолбек без бинарника — `search` по НАЗВАНИЮ цели: ссылки рендерятся текстом названия и находятся, по block-ID поиск не находит (ID хранится атрибутом ссылки, не текстом).

## Запись

Запись и правка — только через `--json`: блок-объект, где структурные поля (`indentationLevel`, `textStyle`, `listStyle`, `taskInfo`) заданы явно, а текст идёт полем `markdown`, всё в одном атомарном вызове (add/update). В `add --json` обязателен ключ `type` (`text`, `page`, `code`, `richUrl`, `line`, `table`, `image`, `video`, `file`). Полная схема и типы блоков — в `blocks learn json`. `--json` вернул ошибку валидации — сверься с `blocks learn` и почини payload. Флаг `--markdown` при записи не используется — он нормализует отступ к 0 и не несёт структурных полей, а update перепарсивает текст. `--siblingId` и `blocks move` уровень не меняют. Удаление — `blocks delete --id/--ids`.

Вложенный массив `content` в `blocks add --json` работает: страница создаётся вместе с телом одним вызовом, ответ возвращает ID всех блоков.

`blocks update` сливает переданные поля с текущими, а не заменяет — и на верхнем уровне, и внутри `taskInfo`: что не передал, остаётся. Убрать подполе `taskInfo` (`deadlineDate`, `scheduleDate`) — передать его со значением `null`; опустить — оставит старое. `blocks update` с `--json` для блока со списком или отступом обязан нести `listStyle` и `indentationLevel`, иначе они сбрасываются.

Verify-after-write: после операции результат проверяется свежим чтением затронутого места, а не diff-ом из ответа вызова — diff показывает переданные поля и молчит о сброшенных. Обязательно после структурных операций: move, смена `listStyle`, пакетные правки. Пакет правок сверяется и целиком, не только по шагам: после выполнения итоговое состояние затронутой сущности перечитывается и сравнивается с целью — пошаговые проверки не ловят потерянный между шагами блок, разъехавшиеся отступы, недоехавшую секцию.

Пакет `blocks add` с одним `--siblingId` и `--position after` инвертирует порядок (каждый встаёт сразу после якоря). Серию блоков вставляй одним многострочным вызовом, цепочкой от предыдущего нового блока либо `--position before` одного и того же соседа (порядок сохраняется). Пакетный `blocks move --ids id1,id2,… --targetId ЦЕЛЬ --position end` работает и сохраняет порядок блоков — перенос секций и групп делать им, а не по одному блоку. Корневой блок документа через `blocks move` не переносится — переносятся его дети пакетом.

Подстраница в теле заметки оформляется карточкой: перед ней тонкий разделитель (`line extraLight`), сам page-блок — `blocks update` с `textStyle "card"` и `cardLayout "regular"` (в raw хранится как `pageCard`). Реальный page-блок update-ом в текст не превращается: `textStyle` меняется, тип page остаётся. Разворачивание подстраницы в тело — перенос её детей наружу пакетным move и удаление опустевшей страницы (перед delete — поиск входящих ссылок).

`invalid:out_of_scope` в ответе тулзы (add/update) — ложь: перечитай блок свежим `blocks get`, ссылка цела. `invalid:out_of_scope` в самом свежем `blocks get` — реальная поломка: подсветить Владу и предложить исправление. Блок-цель со входящими ссылками не удаляй (delete рвёт, update безопасен).

Угловые скобки, образующие HTML-тег, Craft при записи отклоняет с явной ошибкой («Unexpected HTML token»), а не молча теряет — запись падает целиком. В тексте вместо них кавычки-ёлочки; для настоящего кода — блок `type code`, там скобки сохраняются.

Сетевая ошибка или обрыв вызова (5xx, таймаут) — не бросать после одного-двух мгновенных повторов: окружение автономное, ретраить с экспоненциально растущей паузой — предел одной паузы 1 час, общий бюджет 8 часов с первой ошибки. Длинную паузу держать отложенным пробуждением сессии, а не блокирующим ожиданием. Ошибка или обрыв вызова записи — исход неопределён: сперва свежий рид фактического состояния, потом решение о повторе.

Корневой блок дока через `blocks delete` не удаляется. Документ целиком удаляет `documents delete --document` — мягко, в корзину на 30 дней, восстановление через `documents move` в unsorted.

## Ссылки, даты, внешние адреса

Ссылка внутри блока Craft — блок-ссылка на `block://‹id›` из свежего `blocks get`: родной blockLink с бэклинком, web-URL не использовать. `craftdocs://` на записи принимается, но нормализуется в тот же `block://` — писать его в базу смысла нет. Текст ссылки (в квадратных скобках перед адресом) задаём точной копией актуального названия цели вместе с её тегами из того же свежего чтения: при точном совпадении Craft при переименовании цели сам обновляет тексты входящих ссылок, а сокращённый или произвольный текст из этой синхронизации выпадает. Голый `block://‹id›` без текста в квадратных скобках превращается в обычный текст, не ссылку.

Дата-ссылка ставится в поле markdown ссылкой `[текст](date://ГГГГ-ММ-ДД)` — Craft делает нативный dateLink. Токены `@дата` и `[[дата]]` дату не создают, остаются текстом. Тильда (~) в тексте не используется.

Внешний URL (магазин, соцсеть, сайт) — отдельным richUrl-блоком (JSON: `type richUrl` + `url`), а не markdown-ссылкой текстом: Craft рисует карточку и сам тянет заголовок. Сайт отдал мусорный title (Yandex, Link, голый домен) — задать title явно апдейтом; в апдейте richUrl поле `url` обязательно. richUrl на craftdocs://-адрес не делаем — выйдет безликая карточка Link вместо родного blockLink.

Кликабельная ссылка на Craft в чате — https-ссылка `docs.craft.do`: клиентские поверхности гарантированно распознают http(s). Space Влада — `cd8bace6-98dd-7481-9d43-c38a37e9b6a4`. Блок: `https://docs.craft.do/editor/d/‹SPACE›/‹rootBlockId›/x/‹blockId›`. Документ целиком — тот же URL без `/x/‹blockId›`. Оба id — обычные block-ID из чтения. Ссылка — для перехода Владом, не вход для MCP: `documents resolve-link` отвечает на неё «вне scope», в командах берётся block-ID напрямую.

## Таблицы

Таблица — один блок. Внутри Craft у неё есть дочерние блоки-ячейки, строки и столбцы со своими ID, но наружу они не отдаются: чтение на любой глубине показывает только rows со значениями, ID ячейки по `blocks get` и по REST-API отвечает «Block not found», а каждая запись таблицы пересоздаёт все ячейки с новыми ID — даже запись того же содержимого. Значит, любая правка ячейки — перезапись всей таблицы, и свежий `blocks get` именно этого блока делается прямо перед update, без других действий между чтением и записью. Чтение из более ранних сообщений свежим не считается: правки в ячейках, сделанные за это время в приложении, перезапись молча затирает.

Строки и ячейки таблицы задаются только markdown-таблицей в поле markdown: строка заголовка, строка-разделитель `| --- |`, строки реальными переносами. Это ограничение самого Craft, а не инструмента: и MCP, и REST-API на любое другое поле у таблицы отвечают «Table blocks can only be updated via markdown», структурную запись строк (rows, cells) отклоняют и при создании, и при правке, частичной правки строки или ячейки нет. Во всех строках одинаковое число ячеек: лишний или потерянный `|` молча сдвигает ячейки и меняет число столбцов — после записи число столбцов и строк сверяется свежим чтением.

Строка-заголовок и столбец-заголовок, выравнивание текста в ячейке, ширина столбцов через MCP и REST-API не задаются: полей у таблицы нет, `textAlignment` и флаги заголовков отклоняются, двоеточия выравнивания в строке-разделителе (`| ---: |`) при записи стираются до `| --- |`. Это делается в приложении. Что через инструмент не получается — подсветить Владу, а не обходить лишним столбцом, строкой или пометкой в тексте.

Ссылка в ячейке: ячейка целиком из `[Текст](block://id)` даёт родной blockLink и переживает и add, и update. Ссылка плюс обычный текст в одной ячейке — только с экранированными скобками после ссылки: `[Текст](block://id) \(г\)` — blockLink покрывает текст ссылки, «(г)» остаётся текстом. Несколько ссылок в одной ячейке тоже живут: `[А](block://id1) или [Б](block://id2) \(шт\)` даёт два blockLink. При создании таблицы (add любым способом) ячейка с текстом после ссылки теряет ссылку и становится простым текстом, при update — сохраняет. Поэтому таблица с такими ячейками пишется в два шага: add, затем update той же разметкой. Скобки без экранирования после ссылки убивают ссылку. Обходы `\ (…)`, `&nbsp;`, `&#40;`, пробел нулевой ширины остаются в ячейке буквальными символами — не использовать. Ссылки в таблице проверяются чтением `--format json`: у ячейки в attributes есть blockLink со start и end ровно по тексту ссылки.

Формула в ячейке — текст с «=» в начале, адреса ячеек в формате A1 (`=B2*(C1/B1)`). Значение показывает приложение, чтение через MCP возвращает текст формулы. При перезаписи таблицы формулы повторяются в новой разметке заново, адреса — под новое положение строк и столбцов.

## Коллекции и картинки

Коллекции: создание — `collections create`, элементы — `items-add`/`items-update`, вид — `views-create`/`set-active` (table, gallery, kanban). Колонки называть ЛАТИНИЦЕЙ: ключ колонки собирается из латинских символов имени, кириллица стирается (у русских имён ключи вырождаются в пустоту и _N-суффиксы, флаги по display-имени падают), при переименовании колонки ключ пересобирается заново. Вырожденные ключи — писать значения через `items-add --items JSON` с ключами из `collections schema` либо переименовать колонки латиницей через `schema-update` (перечислить ВСЕ сохраняемые колонки: опущенная удаляется вместе со значениями, тела элементов целы). Элемент коллекции — page-блок: тело добавляется `blocks add/move` по ID элемента, картинка первым блоком тела становится превью карточки галереи. Коллекции в заметках — контент, не структура: живут где угодно, форма системой не диктуется.

Картинка с внешнего URL — блок `type image` с полем `url`: сервер Craft сам скачивает файл и перекладывает на res.craft.do (в ответе `uploaded:true`, res/r.craft.do-адрес). Хост должен быть доступен серверу — tildacdn, avatars.mds.yandex, 101hotelscdn тянутся, kurortix нет: недоступный URL молча выпадает из пакета (или add отвечает «Document not found»), остальные блоки встают. Залитую картинку смотри через `images view --url ‹res/r.craft.do-адрес›` и убедись, что кадр — именно запрошенный, прежде чем оставить. Влад просил конкретное фото — общим не подменять: не тянется один источник, искать другой доступный, а не ставить что попало.

## Задачи

Задача всегда инлайн: text-чекбокс «- [ ] Название #задача/оценка», `textStyle body` — независимо от наполнения. Наполнение живёт внутри чекбокса детьми: ссылки шапки (этап; знание — если есть) на `indentationLevel 0`, содержательное тело — дальше секциями по шаблону «2. Задача» тем же уровнем. Пустое тело (только название и ссылки шапки) — законное финальное состояние. Без «- [ ]» выйдет обычный текст, не задача.

Статус задачи читается из `taskInfo.state` в json (todo / done / canceled), не из markdown-чекбокса: canceled в markdown всегда «- [ ]» с зачёркиванием, статус по нему не судится.

Содержимое тогглов «Зависит от» и «Следующий шаг» — соседний блок сразу после тоггла на +1 от него, не ребёнок блока тоггла: вложение внутрь превращает тоггл в подстраницу.

Вложение детей в text-чекбокс может навесить скрытый явный `textStyle page` (в raw — `pageRegular`, на чтении неотличим от производного: `blocks get` отдаёт `type page` у любого блока с детьми, raw виден только в before-diff ответа записи). Снятие — один вызов `blocks update --json` без полей markdown и taskInfo: только `textStyle body` и текущий `indentationLevel` — дети, состояние задачи и время закрытия остаются целы. Работает и на регулярках: repeat и логбук не страдают. `textStyle` из чтения в update не копируется: передашь page — навесишь его по-настоящему, в update задачи `textStyle` всегда body.

Время закрытия ставит только сервер Craft: `completedAt` и `canceledAt` в payload игнорируются везде (add, update) — фактическое значение всегда момент вызова, принёсшего закрытое состояние. Любой вызов, заново несущий закрытое состояние, перештамповывает время на «сейчас»: `blocks update` с полем markdown закрытой задачи (с taskInfo или без) и `tasks update --state done` по уже закрытой. Update без поля markdown состояние и время не трогает. Это штатное поведение Craft, принятое как допустимое: содержательная правка закрытой задачи сдвигает её completedAt, точная история закрытия не гарантируется.

Создание: `blocks add --siblingId ПРЕД_ЗАДАЧА_ИЛИ_ЭТАП --position after --json`, markdown «- [ ] [env] Название #задача/оценка», `indentationLevel` +1 от этапа, `textStyle body`. Тело — по одному блоку через `blocks add --id ЗАДАЧА --position end`. Имя — полная формулировка действия, не ключевые слова и стрелочки; только название и теги, тикет внутри блока, окружение в квадратных скобках, первое слово после скобок с заглавной.

Срок — плановая дата работы или события, она же дата задачи в `taskInfo.scheduleDate`. Дедлайн — только крайний срок «надо успеть к…», отдельное поле `taskInfo.deadlineDate`. Поле выбирается по смыслу даты, а не по уже стоящему у задачи; стоящее не в том поле — исправить, не переиспользовать.

Перенос живой задачи в этап или между этапами: уровень цели уже известен до операции из прочитанного json — сравни его с уровнем переносимого блока. Move: `blocks move --id ЗАДАЧА --targetSiblingId СОСЕДНЯЯ_ЗАДАЧА_ЭТАПА --position after` (соседних нет — блок этапа). Move уровень не меняет и не принимает его: уровни совпадают — один вызов и всё, отличаются — следом заранее известный update с целевым `indentationLevel`.

Перенос закрытой задачи внутрь этапа: `blocks move --id ЗАДАЧА --targetId ЭТАП --position end`, затем `blocks update --json {"indentationLevel":0}` — и ТОЛЬКО это поле. Не добавлять `textStyle`: чтение показывает «type: page» у любого блока с детьми — скопируешь «page» в этот update, навесишь его по-настоящему.

Повторяемость — механикой повтора Craft: в `taskInfo.repeat` задаём `frequency` (weekly/monthly/yearly) и `startDate`, для yearly Craft сам выведет months и days из даты. `type: fixed` — строго по расписанию, `flexible` — отсчёт от выполнения.

## Проекты, этапы, блоки

Новый проект — отдельный документ в папке «Проекты». После создания скопировать на корневой блок стиль дока сферы: styling из свежего чтения — фон, цвета, шрифт, разделители.

Этап: один вызов `blocks add --siblingId СОСЕДНИЙ_ЭТАП --position after --json`, markdown «- [ ] ### Этап N: Название», `indentationLevel` = уровень соседнего этапа (+1 от тоггла «Этапы проекта»).

Блок: `blocks add --json`, markdown «- [ ] ## Блок N: Название», `textStyle h2`, `indentationLevel 1` (+1 от тоггла), `taskInfo` с дедлайном. Вложенные этапы — h3 на уровне 2, их задачи — уровень 3.

Закрытый этап переезжает внутрь своего Блока его ребёнком: `blocks move --id ЭТАП --targetId БЛОК --position end`, затем `blocks update --json` с одним полем `indentationLevel 0`.

Закрытие этапа: один вызов `blocks update`: markdown «- [x] ### Этап N: Название» и ОБЯЗАТЕЛЬНО `indentationLevel` текущего уровня этапа — без него уровень сбросится в 0 и этап выпадет из тоггла «Этапы проекта». Этап остаётся чекбоксом с историей внутри, в тоггл не превращается. После — проверка свежим чтением: этап отмечен, закрытые задачи внутри.

Переезд завершённого проекта в архив: проект — страница-блок внутри дока сферы, переезд — `blocks move --id ПРОЕКТ --targetId ПОДСТРАНИЦА_АРХИВ_СФЕРЫ --position end`. Проект-документ корнем не переносится: его дети переезжают пакетом в новую страницу Архива, в документе остаётся строка-указатель.
