# review-discussion

Переносимый consumer пользовательских комментариев из опубликованного private
Site. Общий модуль реализует HTTP, события, lease и подтверждения доставки;
`review-discussion-codex` реализует только native queue существующего чата.
Контракт адаптера и API — в `data/delivery-contract.md`.

Python 3.12+, стандартная библиотека, POSIX flock. macOS и Linux поддерживают
этот механизм; Windows требует отдельной реализации process lock. Codex
Cloud и другие окружения должны разрешать исходящий HTTPS и фоновый процесс.
Наличие переносимого модуля само по себе не переносит локальный чат между
машинами. На выбранном host должен работать runtime с загруженным нужным UUID.

## Настройки окружения

- `REVIEW_POLL_ENABLED=1` разрешает автозапуск на `session-start`, `after-compact`
  и `prompt`. Без флага хук молчит и пишет причину через штатный trace.
- `REVIEW_URL=https://example.chatgpt.site` — только HTTPS origin конкретного
  Site, без пути, query, fragment, credentials и нестандартного порта.
- `REVIEW_SESSION` — стабильный ID документа/обсуждения, поле `session` в API.
  `review` обозначает неизменную ревизию этого документа. Другая сессия может
  открыть тот же документ по ID и отдельно подписаться на его комментарии.
  Все ревизии входят в один журнал событий. Подписки разных чатов имеют
  независимые cursor/lease: подтверждение одного чата не забирает событие у другого.
  Чтение документа или публикация новой ревизии сами подписку не создают.
- `REVIEW_TOKEN` — сервисный credential private Site для этого origin.
  Он передаётся только через env или `--token-stdin`, не через аргументы,
  файлы репозитория, local state или журналы. Не включайте shell tracing.
- `REVIEW_TARGET_THREAD` необязателен: по умолчанию UUID текущей сессии из
  события. Явное значение обязано совпадать с текущей сессией.
- `REVIEW_CODEX_EXECUTABLE` — путь к Codex; если не задан, используется `which`
  в текущем PATH. Путь машины разработчика не зашит.
- `CODEX_HOME` — необязательный явно выбранный профиль, наследуется Codex
  без изменения. Он должен совпадать с профилем runtime, принимающего очередь.

Автозапуск использует режимы core `modes.json`, личного и source конфига.
Модуль сам готовит `bin/review-discussion` на старте; установщик только
раскладывает части. Подготовка не использует сеть и ничего не скачивает.
Вторая попытка старта проверяет lifetime flock и привязку PID-записи. Lock
передаётся дочернему процессу через fd, без окна между parent и child.
Устаревший PID не блокирует перезапуск; произвольный PID не завершается.

## Ручной bootstrap существующей сессии

Из source checkout, без полной установки (переменные выше уже заданы):

```sh
python3.12 modules/review-discussion/hooks/module.py bootstrap check \
  --session CHAT_UUID --harness codex --state-dir /path/to/jarvis-state
```

`check` только валидирует настройки и наличие адаптера; сеть и queue не вызывает.
Для запуска после проверки используется та же команда с `start` вместо `check`.
`run` запускает consumer в foreground. Credentials можно прочитать защищённым
вводом и подать в stdin с `--token-stdin`; флаг не содержит сам секрет.
`status` показывает статус, lifetime lock и диагностический PID. `stop` ставит
core mode `review-discussion=false`, процесс завершится при следующей проверке.
Он не посылает сигнал процессу по потенциально устаревшему PID. Чтобы снова
разрешить запуск, выставите режим `review-discussion=true` штатным core
`mode.set_session` или уберите явное выключение из session modes.

Подготовленный entrypoint вызывается как `python3.12 .../bin/review-discussion`
с теми же аргументами. Нужно явно выбрать Python 3.12+: системный `python3`
на macOS может быть 3.9.

## Работа и наблюдение

При простое один claim раз в 5 секунд: 12 запросов/минуту на consumer.
После успешной доставки следующая итерация идёт сразу. HTTP timeout 8 секунд,
queue timeout 10 секунд. Ошибки повторяются с паузами 5, 10, 20, 40, 60 секунд;
дальше пауза остаётся 60 секунд. Сетевые ошибки не удаляют серверные события.

В session Storage лежат `review-discussion-process.json`,
`review-discussion-status.json`, `review-discussion.jsonl`, lifetime `.lock`
и `review-discussion-sent-*.json` с eventId/queue ID. Текст комментариев и токен
туда не записываются. Ошибки bootstrap и фоновой доставки попадают также в
core `trace.jsonl` с режимом и autonomous flag. Изменение URL/session при
живом consumer отклоняется: сначала остановите старый процесс. Изменение
credentials требует перезапуска consumer.

После crash новый процесс стартует на следующем session-start/compact/prompt
или ручным bootstrap; автономного OS supervisor этот модуль не ставит.
Компактация не сбрасывает sent journal. Смена host сохраняет server cursor,
но локальный sent journal автоматически не переносится. Два host могут
конкурировать за lease; занятая lease не даёт queue. После истечения lease
восстановление возможно на новом host с доступом к тому же чату.

У Codex 0.166.0-alpha.6 межпроцессный SQLite watcher проверяет изменения раз
в 10 секунд. При общей DB и загруженном idle чате это даёт суммарно примерно
до 15 секунд обнаружения плюс сеть/начало генерации. Занятый чат обрабатывает
очередь после текущего хода; закрытый/unloaded чат модуль не возобновляет.
Одиночный live queue probe в текущем Desktop ранее подтверждён родительским
агентом. Этот модуль сам не выполнял live доставку.

## Проверки

```sh
python3.12 -m unittest tests.test_review_discussion
python3.12 -m compileall -q modules/review-discussion modules/review-discussion-codex
```

Тесты используют временный Storage, поддельный HTTP transport и subprocess
mocks: никаких реальных сообщений, network, установок и фоновых consumer.
Smoke после разрешённого запуска: дождаться первого успешного claim; добавить
один новый комментарий в Site; увидеть тот же eventId в текущем чате и ответ;
повторный ACK/перезапуск не должен создать второй queue для известного eventId.
Проверить отдельно Ок: он меняет прогресс, но не создаёт событие/сообщение.

TDD evidence: `2e3c43f` — RED 13 целевых тестов, модулей ещё нет;
`f5e86bd` — GREEN 13. `1622605` — RED дополнительных bootstrap/status/trace
проверок; `3be5bda` возвращает все 16 проверок в GREEN.
`7c5c4f3` — RED валидного Unicode пакета из 50 событий; HTTP bound увеличен
до 8 MB с сохранением ограничения размера ответа, итог — 17 целевых проверок.
