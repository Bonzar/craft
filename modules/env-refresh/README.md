# env-refresh

Сессия узнаёт, что её набор модулей устарел. В облачном Claude набор ещё и
догоняет main сам.

## Зачем

Набор модулей ставится один раз, а репозиторий, из которого он поставлен,
меняется дальше. Сессия на старом наборе работает по старым правилам и скиллам,
а человек не знает, что окружение надо обновить.

В облачном Claude это особенно остро. Модули ставит setup-скрипт окружения, а он
выполняется один раз — при сборке снимка окружения; дальше сессии стартуют из
снимка, пропуская скрипт (дока cloud-environments, раздел Environment caching,
19.09.2026). Снимок пересобирается сам примерно раз в семь дней, кнопки нет.
Код репозитория платформа отдаёт свежим на каждом старте, а набор в домашнем
каталоге остаётся до недели старым (проба 19.09.2026).

## База: сверяет и предупреждает

База — установленная копия модуля. Она стоит в каждом харнесе (поля `harness`
в шапке нет) и на старте сессии, по порядку:

- автономный прогон (`JARVIS_AUTONOMOUS=1`) — молчит: человека нет;
- облачный Claude, и в чекауте проекта (`CLAUDE_PROJECT_DIR`) лежит адаптер —
  молчит: набор догоняет он, второй голос ни к чему;
- журнала установки нет — молчит: набор в этом окружении ставили не мы.
  Журнал база ищет над своим каталогом модулей (`…/jarvis/installed.json`), так
  что каталог настроек харнеса ей знать не нужно;
- сверяет каждый источник набора (`hooks/freshness.py`) и говорит в контекст
  одну строку, если есть что сказать.

Сверяется не голова репозитория, а коммиты в файлы набора: коммит мимо набора
ничего в нём не меняет, а транк Аркадии движется каждую секунду.

- **Главный набор** — по файлам, которые ставит установщик: `modules`, `core` и
  `tools/jarvis-install`. Против main у origin: `git ls-remote`, объекты
  доносятся `git fetch`, только если их в клоне нет, дальше `git diff
  --name-only` по этим путям.
- **Дополнительный источник** (`--extra-modules`, `JARVIS_EXTRA_MODULES`; junk
  в Аркадии) — по своей папке целиком, как в UI Аркадии у папки последнее
  изменение любого файла внутри. Установщик пишет в источник журнала
  `extra_origins`: путь к папке и последний коммит в неё. База сверяет его с
  главной веткой той системы, в которой папка лежит: git — с main у origin,
  arc — с `arcadia/trunk` (`arc fetch trunk`, `arc log -n1 … -- .`,
  `arc diff --name-only --relative=.`). Какие модули изменились, видно по
  изменённым файлам: одна сверка на источник при любом числе модулей.

Исход сверки источника — один из четырёх:

- **свежий** — файлы источника на удалённом те же; молчим;
- **отстал** — удалённое ушло вперёд; говорим, что окружение надо обновить,
  и называем обе версии: последний коммит в файлы источника у нас и там, с
  датой, и какие модули изменились;
- **выбор человека** — набор поставлен из ветки (в git коммит не предок main;
  в arc коммит trunk в папку не новее установленного) или модуля на удалённом
  нет вовсе; молчим, причина в журнале модуля;
- **не проверить** — команда не ответила, журнал не назвал коммит, папка не
  под версиями; говорим с причиной.

В git «отстал» — это предок: коммит ветки предком main не станет. В Аркадии
trunk линейный, а ветки вливаются в него склейкой, и коммит ветки не бывает
предком trunk даже влитым. Поэтому у arc «отстал» — это коммит trunk в папку
новее установленного, а одинаковое содержимое папки — «свежий», какой бы коммит
его ни принёс.

База ничего не ставит и не меняет: решение обновить окружение за человеком.

## Адаптер облачного Claude: догоняет main

Копия модуля из чекаута репозитория — адаптер к базе. Её зовёт строка хука в
`.claude/settings.json` самого репозитория: она приезжает с чекаутом и потому
свежая по построению, обновлять её незачем. Вне облака (`CLAUDE_CODE_REMOTE`
не `true`) она молчит: предупреждает установленная копия.

В облаке адаптер берёт вердикт базы по главному набору, сверяя его с чекаутом
сессии:

- набор отстал — разворачивает main во временный каталог рядом (`git archive` и
  распаковка) и передаёт установку копии модуля из этой распаковки;
- получилось — печатает справку: набор обновлён с такого коммита на такой,
  перечислены изменившиеся модули; старт продолжается;
- не получилось — печатает одну строку с причиной; набор остаётся прежним;
- любой другой исход — то же, что сказала бы база.

Коммит мимо файлов набора набор не переставляет: тогда в журнале остаётся
прежняя голова, и следующий старт снова сверит её с main, не скачивая
объектов, которые в клоне уже есть.

### Локальный Claude

Адаптер в локальном Claude не годится (проба 27.10.2026 в песочнице с
раскладкой мака: набор из основного чекаута, сессия в worktree). Без признака
облака он молчит. С признаком облака переустановка проходит, но источником в
журнал уходит worktree сессии, и после его удаления база уже не может сверить
набор. Кроме того, локально каталог настроек общий для всех идущих сессий, а
адаптер на время установки отставляет набор в сторону у них из-под ног.
Поэтому локально набор только предупреждает.

### Две роли одного файла

**Копия из чекаута — запускатель.** Сверяет набор с main, доносит объекты и
разворачивает main рядом — и на этом его работа кончается.

**Копия из распаковки — работник.** Установку делает она, своим же установщиком
из того же коммита. Договор между модулем и установщиком — флаги и форма
журнала — живёт в одном коммите, и стороны обязаны браться оттуда же. Иначе
выходит то, что поймала живая проба 19.09.2026: модуль с ветки позвал
установщик из main флагами, которых в main ещё нет, и установщик отказал на
разборе аргументов.

Поручение работнику — два факта: чекаут репозитория и коммит, из которого
ставим. Всё остальное он берёт сам: каталог настроек — у идущего харнеса
(`CLAUDE_CONFIG_DIR`, иначе `~/.claude`), харнес, каталог состояния,
интерпретатор и дополнительные источники — из записи источника в журнале.
Наружу работник отдаёт готовую строку для модели, а причину отказа — последней
строкой stderr.

Копии модуля в распаковке нет — передавать работу некому: одна строка в
контекст, ничего не тронуто.

Что произошло, видно и в журнале модуля в зоне сессии (`env-refresh.jsonl`): по
строке на ход, с исходом сверки каждого источника и замером времени.

## Что не трогает

- Рабочее дерево сессии, её HEAD и ветку: ни checkout, ни reset, ни смены
  ветки. `git fetch` доносит объекты в хранилище клона, и только.
- Набор, поставленный из ветки, и набор, про который не доказано, что он отстал.
- Окружение без журнала установки.
- Про Craft, поставщиков данных и стартовый контекст не знает ничего и в их
  цепочку не встраивается: он только про свежесть окружения.

## Провал оставляет прежний набор целым

Прежний набор уходит в сторону одним переименованием — каталог `jarvis` и части
в местах харнеса, — а настройки харнеса копируются рядом, первыми, до единого
переноса. Установка дошла до конца: отставленное удаляется. Не дошла: набор
возвращается на место целиком, а то, что успела создать неудачная установка,
убирается.

Отставляется переименованием, а не копией: набор весит мегабайты.

Запасных путей нет: либо набор обновился, либо в контекст уходит одна строка с
причиной — последней строкой того, кто отказал, целиком, а не первыми знаками
вывода.

## Успех старт не останавливает

Сначала модуль печатал остановку: считалось, что контекст этого старта собран
прежним набором. Замер 19.09.2026 на claude 2.1.278 это опроверг. Сессия
поднималась на старой ревизии, модуль догонял main, и в стартовый контекст
доезжали новые правила (различающая строка `behavior.md`), новое описание
скилла и новые данные поставщика — оба маркера пробы новые, старых в контексте
нет. То есть харнес читает правила, скиллы и данные уже после работы модуля.

Поэтому модуль печатает справку, а не остановку. Остановка была вредна вдвойне:
она утверждала неправду и вешала сессии без человека — дочерняя облачная сессия
сжать контекст себе не может и просто простаивала.

Замер сделан на одном харнесе и одной версии. Поменяется порядок старта —
замер повторяется маркерами модуля-пробы: `probe/skill/SKILL.md` и
`probe-data/data/hello.md` несут по строке, различающей версии набора.

Гарантия эта неполная, и строка говорит об этом прямо. Правила и скиллы харнес
читает сам, после хуков, — тут порядок за него. А соседние хуки старта идут
параллельно с обновлением: что поставщик успел прочитать до подмены, уедет в
контекст из прежнего набора. В обоих замерах 19.09.2026 соседи собирали уже
после подмены и печатали новое, но это наблюдение, а не порядок: гонка
остаётся. Чтобы её убрать, цепочке печати пришлось бы ждать вердикта модуля
свежести, а это отменяет решение «модуль не встраивается в цепочку стартового
контекста» — отдельный разговор, не правка.

## Чем платим

Холостой ход — один `git ls-remote` на главный набор, он идёт на каждом
старте сессии, где есть наш набор, во всех харнесах. Замер 27.10.2026 на маке:
`git ls-remote` к GitHub по ssh — 2–3 с, раз в несколько прогонов до 14 с; вся
сверка набора на маке — 2–14 с. Хуки старта идут параллельно, так что это
время не складывается с остальными, но старт ждёт самого долгого.

Модуль в Аркадии стоит дешевле: `arc fetch trunk` ~0,15 с (VFS тянет только
ссылку), `arc log -n1` по папке ~0,2 с, `arc diff --name-only` ~0,1 с — вся
сверка модуля 0,8 с; коммит папки при установке — 0,4 с на модуль (замер
27.10.2026).

Обновление идёт параллельно с остальными хуками старта: набор подменяется под
ногами у соседей, которые в это время ещё работают. Их вывод всё равно
собран прежним набором. Замер 19.09.2026 показал, что снимок Craft при этом
доезжает целым: пятнадцать кусков, все стыки на месте. Всю сетевую работу
модуль делает до того, как тронет установку, чтобы окно было как можно короче.

Собранное самими модулями (`bin/` — бинарник и отпечаток исходников рядом с
ним) возвращается на место после успешной установки: `bin` — не часть модуля, а
его собственный склад, и переустановка его не трогает.

Возвращается оно как есть, без сверки с отпечатком: если обновление поменяло
исходники модуля, сессия доработает на прежнем бинарнике, а пересоберёт его
хук модуля на следующем старте. Это лучше, чем остаться совсем без инструмента,
но знать об этом надо.
