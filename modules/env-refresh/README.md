# env-refresh

Догоняет набор модулей до актуального main на старте облачной сессии.

## Зачем

Модули ставит setup-скрипт окружения, а он выполняется один раз — при сборке
снимка окружения; дальше сессии стартуют из снимка, пропуская скрипт (дока
cloud-environments, раздел Environment caching, 19.09.2026). Пересобирается
снимок сам: при правке скрипта или сетевых хостов и примерно раз в семь дней.
Кнопки пересборки нет.

Поэтому в облачной сессии расходятся две вещи. Код репозитория платформа
отдаёт свежим на каждом старте: рабочий чекаут создаётся в момент старта и
стоит на голове main. А результат установки в домашнем каталоге — тот, каким
его застал снимок: до недели старый (проба 19.09.2026: чекаут на `a98961b2`,
`~/.claude/jarvis/installed.json` от 18.09, модулей из свежих PR в установке
нет).

Этот модуль сверяет набор с main и, если он отстал, ставит набор заново.

## Что делает

На событии «старт сессии», по порядку:

- нет признака облачной сессии (`CLAUDE_CODE_REMOTE` не `true`) — молчит;
- запущен не из чекаута репозитория — молчит (об этом ниже);
- спрашивает голову main у origin одним запросом `git ls-remote`: объекты ради
  сверки не качаются;
- сравнивает её с коммитом источника из журнала установки
  `‹каталог настроек›/jarvis/installed.json`; совпали — молчит совсем, ни
  строки в контекст;
- разошлись — доносит объекты `git fetch`, разворачивает main во временный
  каталог рядом (`git archive` и распаковка) и запускает оттуда
  `tools/jarvis-install` теми же харнесом, каталогом состояния и
  интерпретатором, какими поставлен нынешний набор;
- получилось — печатает в контекст остановку: набор обновлён с такого коммита
  на такой, перечислены изменившиеся модули, работать по этому контексту
  нельзя, нужно сжатие;
- не получилось — печатает одну строку с причиной; набор остаётся прежним.

Что произошло, видно и в журнале модуля в зоне сессии
(`env-refresh.jsonl`): по строке на ход, с замером времени.

## Откуда берёт main и куда ставит

Голова main берётся у `origin` того клона, из которого запущен хук, ветка
`refs/heads/main`. Ветка сессии в набор не попадает никогда: разработка — не
применение, и агент всегда работает по main, даже когда сессия стоит на рабочей
ветке.

Ставится набор в каталог настроек идущего харнеса: `CLAUDE_CONFIG_DIR`, а без
неё `~/.claude`. Каталог настроек задаёт сам харнес, а не прошлая установка:
ставить надо туда, откуда идущая сессия читает настройки. Остальные условия
установки — харнес, каталог состояния, интерпретатор — модуль берёт из записи
источника в журнале: из каталога настроек их не видно, а повторная установка
обязана повторить прежнюю.

Журнала нет вовсе — набор считается неизвестным и ставится заново.

## Почему работает только копия из чекаута

Модуль лежит в двух местах сразу: установленной копией в каталоге настроек и
исходником в чекауте репозитория. Обе копии стоят на одном событии, и обе
запускаются на старте.

Работает только копия из чекаута. Она приехала с чекаутом и потому свежая по
построению, а установленная копия — ровно то, что мы и собираемся заменить: ею
обновляться значило бы догонять main кодом недельной давности.

Копии разведены тем, где лежит файл модуля: над папкой копии из чекаута стоит
репозиторий с `tools/jarvis-install`, над установленной копией — каталог
настроек харнеса. Установленная копия пишет строку в свой журнал и молчит.

Зовёт копию из чекаута строка хука в `.claude/settings.json` самого
репозитория. Кода там нет, только вызов: код живёт один раз, в модуле.

## Что не трогает

- Рабочее дерево сессии, её HEAD и ветку: ни checkout, ни reset, ни смены
  ветки. `git fetch` доносит объекты в хранилище клона, и только.
- Ветку сессии в набор не ставит ни при каких условиях.
- Про Craft, поставщиков данных и стартовый контекст не знает ничего и в их
  цепочку не встраивается: он только про свежесть окружения.

## Провал оставляет прежний набор целым

Прежний набор уходит в сторону одним переименованием — каталог `jarvis` и части
в местах харнеса, — а настройки харнеса копируются рядом. Установка дошла до
конца: отставленное удаляется. Не дошла: набор возвращается на место целиком, а
то, что успела создать неудачная установка, убирается.

Отставляется переименованием, а не копией: набор весит мегабайты.

Запасных путей нет: либо набор обновился, либо в контекст уходит одна строка с
причиной.

## Успех останавливает старт

Контекст этого старта собран прежним набором: правила, скиллы и данные в нём
уже устарели. Поэтому модуль печатает не справку, а остановку — работать по
этому контексту нельзя, нужно сжатие.

После сжатия событие приходит уже с `source = compact`, то есть единым именем
«после сжатия». Модуль стоит только на старте сессии, поэтому на нём он вообще
не поднимается, и стартовый контекст печатается по новому набору.

## Чем платим

Холостой ход — один `git ls-remote`, он идёт на каждом старте облачной сессии.

Обновление идёт параллельно с остальными хуками старта: набор подменяется под
ногами у соседей, которые в это время ещё работают. Их вывод всё равно
негоден — он собран прежним набором, — а сессия останавливается на сжатие. Всю
сетевую работу модуль делает до того, как тронет установку, чтобы окно было
как можно короче.

Собранное самими модулями (`bin/` — бинарник и отпечаток исходников рядом с
ним) возвращается на место после успешной установки: `bin` — не часть модуля, а
его собственный склад, и переустановка его не трогает. Без возврата модуль
остался бы без инструмента до следующего старта сессии: своим хуком он
собирается на старте, а после сжатия хуки старта на него не выходят.
