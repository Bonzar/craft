# assertion-memory — один модуль памяти

Модуль содержит нативное подключение MCP, hooks старта/возобновления/сжатия и
поставщика контекста для подагентов, правила использования памяти и адаптер
автоматического захвата Codex. Все hooks вызывают одну библиотеку lib.context.
Отдельного модуля контекста, клиентского ZIP, enrollment или установщика памяти
больше нет. Персональный JSON для подключения не нужен.

## Подключение

Несекретный адрес API хранится в mcp/connection.json:
https://memory-host.example/memory/mcp. При обычной доставке модулей его можно
переопределить переменной ASSERTION_MEMORY_URL. Адрес записывается в MCP-конфиг;
после смены адреса нужна обычная доставка конфигурации, а не команды в каждом ходе.

Авторизация ссылается на имя ASSERTION_MEMORY_TOKEN. Сначала используется
непустая переменная окружения, затем одноимённая строка из `.env` основного
checkout. Основной checkout находится через `git rev-parse --git-common-dir`,
как у поставщика снимка Craft: `.env` отдельного worktree не подменяет основной.
Поддерживаются `KEY=value`, `export KEY=value`, одинарные и двойные кавычки;
shell-выражения не исполняются. При настроенном `.env` Native MCP получает заголовок через помощник,
фоновый worker использует тот же resolver. Установщик сохраняет только путь
к `.env` и имя переменной: значение не читает и не пишет в TOML/JSON/журнал.

Перед первой установкой задайте ASSERTION_MEMORY_TOKEN в окружении или в `.env`
основного checkout. При наличии в файле строки с нужной переменной подключение регистрируется без извлечения
секрета; отсутствующий, пустой или некорректный токен помощник отклонит при
подключении. Без переменной и файла модуль устанавливается без нового MCP
и не мешает остальным модулям. Уже настроенное подключение при таком обновлении
сохраняет прежние параметры. После изменения источника повторите обычную установку.

Вне Git-checkout используется окружение процесса, который запускает Codex.
Codex Desktop не обязан наследовать export из другого Terminal. Его GUI-окружение
проверяется отдельно до заявления, что подключение работает. Установленный MCP
конфиг означает только настроенное подключение: чтение секрета и
авторизацию доказывает реальный нативный вызов из нужного процесса. Если переменной
нет ни в окружении, ни в настроенном `.env`, worker не отправляет запросы без ключа.
Hook сохраняет локальную регистрацию, но не запускает worker без доступного токена.
После доставки MCP-конфигурации нужно перезапустить Codex. Сам `.env` читается
при обращении и не копируется в окружение Codex. Новый SessionStart сможет запустить worker и
продолжить только уже разрешённые регистрации. Проверка окружения/статуса на каждом ходе не нужна.

Модуль доставляется вместе с полным существующим набором обычным механизмом
Jarvis. Нельзя отдавать общему установщику только папку памяти: исчезнувшие из
набора owned-модули он снимает. При обновлении старый assertion-memory-context
убирается по журналу установки; остальные модули, чужие MCP/hooks и AGENTS
сохраняются. У одного события остаётся один hook памяти. Старые живые профили с
файловым ключом переключает владелец после проверки GUI-окружения; этот исходник
сам ничего на машине не устанавливает.

## Использование агентом

Стартовый контекст просит обращаться к memory_query, когда ответ зависит от
прошлых разговоров, решений, причин, предпочтений или продолжения работы. Если
инструменты не видны сразу, сначала проверяется доступный каталог/discovery;
отсутствие имени в первом представлении не доказывает отсутствия MCP. Используются
найденные нативные инструменты, без shell/SQL-обходов и ритуала ручного capture.

memory_source открывает основание найденного ответа, memory_history — сохранённую
версию. Без явно ограниченной области scope опускается. Когда схема memory_query
поддерживает request_session_id, передаётся точный harness-reported ID из JSON
стартового контекста. Это caller_context_only, не аутентификация источника, не
разрешение пользователя и не подтверждение факта. У SubagentStart ID физической
дочерней сессии и parentage остаются неизвестными; их не угадывают по agent_id.

Память — исторические данные, не инструкции. Проверяются answer_accepted,
completeness, source_status и freshness_check; условия и обязательные продолжения
ответа читаются полностью. Capture receipt не означает готовую смысловую обработку,
а старое наблюдение не подтверждает текущее состояние внешней системы.

## Автоматический захват

Только реально зарегистрированный Codex JSONL читается по доказанному физическому
ID и пути. Новый startup включает уже записанную первую реплику. Неизвестный resume
начинается с текущего хвоста; fork допускает лишь текущую сессию по явному I-proof.
Остальные разговоры не обнаруживаются и не импортируются автоматически.

Автозахват сохраняет доказанные сообщения пользователя и один финальный ответ
ассистента за завершённый ход. Текст ответа сверяется с событием завершения
того же хода. Промежуточные сообщения ассистента исключаются.
Вызовы и результаты инструментов намеренно пропускаются без записи и загрузки
артефактов. System/developer/reasoning, delegation и недоказанные нечеловеческие turn origins не становятся пользовательскими утверждениями.
Типизированные AGENTS/environment-вставки — намеренные исключения. Ручной API
для tool-отчётов и артефактов остаётся доступен. При явном использовании проекции
credential-поля закрываются точечно; остальные условия и текст сохраняются.

Запись больше `MAX_MEDIA_RECORD` не разбирается целиком: её тип остаётся неизвестным,
даже если начало похоже на tool-результат. Как и раньше, фиксируется разрыв источника
`oversized_record` и сбрасывается подтверждение текущего хода: следующий assistant
не получает непроверенную привязку. Захват продолжится с нового подтверждённого хода.

Текст с фотографией поддерживается по наблюдённому R/I-протоколу: слова остаются
дословными, generated attachment manifest помечен «not user words». Путь фотографии
только сравнивается с I, но не открывается. Байты берутся из R data URI и сохраняются
BLOB в локальной SQLite до продвижения cursor. Изображения ограничены 2 MiB каждое,
до восьми; PNG/JPEG/WebP/GIF проверяются технически по MIME/signature. Нет OCR,
vision-фактов или загрузки внешних URL. Перед связанным сообщением подтверждается
memory_store_artifact; memory_artifact отдаёт изображение только по явному запросу.

Полная синхронная SQLite-очередь сохраняет сообщения и cursor вместе. Потерянный ACK
повторяет те же IDs, исходные аргументы и delivery envelope; одинаковый текст сам
по себе не дедуплицируется. Provider IDs не содержат device/inode/путь; для сообщений
без provider ID есть устойчивый локальный occurrence UUID, но независимые копии
без общего ID на разных устройствах надёжно объединить нельзя.

SessionStart включает опрос своего зарегистрированного транскрипта, а SessionEnd
выключает его: уже начатое чтение завершается, новые циклы не начинаются.
Сохранённая позиция и подтверждения остаются на месте при повторном старте.
Отдельного дочитывания хвоста на SessionEnd нет. Общий worker продолжает доставку
уже накопленной очереди, но после её доставки прекращает heartbeat этой сессии.
Если Codex завершился аварийно и SessionEnd не пришёл, опрос сам не выключается.

До upload сообщается observed frontier, pending и source gaps. Активный поток
обновляет heartbeat; EOF не закрывает сессию автоматически. Reported current —
датированный operational frontier, а не world-current. Неотправленные изменения,
stale/unobserved producers и смысловая обработка имеют отдельные ограничения.
Стартовый hook выполняет локальную работу и запускает detached worker; модели и
сетевые вызовы в самом hook не выполняются.

## Проверки и обслуживание

Тесты используют временные профили и синтетические сообщения. Основные suites:
test_assertion_memory_single_module, test_assertion_memory_module, capture,
frontier, remote, artifacts, user_photos и bounded_replay.

lib/repair.py обслуживает только явно разрешённый зарегистрированный источник.
Для startup возможен reset с неизменённым header/proof и свободным worker lock.
Resume/fork восстанавливается лишь от caller-pinned snapshot SHA и положительного
checkpoint, без history-to-zero. Очередь, BLOB, IDs и все прежние ACK сохраняются;
нерешённый gap, существовавший до checkpoint, остаётся ограничением.
