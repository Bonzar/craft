# craft-type-lock

Замок «запись в сущность без её скилла и шаблона». Агент не запишет в Craft
в сущность — задачу, этап, раздел, заметку, проект, — пока в этом ходе не
вызвал скилл её типа и не прочитал её шаблон. Тип записи — место ∪
содержимое, и по каждому задетому типу нужны скилл и шаблон. Решение
сущностью не считается: запись в «Решения» раздела — запись в раздел, ей
нужен скилл раздела.

Тип записи считает один хозяин — замок. Что он насчитал, он кладёт строкой
в объём ревью хода, и ревью выбирает критерии только по ней: см. «Строка в
объём ревью».

## Что ловит

Вызов `craft_write` и `craft_write_and_show` сервера Craft MCP. Второй
инструмент исполняет те же команды, что и первый, поэтому закрыт тоже.
Инструмент узнаётся по хвосту имени (`mcp__‹сервер›__craft_write`): имя
сервера зависит от того, как Craft подключён, и замок от него не зависит.

Тип записи складывается из двух частей:

- **место** — тип ближайшего владельца места записи: страницы или блока,
  которому место принадлежит детьми или отступом. Задача на +1 под этапом
  принадлежит этапу, решение под «Решениями» раздела — разделу, тело задачи
  — задаче. Как замок находит владельца — в «Владелец места»;
- **содержимое** — типы сущностей, которые запись заводит или правит: теги
  типа в тексте команды вне текста ссылок и тег типа в тексте самой цели
  правки, переноса или удаления (`tasks update` по задаче правит задачу).

Скилл и шаблон нужны по каждому типу обеих частей: новая строка `#задача`
на +1 под этапом требует craft-task и craft-stage и по шаблону задачи и
этапа, закрытие этой задачи — тоже оба. Переименование задачи — только
craft-task: правка сущности с типом задевает только её саму.

## Шаблон сущности

Шаблон прочитан, когда в этом ходе был `craft_read`, одна из команд
которого — `blocks get ‹id шаблона› --depth -1`, в том числе внутри пачки.
Регистр id не важен. У тега шаблонов бывает несколько, хватает любого:
регулярная задача делит тег `#задача` с обычной. Страница, которая только
попала в ответ чтения (поиск, ссылка внутри прочитанного), прочитанной не
считается, как и чтение не на всю глубину (`blocks get` без `--depth -1`) и
id шаблона в другой команде (`search … --document ‹шаблон›`): шаблон читают
целиком, а не видят в выдаче.

Счёт шаблонов — по ходам, как у скиллов: реплика и сжатие его сбрасывают.
Шаблон из прошлого хода к записи уже не свеж, после сжатия его текста в
контексте нет. Нет шаблона — запрет; в причине тег и команды чтения каждого
его шаблона.

Чтение круга сверки — входящих ссылок, задетых разделов — не дело замка: он
проверяет только шаблон сущности, в которую пишет.

Тег ищется по всей строке команды: в `--markdown`, в JSON после `--json`, в
пачке через `;`. Тег с хвостом тоже тег: `#задача/готово`, `#этап/отменено`.
Слово, которое только начинается как тег (`#задачами`), тегом не считается.
Регистр не важен: `#Задача` — тот же тег. Кириллица, записанная в JSON как
`\uXXXX`, разворачивается перед поиском. Теми же правилами ищется тег в
тексте владельца.

Текст ссылки на блок (`[Сборка #этап](block://…)`, то же с `craftdocs://`)
из поиска вырезается — и в команде, и в заголовке. Текст ссылки — копия
имени цели с её тегами, поэтому такие ссылки есть почти в каждой записи: у
задачи проекта — ссылка на этап, у этапа — ссылки на разделы. Ссылка цель не
пишет, и скилл цели для неё не нужен.

## Модули сущностей

Какой тег какой скилл и какие шаблоны требует, замок узнаёт по модулям
сущностей. Модуль сущности объявляет себя замку полем `for =
["craft-type-lock", …]` в шапке и несёт `data/entity.json`:

```json
{"tags": ["#этап", "#веха"],
 "templates": {"#этап": ["8b8d4dc3-4663-57d5-a01e-a6461d748069"],
               "#веха": ["d4d93256-a59b-4230-1ef2-296a7504cf6a"]}}
```

`templates` — ровно теги из `tags`, у каждого непустой список id
страниц-шаблонов. Скилл тега — скилл этого
модуля, имя совпадает со slug по правилу установщика. Замок находит такие модули ядром
(`registry.adapters`), а не обходом всех папок, и своего справочника не
держит: отказ от сущности — удаление одного модуля. Модуль с
`data/entity.json`, но без `for` на замок, замку не сущность.

Справочник собирается заново на каждом событии, где он нужен: на каждой
записи в Craft (`pre-tool`) и на каждом вызове скилла (`post-tool`).
Модулей сущностей нет вовсе — справочник пуст, и требовать замку нечего:
проверка на запись в непрочитанное остаётся.

Справочник не собрался: у модуля с `for` на замок нет `entity.json`, файл
испорчен, у тега нет шаблонов или тег стоит у двух модулей. Что тогда:

- Запись в Craft — запрет. В причине путь к файлу, у повтора тега ещё и
  модуль, у которого тег уже есть. Без справочника тег не опознать ни в
  команде, ни в тексте владельца, а пропуск отдал бы запись без скилла.
- Вызов скилла — ошибка хука с путём к файлу. Скилл в счёт не идёт.

Установщик проверяет `entity.json` всех модулей набора, шаблоны каждого
тега и то, что у каждого модуля с `for` на замок файл есть, и на такой ошибке падает. После установки
справочник ломается только правкой файла на месте.

Нет вызова нужного скилла или чтения шаблона в текущем ходе — запрет. В
причине: какой тег найден в тексте, каких владельцев задевает запись, какую
сущность она правит и их теги, какой скилл вызвать, какой шаблон прочитать и что потом запись надо
повторить. Скиллы вызваны — замок
молчит, кроме первого отказа окружения за сессию, о нём текст в ход:
перечень в «Владелец места».

## Владелец места

Место записи — ближайший владелец с типом, и только он. Владение в Craft
двух видов:

- **дети** — блок лежит на странице: в странице-блоке или в корне
  документа. Детьми владеют только страницы, задача с телом — тоже страница
  (`type: page`, у задачи ещё `listStyle: task`);
- **отступ** — на странице блок с отступом больше, чем у ближайшего
  предыдущего соседа с меньшим отступом, принадлежит этому соседу. Задачи
  стоят на странице проекта соседями этапа на +1, а не его детьми, и всё же
  принадлежат этапу; этапы на +1 после вехи принадлежат вехе.

Владелец — ближайший уровень с типом: блок или страница, в собственном
тексте которых стоит тег типа с модулем сущности. Уровень без типа уровнем не
считается: переключатель «Решения», заголовок, текст, страница или
подстраница без тега. Подъём идёт через них к ближайшему владельцу с типом в
том же документе: подстраница «Архив» без тега в сфере принадлежит сфере,
подстраница «Меню» в «Банкет #заметка» — заметке. До корня документа типа
нет (заметка дня, документ без тега) — владельца нет, скилл места не нужен,
в следе «без владельца с типом».

Подъём от места, шаг за шагом:

1. На странице места — предыдущие соседи снизу вверх: первый с отступом
   меньше текущего. С типом — он владелец. Без типа — его отступ становится
   текущим, поиск идёт дальше вверх. Отступ 0 — соседи кончились.
2. Сама страница. С типом — она владелец.
3. Без типа — подъём на страницу выше: место теперь — эта страница среди
   своих соседей, с её отступом, и снова с шага 1.

Тег берётся из того, что агент прочитал за последние десять минут, или из
свежего ответа API, а не из памяти хода: переименование или смена тега видны
сразу после чтения (см. «Дерево из прочитанного»). Тег в тексте ссылки (`[Этап #этап](block://…)`) тип блоку
не даёт. Проект и сфера — сущности со своими модулями: запись на их страницу,
в том числе в «Решения проекта» и «Решения сферы», требует их скилла и
шаблона.

### Какие владельцы задеты

Какое место у записи — по роли цели, её даёт `command-tree-craft`, и по
глаголу команды:

- **новая строка рядом** (`--siblingId`) — владелец места, куда она встанет,
  с её отступом из нагрузки: `indentationLevel` каждого верхнего блока
  `--json`. Поля нет или нагрузка `--markdown` — отступ 0 (правило
  craft-tool.md: `--markdown` нормализует отступ к 0, update без поля
  сбрасывает его в 0; для add это вывод, не замер). `--position after` —
  сосед стоит перед местом, `before` — перед местом только те, кто перед
  соседом;
- **новая строка в дети** (`--id` у `blocks add`) — родитель, если у него
  тип, иначе его владелец. С отступом больше 0 и `--position end` (или без
  позиции) владельцем может стать и ребёнок родителя по отступу;
- **правка блока без типа** (`blocks update`, текст решения) — его владелец;
- **правка блока с типом** (`blocks update`, `tasks update` по датам,
  переименование) — только он сам, в содержимое, владелец не задет;
- **смена состояния блока с типом** — он сам и его владелец. Смена
  состояния: флаг `--state` у `tasks update`, `taskInfo.state` в нагрузке,
  или новый текст из нагрузки `blocks update`, у которого другой чекбокс
  (`- [x]` против `- [ ]`) или другие закрывающие хвосты тегов
  (`/готово`, `/отменено`), чем у текста цели. Владелец того же модуля,
  что закрытая сущность, отдельно не требуется: скилл закрытой сущности
  уже несёт его правила (этап закрывается внутри вехи скиллом этапов).
  Правило общее, по модулю, имён типов в коде нет;
- **перенос** (`blocks move`) — сам блок в содержимое, владелец там, откуда
  он уходит, и владелец там, куда он встаёт: с отступом переносимого блока
  (перенос отступа не меняет);
- **удаление** (`blocks delete`) — сам блок и его владелец: блок уходит от
  владельца, как при переносе.

Примеры на странице проекта: «Этапы проекта» — переключатель без тега на 0,
этапы на +1, их задачи на +2, веха на +1 и её этапы на +2.

| Запись | Место | Содержимое |
| --- | --- | --- |
| новая задача на +2 после этапа или его задачи | этап | задача |
| новый этап на +1 после задачи | проект | этап |
| решение в «Решениях» раздела | раздел | — |
| правка решения раздела | раздел | — |
| тело задачи (`blocks add --id ЗАДАЧА`) | задача | — |
| переименование задачи, её срок | — | задача |
| закрытие или отмена задачи этапа | этап | задача |
| закрытие задачи этапа вехи | этап вехи | задача |
| закрытие этапа проекта | проект | этап |
| закрытие этапа внутри вехи | — (веха того же модуля) | этап |
| закрытие проекта-страницы в сфере | сфера | проект |
| перенос задачи между этапами | оба этапа | задача |
| перенос задачи в «Решения» раздела | этап и раздел | задача |
| удаление задачи этапа | этап | задача |
| строка в подстранице «Архив» сферы | сфера | — |
| строка в подстранице «Меню» заметки | заметка | — |
| строка в заметке дня | — | — |
| правка заголовка корня документа с типом | — | тип корня |

### Дерево из прочитанного

Агент по правилам читает страницу до записи в неё, и в этом чтении уже есть
всё, что нужно замку: блоки страницы по порядку, их отступы и тексты. Поэтому
замок сперва ищет место записи в том, что агент прочитал в сессии, и только
чего там нет — спрашивает connect-API. В обычном случае запись не стоит ни
одного запроса (решение владельца 02.11.2026, вариант Б).

Ответ `craft_read` приходит в `post-tool` списком кусков `{"type": "text",
"text": …}` (замер 02.11.2026 по записям ревью хода у `craft_write` того же
сервера; строка и словарь с `content` тоже разбираются). Из него замок берёт:

- **JSON-чтение** (`--format json`) — целиком: `{"data": [корень],
  "nextCursor": …}`, у каждого блока `id`, `type`, `markdown`,
  `indentationLevel`, у страницы в пределах глубины — `content` с детьми.
  Страница за пределами глубины несёт только `contentPreviewMd`: её блок и
  отступ известны, дети — нет. Прямых детей корня ответ отдаёт до 50, дальше
  курсор `--cursor 50:…` (замер 02.11.2026: проект на 60 детей); ответ по
  курсору дописывает детей, если стыкуется с уже известными. Список ровно на
  50 детей полным не считается: где лежит `nextCursor`, сказано справкой
  `blocks get --help`, а не замерено.
- **markdown-чтение** (по умолчанию) — только вложенность страниц: id есть
  только у тегов `<page id>`, а отступ страниц в тексте не виден вовсе (этап
  на +1 и задача на +2 стоят одинаково, замер 02.11.2026). Страница из такого
  чтения встаёт в дерево с неизвестными детьми.

Дерево — файл `craft-type-lock-tree.json` в зоне сессии: страница → её блок,
дети по порядку и полон ли их список; блок → страница, где он лежит; страницы,
которые поиск API назвал корнем документа. Свежее чтение страницы заменяет её
поддерево. Что замок узнал из API по ходу проверки — детей страницы, путь
поиска, корень документа, — тоже ложится в дерево: следующей записи это уже
не стоит запросов.

На записи, по каждой цели:

1. Цель и страницы над ней есть в дереве, а дети страниц места известны —
   ни одного запроса.
2. Цели в дереве нет, но есть страница с неизвестными детьми: страница над
   целью из markdown-чтения, иначе прочитанная страница с неизвестными
   детьми, свежие первыми, — ровно один запрос `GET
   /blocks?id=‹страница›&maxDepth=1`, и дети ложатся в дерево.
3. Цели нет и там — прежний путь через API (ниже). Цель не нашлась ни на
   одной прочитанной странице — запись в непрочитанное, как и раньше.

Полный список детей из дерева, в котором нет блока-соседа записи, устарел:
блок лёг после чтения. По такому списку место не судится, дети страницы
запрашиваются у API. Нет соседа и в ответе API — дети запрашиваются ещё раз,
а без соседа и тогда запись судится как запись в непрочитанное: страница уже
не та, что агент читал, и её надо прочитать заново.

Путь страниц из дерева годится, когда доходит до корня документа или проходит
через прочитанную страницу. Иначе страница, прочитанная выше известного
куска, осталась бы не видна, и запись ушла бы в непрочитанное зря — такой путь
ищется поиском.

Дерево устаревает тремя путями, и на каждый своё правило:

- **своя запись** — `post-tool` записи в Craft сбрасывает детей страницы над
  каждой целью и самой цели: следующая запись туда стоит один запрос.
  Команда без id цели (`blocks add --date`, `tasks add`) легла на страницу,
  которую по команде не узнать, поэтому она сбрасывает всё дерево.
  Запрещённая или упавшая запись `post-tool` не даёт: на Craft она не влияла;
- **чужая правка** — человек правит базу в приложении параллельно. Запись в
  дереве живёт десять минут (`TTL_SEC`): агент перед записью по правилам
  читает страницу заново, и старое дерево к записи уже не нужно;
- **сжатие** — дерево стирается: агент читает страницу заново, и замок не
  опирается на чтение, которого в контексте больше нет.

Дерево держит не больше 30 страниц (`MAX_PAGES`) и 3000 связей блок →
страница: файл читается на каждой записи в Craft. Порча файла — запрет записи
с путём к файлу и выходом: удалить его, дерево соберётся заново. Проверяется
каждая запись файла — страница с детьми, связь блок → страница и корень, —
иначе испорченная запись уронила бы хук, а упавший хук запись пропускает. Правки
дерева идут операциями и под локом состояния накатываются на свежую копию
файла, поэтому параллельные хуки не затирают друг друга.

Чтобы обычная запись не стоила запросов, страница места должна быть прочитана
JSON: markdown-чтение отдаёт только вложенность страниц, и запись по нему
стоит один запрос. Правила чтения сейчас велят markdown (craft-tool.md:
«Чтение базы — через markdown»), скиллы сущностей — `--depth 2` для проекта
и `--depth -1` для сущности, без `--format json`.

### Как замок находит владельца

Родителя у блока connect-API Craft (`CRAFT_API_BASE`) не отдаёт: ни в `GET
/blocks`, ни с `fetchMetadata` поля родителя нет (замер 02.11.2026). Путь
страниц до блока отдаёт поиск внутри документа: `GET /blocks/search` с
`blockId` любого блока документа возвращает у каждой находки
`pageBlockPath` — страницы от корня документа до той, где находка лежит, сама
находка в путь не входит. Ищет он по тексту без разметки (у задачи «- [x]
Удалить скилл-док» находка «Удалить скилл-док»), числа находок не режет
(2554 находки на одну букву) и видит правку тринадцатиминутной давности
(всё — замер 02.11.2026). Соседей находки поиск тоже отдаёт
(`beforeBlocks`), но без отступа, поэтому владельца по ним не найти.

Отступ и порядок соседей отдаёт сама страница: `GET /blocks?id=‹страница›&maxDepth=1`
— страница и её прямые дети по порядку, у каждого `indentationLevel` (поля
нет — уровень 0), текст и у задач `taskInfo.state`. `GET` блока с
`maxDepth=0` тоже несёт его `indentationLevel` (замер 02.11.2026).

На каждую цель записи, id из `--id`, `--ids`, `--siblingId`, `--targetId`,
`--targetSiblingId` в любом месте команды:

1. `GET /blocks?id=‹цель›&maxDepth=0` — сама цель: тип, текст, отступ. 404
   повторяется в другом регистре id.
2. Цель сама прочитана — путь не запрашивается, пока не понадобится. Иначе
   `GET /blocks/search?blockId=‹цель›&pattern=‹первые шесть слов её
   текста›&beforeBlockCount=0&afterBlockCount=0`, из находок берётся та, чей
   id — цель. Слова — из текста без адресов ссылок, структурных тегов,
   маркера списка, чекбокса и решёток заголовка, склеены `\W+`.
3. Подъём к владельцу: на странице с отступом места больше 0 — её дети
   (`maxDepth=1`), страница без детей в памяти — сам блок (`maxDepth=0`).
   Правка блока с типом без смены состояния подъёма не делает.

Запасной путь — для цели без слов (разделитель, картинка) и для цели,
которой поиск не нашёл (только что записанное поиск может ещё не видеть):
прочитанные страницы запрашиваются целиком (`maxDepth=-1`), свежие первыми,
и путь до цели ищется в их деревьях. Дети страниц этого дерева ложатся в
память проверки, второй раз их не запрашивают. Подъём выше корня дерева
прочитанной страницы снова ищет путь её корня поиском.

Цена проверки места по тому, что прочитано до записи, замер 02.11.2026 на
настоящем пространстве: новое решение в «Решениях» шаблона этапа, отступ 1.

| Что прочитано до записи | Запросов | Время проверки места |
| --- | --- | --- |
| страница места JSON-чтением | 0 | 0,00 с |
| страница места markdown-чтением | 1 (дети страницы) | 0,4–0,7 с |
| дерева нет: только API | 3 (цель, поиск, дети) | 1,25–2,7 с |

Три прогона одной и той же записи; ответ чтения собран в обёртке MCP из тела
страницы, которое отдал тот же API.

Дальше — цена пути через API, замер 02.11.2026 из контейнера на настоящем
пространстве, живыми вызовами проверки места по проекту «Модульная система агента» (60 детей на
странице): страница с детьми — 46 КБ и 0,8–2 с, у раздела и сферы 14–17 КБ
и 0,75–1,1 с; блок без детей — 0,4–1,4 КБ и 0,5–3 с. Закрытие задачи этапа
— 3,8 с, новая строка под этапом — 3,6–5,4 с, правка решения проекта — 4,2
с, закрытие этапа — 2,1 с, переименование задачи — 3,3 с, перенос задачи
между этапами — 5,8 с. Запросов: правка сущности без смены состояния — два
(цель, поиск), правка или новая строка с подъёмом — три (цель, поиск, дети
страницы), перенос — пять, запись в прочитанного родителя с типом на
отступе 0 — один. Отдельный запрос API иногда стоит 9–10 с, а пару раз не
уложился в 10 с: тогда место не определено. Запросы connect-API считает
квотой на ссылку: 100 запросов в минуту (`x-ratelimit-limit: 100`, сброс —
`x-ratelimit-reset`, сверх квоты 429 Too Many Requests с `Retry-After`,
замер 02.11.2026). Квота общая для всех сессий и утилит синхронизации, ходящих этой
ссылкой: в замере её выбирал параллельный потребитель, и проверка места
получала 429 уже на первом запросе. Это тоже «место не определено». Потолок на
всю проверку — 12 с. Без User-Agent connect-API отвечает 403 (замер
01.11.2026), поэтому запрос идёт с заголовком.

### Запись в непрочитанное

Цель должна лежать на странице, которую агент читал в сессии: сама цель или
одна из страниц на пути к ней среди прочитанных. Прочитанные — id страниц из
ответа `craft_read` (теги `<page id="…">` в markdown, корневой id в JSON; так
запоминается и заметка дня, прочитанная по дате) и id из его команды, до
двадцати последних. Не лежит — запись в непрочитанное, и замок её
запрещает: по механике Craft страница цели читается до записи. В причине —
команда чтения, после которой запись надо повторить. Чтений в сессии нет
вовсе — тот же запрет без запросов к API.

Глубина не ограничена: цель на подстранице прочитанной страницы на любой
глубине — на прочитанной странице.

### Когда место не определить

Когда замок судить о месте не может и ход в этом не виноват, тип владельца
не судится, а проверка по тегам текста идёт как обычно. Два случая. У
флага цели значение не id (`--id ЗАДАЧА`) — молчание, причина в следе
содержит «место записи не проверено»: такую команду Craft и сам не
исполнит. Место цели не определено: нет `CRAFT_API_BASE`, API не ответил,
цель не нашлась в API ни в одном регистре, API ответил 429, проверка не
уложилась в 12 с или страница над целью не видна — в первый раз за сессию
текст в ход с той же причиной, на пропуске и на запрете по тегу; дальше молчание с причиной в
следе. stderr хука до модели не доходит (замер 01.11.2026), поэтому текст, а
не stderr. Владельцы целей, найденных до отказа, судятся. Цель в
непрочитанном запрещается, даже когда место другой цели не определено.

Пропуск при неопределённом месте — решение, которое ещё открыто: оно стоит
одной константой `UNAVAILABLE_PASSES` в `hooks/module.py`, и `False`
превращает его в запрет.

Разобранные цели при неразобранных судятся: `blocks move --id ‹решение
раздела› --targetSiblingId ЗАДАЧА` запрещён без craft-section.

### Когда цели нет вовсе

У команды, у которой цель есть всегда (`blocks add/update/move/delete`,
`tasks update/delete`, `documents move/delete`), нет ни флага цели, ни id в
JSON правки — запрет с причиной «Цель записи не найдена» и списком флагов
цели. Craft мог бы найти цель путём, которого замок не видит, и такая
запись прошла бы мимо проверки места. Цели — флаги `--id`, `--ids`,
`--siblingId`, `--targetId`, `--targetSiblingId`, `--task` (сама задача у
`tasks update/delete`), `--document` (сам документ у `documents
move/delete`), а у `blocks update` без них — поля `id` верхних блоков
`--json`. `blocks add --date ‹дата›` пишет в заметку дня: цель есть, но не
id, место не судится. Команда со `--help` ничего не пишет и целей не имеет.

### Когда замок не может судить

Испорченный файл состояния или отступ блока из API не числом на записи в
Craft — запрет с причиной и выходом: какой файл удалить. Ошибку хука
харнес считает неблокирующей, и упавший замок пропустил бы запись.

Регистр id API различает: документ с id в верхнем регистре на id в нижнем
отвечает 404, и наоборот (замер 01.11.2026). Поэтому id хранятся и
запрашиваются как есть, сравниваются без учёта регистра, id из ответа
чтения идёт впереди id из команды, а 404 повторяется в другом регистре.

### Когда отступ записи не разобрать

Отступ новой строки не разобран: нагрузка `--json` не читается как JSON или
отступ в ней не число, у `blocks add` нет ни `--json`, ни `--markdown`, у
переноса не получен сам переносимый блок. Тогда владелец не определён, и
замок закрывает запись наглухо: требует всех кандидатов — владельцев места
на любом отступе от 0 до 7. Новая строка после задачи этапа без разобранного
отступа требует проект, этап и задачу. Строка `entity` такой записи —
`determined: false`, в следе «отступ записи не разобран: все кандидаты».

### Границы схемы

- Тип содержимого у цели правки — по тегу в её тексте, а не по тому,
  страница ли она: задача без тела тоже задача. Блок с тегом типа вне
  ссылки в тексте (редкость: теги стоят в заголовках) тоже даст тип и
  станет владельцем того, что стоит под ним с отступом.
- Владелец по отступу считается по отступу до записи. Перенос отступа не
  меняет, поэтому место переноса судится по отступу переносимого блока;
  следующий `blocks update` с новым `indentationLevel` судится как правка
  этого блока на его новом месте.
- Отступ из `--json` без поля `indentationLevel` считается нулём — по
  правилу craft-tool.md, для `blocks add` это вывод, а не замер.
- Пачка команд через `;` судится по командам: у каждой свои цели, глагол,
  отступы и смена состояния. Требуются типы всех команд, исход пачки —
  самый строгий исход её команд: запрет любой команды запрещает пачку,
  место не определено хоть у одной — строка `entity` пачки
  `determined: false`.
- Флаги цели, позиции и состояния берутся из слов команды, а не из её
  текста: `--state done` внутри `--markdown` или `--json` — текст нагрузки.
- `blocks add` без отступов в нагрузке (`--json '[]'`) судится как
  неразобранный отступ: все кандидаты.
- Смена состояния узнаётся по нагрузке и тексту цели: флаг `--state`,
  `taskInfo.state`, чекбокс или закрывающий хвост тега в новом тексте.
  Правка текста без чекбокса у задачи с чекбоксом тоже считается сменой
  состояния: задача превращается в текст.
- Цель без слов или ещё не видная поиску находится только в деревьях
  прочитанных страниц. Если цель — сам корень такого дерева, а нужна
  страница над ней (сосед прочитанной подстраницы), место не определено.
- Место определяет дерево прочитанного или поиск API: устарей первое за
  десять минут или ошибись второй путём, ошибётся и замок. Текст
  страниц на подъёме замок берёт из чтения или запроса, а не из пути поиска: там заголовок
  без разметки и из индекса поиска, тег в тексте ссылки от настоящего не
  отличить, а только что сменённый тег может быть ещё старым.
- Страница с отступом места больше 0 запрашивается с детьми: у большого
  проекта это десятки килобайт и до двух секунд. Подъём через несколько
  подстраниц без тега — по запросу на каждую.
- API недоступен или режет запросы — тип места не судится, о чём замок раз
  за сессию говорит в ход. Ревью хода тогда берёт для записи критерии всех
  сущностей: см. «Строка в объём ревью».

Суждение о месте живёт в `hooks/place.py`, подъём к владельцу — в
`hooks/owner.py`, дерево из прочитанного — в `hooks/tree.py`, разбор ответа
чтения — в `hooks/reads.py`, разбор нагрузки (отступ, смена состояния) — в
`hooks/payload.py`, запросы к API — в `hooks/api.py`, строка в объём ревью —
в `hooks/review_row.py`, справочник модулей сущностей — в
`hooks/entities.py`, файл состояния — в `hooks/state.py`; точка входа
`hooks/module.py` их импортирует. Цели из команды — флаги, роль цели —
разбирает библиотека `command-tree-craft` (`write_targets`), place получает
их готовыми.

## Строка в объём ревью

Замок — поставщик записей ревью хода (`for = ["turn-review"]`, контракт — в
[README ревью](../turn-review/README.md), раздел «Контракт поставщиков»). За
каждую запись в Craft, которая случилась, он дописывает в объём ревью строку
`entity`. Считает её `pre-tool`, а кладёт в объём `post-tool` той же записи:
запрещённая или упавшая запись `post-tool` не даёт, и строки без записи
`write` в объёме не остаётся — ревью остановило бы такой ход зря. До
`post-tool` строка ждёт в `craft-type-lock-rows.json` по ключу `tool_use_id`
вызова, а без него — по реплике и команде; файл держит последние 20 строк,
запрещённые там ждут напрасно.

```json
{"kind": "entity", "prompt_id": "‹id реплики›", "command": "tasks update --id ‹задача› --state done",
 "targets": ["‹id задачи›"], "place_types": ["#этап"], "content_types": ["#задача"],
 "determined": true, "note": "цель bbbbbbbb у владельца bbbbbbbb (#этап), правит сущность (#задача), меняет её состояние"}
```

- `command` — команда записи как есть: по ней и `prompt_id` ревью находит
  запись `write`, к которой строка относится, без своего разбора команды.
- `targets` — id целей из флагов команды (`write_targets` разбора).
- `place_types` — типы владельцев: места новой строки, правленого блока без
  типа, источника и места переноса, сменившей состояние сущности (кроме
  владельца того же модуля); `content_types` — типы содержимого. Ровно те,
  по которым замок требовал скилл и шаблон; пустой список — такой сущности
  нет, явно.
- `determined` — место всех целей известно: `true` при найденном месте и у
  команды без цели, `false` при записи в непрочитанное, неразобранной цели,
  неопределённом месте и неразобранном отступе записи (тогда в
  `place_types` все кандидаты).
- `note` — причина из следа: что замок увидел или почему не смог.

Пропуск или запрет в строку не идёт: ревью берёт из неё только выбор
критериев, а не довод, что запись верна. Строка лежит только у записи,
которую замок пропустил и инструмент исполнил. Почему так — в README ревью.
Второго похода в Craft на остановке нет: тип уже лежит в объёме. Вызов
подагента строки не оставляет: его записей в объёме нет. Строку пишет
`Storage.append_line` ядра, lib ревью замок не импортирует.

## Что пока не проверяет

Замок проверяет владельца места и шаблон: запись в непрочитанное запрещена,
тип владельца требует скилла и шаблона. Что агент прочитал весь круг
сверки до записи — задетые разделы, входящие ссылки, — замок не проверяет и
не будет: это дело скиллов и ревью хода.

## Что не ловит

- Запись без тега типа в тексте там, где выше до корня документа типа нет:
  правку заметки дня, документа без тега. Замок молчит и пишет в след «тега
  типа нет». Та же запись в цель, которой нет среди прочитанных страниц,
  запрещается как запись в непрочитанное.
- Запись без id цели вовсе: `tasks add --help`, команды коллекций. Замок
  молчит, в следе «тега типа нет».
- Справку без тега: `tasks add --help`. Справку с тегом в команде замок
  проверяет как запись: `--help` в полезной нагрузке иначе открывал бы замок.
- Чтение: `craft_read` замок не блокирует, только запоминает id прочитанных
  страниц в `craft-type-lock.json`, поле `reads`, и само прочитанное — в
  дереве `craft-type-lock-tree.json`.
- В Codex замок получает `pre-tool`, `post-tool`, `prompt` и `after-compact`.
  Имена `craft_craft_read` и `craft_craft_write` из Apps узнаются так же, как
  обычные имена Craft MCP.

## Как устроен ход

Ход — от реплики до реплики. Счёт хранит сам замок:

- реплика (`prompt`) — номер хода растёт на 1;
- вызов инструмента `Skill` (`post-tool`) со скиллом модуля сущности —
  скиллу пишется номер текущего хода. Имя скилла с префиксом плагина
  (`плагин:craft-task`) берётся по части после последнего двоеточия;
- запись в Craft (`pre-tool`) — каждый скилл задетых типов, владельцев и
  содержимого, должен нести номер текущего хода, и у каждого такого тега
  в этом ходе прочитан шаблон; строка `entity` ложится в объём ревью;
- после сжатия (`after-compact`) счёт сбрасывается: правила скилла и
  шаблон из контекста ушли, скилл надо вызвать и шаблон прочитать заново. Список прочитанных страниц остаётся: это
  не знание агента, а подсказка, где искать цель записи. Дерево из
  прочитанного стирается: текст владельца после сжатия берётся из нового
  чтения или из API;
- чтение Craft (`post-tool` на `craft_read`) — в начало списка прочитанных
  страниц встают id из ответа (теги страниц в markdown, корневой id в JSON),
  за ними id из команды. Id, прочитанные целиком (`blocks get ‹id› --depth
  -1`), вдобавок идут в чтения хода (`turn_reads`), по ним замок узнаёт
  прочитанный шаблон. Сам ответ ложится в дерево из прочитанного;
- запись в Craft исполнена (`post-tool` на `craft_write`) — строка `entity`
  из `pre-tool` ложится в объём ревью, дети страниц над целями в дереве
  сбрасываются, а у команды без id цели — всё дерево.

Скилл, который Влад вызвал сам командой `/craft-task`, через инструмент
`Skill` не идёт, и `post-tool` на нём не приходит. Замок его не видит и
запись в этом ходе запретит. Тогда агент вызывает скилл ещё раз
инструментом.

Хуки параллельных вызовов идут параллельно. Поэтому чтение и запись счёта
идут под локом на файл `craft-type-lock.lock` рядом с состоянием: иначе два
скилла в одном сообщении перезаписали бы друг друга.

В автономном прогоне поведение то же.

Зачем замок, а не правила в ответе хука: правила, которые хук кладёт в ход,
занимают контекст на каждой записи, даже на верной. Замок на верной записи
молчит и ходит по своему журналу, в сеть только за страницей цели.

## Где файл состояния

Зона сессии хранилища, файл `craft-type-lock.json`:
`{"turn": 3, "skills": {"craft-task": 3}, "reads": ["‹id страницы›"], "turn_reads": ["‹id›"], "place_warned": false}`. Каталог хранилища — из журнала
установки, у модуля без установщика `~/.local/state/jarvis/‹сессия›/`.
Рядом лежат дерево из прочитанного `craft-type-lock-tree.json` и строки,
ждущие своей записи, `craft-type-lock-rows.json`.
Испорченный файл, в том числе `reads` или `turn_reads` не из id блоков, — ошибка с путём к
файлу, а не тихий сброс. Каждое
следующее событие будет падать так же, пока файл на месте, а запись в Craft
— запрещаться, и причина называет путь именно испорченного файла: состояния,
дерева или отложенных строк. Лечится удалением этого файла в зоне сессии.
Удалён `craft-type-lock.json` — счёт начнётся заново, и до нового вызова
скилла запись в сущность будет под запретом.

## Как выключить

Режимом модуля из ядра: `{"craft-type-lock": false}` в одном из трёх
источников — `modes.json` в зоне сессии, личный `~/.config/jarvis/modules.json`
или `modules.json` рядом с папками модулей. Действует со следующего события.

## Разбор команды

Команду Craft замок сам не разбирает: имя инструмента, теги в команде (тег в
тексте ссылки не считается, `\uXXXX` раскрыт), id блоков, страницы из ответа
чтения и цели записи отдаёт `lib` модуля `command-tree-craft`, по slug из
`requires`. Своей части `lib` у замка нет. Тем же поиском тегов замок
читает тексты владельцев из ответа API. Справочник «тег → скилл» по
`data/entity.json` модулей сущностей собирает сам замок: это его контракт с
модулями сущностей, а набор тегов он передаёт разбору.

## Зависимости

`requires` — только `command-tree-craft`: без разбора команду не прочесть.
Пока его нет, библиотека молчит за замок и говорит в чат, чего не хватает.
Модули сущностей в `requires` не стоят: они приходят сами через `for`, а без
них требовать нечего. Ревью хода замок тоже не требует: `for =
["turn-review"]` объявляет его поставщиком, а без ревью строки `entity`
просто никто не читает.

Тесты: `python3 -m unittest tests.test_craft_type_lock
tests.test_craft_type_lock_entities tests.test_craft_type_lock_place
tests.test_craft_type_lock_review tests.test_craft_type_lock_tree`, общая
обвязка — `tests/craft_type_lock_harness.py`.


Полное чтение установленного скилла через отдельный `cat /…/SKILL.md`
на событии `post-tool` тоже засчитывается. Путь сверяется с частью `skill`
журнала установки, а вывод обязан содержать весь актуальный файл. `head`,
обрезанный вывод и одноимённая копия в другом месте не открывают замок.
Подтверждённое чтение пишет строку `skill` в объём ревью, чтобы требования
скилла попали в поручение ревью. Счёт сбрасывается новой репликой и compact.
