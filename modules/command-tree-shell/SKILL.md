# command-tree-shell — дерево команды оболочки

Адаптер возможности `command_tree` под оболочку. Харнес про него не знает и не
запускает: его зовёт модуль, объявивший `command_tree` в `requires` (решение 25).
Контракт один: `call(event, args) -> словарь`; не смог — `{"unsupported": "…"}`.

Владельца возможности отдельным пакетом нет намеренно: реализация одна, разбор
команды нужен только оболочке. Контракт формы дерева поэтому лежит здесь.

## Что принимает

Текст команды из `args["command"]`, а без него — из входа вызова
(`event["input"]["command"]`). Имя этого поля знает адаптер оболочки, и больше
никто.

## Что отдаёт

    {"source": "…", "statements": [ … ]}

`source` — исходный текст команды: дерево есть его вид, и потребителю, которому
нужен сам текст (искомое внутри кавычек словом не становится), не приходится
знать, из какого поля вызова его достают.

Утверждения идут ПЛОСКИМ списком слева направо, в порядке исполнения. Поля:

    depth        вложенность: 0 — верхний уровень; ниже — подоболочка, тело
                 цикла, ветка условия, содержимое подстановки
    line         номер строки исходной команды
    line_first   первое ли это утверждение своей строки НА СВОЕЙ ГЛУБИНЕ
    sep          оператор ПЕРЕД утверждением: "" | "\n" | ";" | "&" | "&&" |
                 "||" | "|" | "|&"
    kind         "call" — вызов команды; "other" — всё прочее (`[[ … ]]`,
                 арифметика, объявление): слов у такого утверждения нет
    background   кончилось ли утверждение знаком `&`
    words        [{text, quoted, expanded, process}] — слова команды
    redirects    [{op, target, heredoc}] — перенаправления

Слово: `text` — собранное значение, `quoted` — было ли оно в кавычках,
`expanded` — есть ли в нём подстановка, `process` — процессная ли это подстановка
(`<(…)`). Последнее отделено нарочно: такое слово даёт путь к каналу, а не к
файлу, и тот, кто называет прочитанные файлы, обязан его отличить. Присваивание
окружения приходит словом вида `X=1` впереди остальных.

Перенаправление: `op` — числовой код оболочки (`54` = `>`, `55` = `>>`,
`56` = `<`, `60` = `>|`, `61` = `<<`, `62` = `<<-`, `63` = `<<<`, `64` = `&>`,
`65` = `&>>`; `58` = `<&` и `59` = `>&` — дескрипторы, не файлы), `target` —
слово цели, `heredoc` — тело у форм heredoc, иначе `null`.

## Три обещания, на которых стоят потребители

**Закавыченная строка — одно слово.** Тело `bash -c "…"` приходит словом с
`quoted: true`; спускаться ли внутрь, решает потребитель, и адаптер зовётся на
теле повторно.

**Подстановка помечена, а не выдумана.** `${x}` и `$(…)` текста не добавляют:
их значение известно только оболочке, и подставить догадку значит назвать путь,
которого нет. Содержимое `$(…)` при этом не теряется — оно ложится в список
утверждениями глубиной ниже.

**Тело heredoc — не команда.** Оно едет полем `heredoc` и утверждениями не
становится: текст «rm -rf …» внутри печатаемого документа командой не является.

## Чего адаптер НЕ делает

Разбор идёт внешним `shfmt --to-json` (mvdan/sh). Его нет в PATH или он не
разобрал строку (незакрытая кавычка) — ответ `{"unsupported": "shfmt: …"}` с
текстом ошибки. Резки регулярками взамен НЕТ (решение 14): догадка на месте
разбора и есть тот фолбэк, ради устранения которого адаптер заведён.

Путь к разбору переопределяется переменной `SHFMT` — ею же кейсы показывают
адаптеру пустое окружение, не трогая настоящий PATH.

## Установка разбора

    brew install shfmt                      # мак
    bash tools/install-shfmt.sh             # линукс: бинарник с проверкой суммы
