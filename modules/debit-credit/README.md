# debit-credit

Отдельный модуль с читающими адаптерами Яндекс Банка и Debit & Credit
и редактором отдельной резервной копии.
Python 3.11+, стандартная библиотека. Хуков и запуска Shortcuts нет.
Операции меняются после восстановления подготовленной копии пользователем.
На Mac модуль может добавить отдельную копию в список восстановления закрытого
приложения. HTTP-сборщик разрешает только два читающих запроса истории банка.
Установщик переносит `lib` по обычному контракту модуля.
В репозитории не было кода финансовых адаптеров, поэтому существующие библиотеки
агента не расширяются банковскими правилами.

## Запуск

Из каталога модуля:

```sh
python3 lib/cli.py debit-credit '/путь/Все счета.csv' --timezone Europe/Moscow --output /tmp/dc-export.json
python3 lib/cli.py debit-credit-backup /путь/копия.dcbackup --timezone Europe/Moscow --from-date 2026-07-04 --to-date 2026-07-05 --output /tmp/dc-snapshot.json
python3 lib/cli.py yandex-bank /tmp/opened-cards.json --output /tmp/bank-operations.json
python3 lib/cli.py yandex-bank-api /tmp/yandex-bank-history-resumed.json --output /tmp/bank-api-normalized.json
python3 lib/cli.py compare /tmp/bank-operations.json /tmp/dc-snapshot.json --accounts /tmp/accounts.json --window-seconds 120 --output /tmp/comparison.json
python3 lib/cli.py review /tmp/comparison.json --output /tmp/review.json
python3 lib/cli.py classification-evidence /tmp/review.json --output /tmp/classification.json
python3 lib/cli.py movement-control /tmp/expected-source.json --ledger /tmp/dc-snapshot.json --accounts /tmp/accounts.json --from-date 2026-01-01 --to-date 2026-10-18 --timezone Europe/Moscow --output /tmp/movement.json
python3 lib/cli.py resolve-source /tmp/bank-api-normalized.json --resolutions /tmp/confirmations.json --output /tmp/resolved-source.json
python3 lib/cli.py yandex-accounting /tmp/resolved-source.json --parent-window-seconds 120 --output /tmp/expected-source.json
python3 lib/cli.py transfer-accounting /tmp/expected-source.json --accounts /tmp/accounts.json --output /tmp/expected-transfers.json
python3 lib/cli.py verify-import /путь/before.dcbackup /путь/after.dcbackup --expected /tmp/expected-records.json --timezone Europe/Moscow --output /tmp/import-check.json
PYTHONPATH=lib python3 -m unittest discover -s tests -v
node --test tests/test_capture.js tests/test_queries.js
python3 lib/build_userscript.py /tmp/yandex-bank-history-reader.user.js
```

Команды читают вход, возвращают краткую сводку и при `--output` создают новый
JSON-файл с правами 0600. Существующий файл не перезаписывается. Данные не сохраняются в модуле
и не попадают в Git. Код возврата 0 означает отсутствие ошибок разбора, 1 —
отклонённые карточки/строки или неразрешённые поля, 2 — ошибка входного файла.
`ready` относится только к разбору, не к готовности переноса или сверке счёта.

## Общий результат

`schema_version: 1`, `adapter`, `input_count`, `records`, `rejected`, `issues`,
`coverage`, `ready`, `limitations`, а у CLI ещё `input_sha256`.

Каждая входная строка/карточка попадает либо в `records`, либо в `rejected` с
причиной и исходными данными. Счёт входа проверяется кодом. Совпадающие записи
сохраняются с исходной кратностью. `locator` — позиция в данном входном файле,
не постоянный ID и не часть метки.

Запись содержит `source`, `source_id`, `timestamp` с часовым поясом,
`timestamp_precision`, точную знаковую `amount` строкой без float, `currency`,
`account`, `other_account`, `kind`, `status`, `cleared`, `description`, `notes`,
`category`, `tag`, `markers` и `raw`. Неизвестные значения остаются `null`.

У CSV `kind` описывает запись приложения. У карточки банка смысл расхода или
дохода требует разбора, поэтому `kind` без подтверждённых двух счетов остаётся
`null`. Знак суммы при этом сохранён. Внутренние переводы представлены сторонами
`transfer_leg`, которые ещё предстоит сопоставить, а не двумя готовыми переводами.

Полнота периода не выводится из наличия списка: `coverage` остаётся `unverified`.
Ни пустой список, ни успешный разбор не доказывают полноту банковской истории.
Локальный JSON — переносимый промежуточный результат запуска, не обязательный
журнал. Повторный запуск строит его заново из источников.

## Разбор перед уточнениями

`review` читает результат `compare` и сохраняет все исходные случаи, отклонённые
строки, кандидатов с их полями и отличиями, а также записи приложения без
сопоставления. Вопросу доступны даты, суммы, счета, описание, заметки, категории
и теги кандидатов. Сырые ответы остаются во входном файле, который связан хешем.

Группы собираются по источнику, счёту, валюте, направлению суммы, названию,
статусу и результату сопоставления. Все случаи входят ровно в одну группу,
одинаковые операции сохраняются по отдельности. Группа содержит полный список
случаев, их число и границы дат. Это заготовка разбора, не правило классификации
и не утверждённый пакет для записи. `human_question_count` остаётся `null`:
число групп не означает число вопросов человеку.

`marked_fields_match` относится только к полям, проверенным `compare`, а не
к полноте учёта или верности категории и тега. `no_candidate` не доказывает
пропуск. Неподтверждённая полнота источника и ограничения сопоставления сохраняются.
Отчёт не разворачивает правила округления и кешбэка, не применяет отдельные
подтверждения из диалога автоматически и не пишет в приложение. `ready` всегда `false`.

`pending_rechecks` содержит все записи переданной выгрузки с `cleared=false`,
в том числе уже сопоставленные и находящиеся вне периода новых операций.
Для каждой сохранены поля записи, `ledger_index`, все метки в `recheck_sources`
и причины уточнения в `recheck_issues`. Отсутствие метки не скрывает запись
и не подменяется догадкой о банке. Разные записи с одинаковыми метками остаются
разными записями. `ledger_input_count` показывает объём проверенной выгрузки.
Чтобы охватить все незавершённые записи приложения, нужна полная свежая выгрузка.
Это список для последующего чтения источников, а не результат такого чтения
и не подтверждение завершённости. Сетевые запросы эта команда не выполняет.

Читающий JS-адаптер принимает прежние банковские ID через
`collectDetailsByIds(ids, options)`. Он запрашивает карточки заново без фильтра
периода и сохраняет исходный список ID, собственные ID карточек и ошибки.
`collectHistoryWithBalance({recheckIds, ...})` выполняет это чтение после нового
периода и до второго замера остатка. Непрочитанная прежняя карточка оставляет
общий результат неполным. `resumeHistory` повторяет такие запросы и сохраняет
уже прочитанный список нового периода. Ответы прежних карточек лежат отдельно
в `rechecks` и не объявляют полноту истории за старые даты.
Прежний ID может адресовать старую версию карточки: повторный HTTP-запрос
не доказывает актуальность её статуса. Поэтому `rechecks.coverage` равен
`requested_versions_only`. Перед обновлением записи нужно сопоставление
с актуальной историей, включая прежние даты незавершённых операций.
Сборщик для запуска через CDP создаётся вызовом
`build(output, period=period, recheck_ids=ids)`: прежние ID входят в собранный
скрипт без ручного ввода в браузере. Их источник — метки незавершённых записей
свежей полной выгрузки, относящиеся к Яндекс Банку. Записи других источников
и записи без меток остаются в общем отчёте повторной проверки.

### Подтверждения к конкретным операциям

`resolve-source` применяется к исходному результату адаптера до `compare`.
Вход подтверждений — JSON-массив объектов `source`, `id`, `expect`, `set`, `reason`.
В `expect` обязательны точные исходные `timestamp`, `amount`, `currency`, `account`,
`status`, `cleared`, включая `null`. Изменение любого значения, отсутствие или
повтор ID останавливают применение. `set` допускает только непустые `account`,
`other_account` и `kind` (`expense`, `income`, `transfer`, `transfer_leg`).
Подтверждение одной операции не меняет одноимённые счета остальных операций.

Необязательное `same_operation_as: {"source": "yabank", "id": "other-id"}`
указывает второе отображение основной операции. Обе исходные строки остаются,
их суммы и валюты не заменяются. Цель должна существовать ровно один раз,
цепочки связей запрещены. `review` показывает `confirmed_source_alias` со ссылкой
на основной случай и сохраняет прежнюю оценку совпадений в `source_match_assessment`.
Это связь представлений, она не создаёт перевод между счетами.

Применённые поля и прежние значения сохраняются в `resolution` каждой строки,
весь исходный JSON и файл подтверждений связаны хешами. Общие замечания источника
остаются в результате, снимается только `unknown_account` у явно указанной строки.
`reason` хранит основание, но сам текст не доказывает согласие: вызывающий агент
должен использовать только действительно подтверждённые человеком случаи.
Файл — воспроизводимый вход текущего разбора, не обязательный локальный журнал.
После записи устойчивую связь обеспечивают метки в приложении. Файлы с реальными
операциями не входят в Git. Сам `resolve-source` не меняет приложение.

### Округления и ожидаемый кешбэк

`yandex-accounting` применяется после подтверждений, до `compare` и `review`.
Успешные и незавершённые операции с банковским полем «Округление» между
«Карта Пэй» и «Округление» становятся ожидаемыми расходом и доходом с собственными
ID. Обратные переводы и обычные переводы без этого поля остаются переводами.
Категория дохода — «Округление». Категория расхода требует связи с покупкой.

Для каждой стороны подбираются все предшествующие покупки с карты в явно
заданном окне. Ни единственный, ни ближайший кандидат не считаются подтверждением.
У кандидата есть предлагаемое время «покупка +1 минута». Пока связь не установлена,
дата остаётся исходной банковской, а `rounding_parent_requires_review` и
`accounting.unresolved_fields` показывают недостающие сведения.

Положительный `cashback_hint` покупки без замечаний создаёт ожидаемый доход
на «ЯПлюс Баллы» в единице `YPLUS_POINTS`, категория «Баллы», через две минуты.
Метка использует ID покупки с `role=cashback`. Самостоятельные начисления баллов
сохраняются отдельно: эта команда не решает, являются ли они тем же начислением.
Отменённые, неуспешные операции и подтверждённые вторые отображения доход не
порождают. Покупка с замечанием о кешбэке остаётся на уточнение.

API-статус кешбэка `NONE` означает предварительную сумму: отдельный доход
получает `status=pending`, `cleared=false`, даже если покупка завершена.
`FULLY` даёт завершённый доход. При нескольких составляющих все должны быть
`FULLY`, иначе весь доход предварительный. Неизвестный код остаётся на уточнение.
Идентификатор и роль при подтверждении остаются прежними, сумма берётся итоговая.
Согласованное правило повторной записи: пока кешбэк предварительный, существующая
запись не меняется. После подтверждения меняются сумма и завершённость той же
записи. `plan_cashback_confirmations(comparison)` предлагает исправление только
по одной точной метке прежнего незавершённого дохода без других отличий и
замечаний. Предварительный источник оставляет запись как есть. Совпадение по
сумме и дате, конфликт меток или отличие счёта требуют уточнения.
Общий механизм `plan_confirmations(comparison)` обрабатывает расходы, доходы
и переводы любого источника. Пока источник сообщает `pending`, прежняя запись
не меняется. После `completed` он предлагает сумму и `cleared=true` той же
записи по точной метке. Конфликты, смена направления, счёта, валюты, времени,
типа и прочие замечания остаются на уточнение. Обе связанные стороны перевода
подтверждаются вместе, с равными противоположными суммами в одной валюте.
Сплит и валютный перевод требуют отдельного разбора.

```sh
python3 lib/cli.py plan-confirmations /tmp/comparison.json --output /tmp/confirmations.json
```

Это предложение, `ready=false`. Список `updates` после проверки включается
в явный план `prepare_backup` со свежим хешем копии. Backend проверяет прежнюю
незавершённость и однозначность меток, сохраняет записи и пересчитывает оба
остатка счёта. Правка суммы до подтверждения, завершённой записи или метаданных
вместе с подтверждением отвергается. Этот путь проверен на изолированных копиях,
реальное восстановление такого подтверждения в приложении ещё не проверено.

В старом снимке без собственного статуса кешбэка завершённость дохода от покупки
в обработке остаётся неизвестной с явным замечанием. Ожидаемый доход хранит происхождение
от покупки, но не наследует доказательство её счёта или подтверждение её полей.
Понятное описание создаётся отдельно от служебной метки. Тег требует контекста.

Все исходные строки сохраняются в начале `records`, производные дописываются.
`source_input_count` — число исходных строк вместе с отклонёнными,
`derived_count` — число производных, `input_count` — их сумма для последующего
сопоставления. `origins` связывает каждую прочитанную исходную строку со всеми
ожидаемыми строками, полнота этой связи проверяется. `coverage` остаётся оценкой
чтения источника, а не правильности учёта. Повторный разворот правил запрещён.
Это ожидаемые записи для проверки, не утверждённый план изменения приложения.

### Перевод с одной исходной записью

`transfer-accounting` дополняет ожидаемые записи перед сопоставлением и `plan-transfers`.
Тип `transfer` означает уже определённый перевод с двумя известными собственными
счетами. Его исходная сторона становится `transfer_leg`, а ожидаемая вторая
сторона получает противоположную сумму. Применяется только при совпадении единиц
источника и валют счетов приложения. Межвалютный курс не предполагается.
Неполные сведения, прежняя роль метки, замечания источника и неподтверждённый
статус остаются в результате с причиной уточнения. Незавершённый перевод
сохраняет незавершённость обеих ожидаемых сторон.

У второй стороны нет придуманного банковского ID: используется ID исходной
операции с ролью `transfer-counterpart`. `native_id` остаётся пустым. Это
производная запись учёта, а не найденное зачисление из второго источника.
Происхождение и счёт исходных/производных строк сохраняются вместе с прежними
связями округлений и кешбэка. Обычные операции и уже прочитанные стороны
`transfer_leg` не разворачиваются повторно. Повторный запуск этапа запрещён.
План переводов проверяет существующие метки обеих сторон и прежние кандидаты.
Этап не создаёт счета, не исправляет прежние записи и не меняет приложение.

### Предложения категорий по прежним записям

`classification-evidence` дополняет `review` профилями с вариантами категорий,
типов операции, примерами описаний и тегов. Профиль ограничен источником, счётом,
валютой, направлением, названием операции, ролью и MCC. Для каждого примера
сохранены точные индексы случая и строки приложения. Исходные случаи не меняются.

Основанием служат только завершённые операции без замечаний с единственным
кандидатом или меткой. Кандидат с отличиями финансовых полей, общей ссылкой из
нескольких исходных записей, составной категорией или переводом не становится
основанием. Временное отличие допустимо как пример для проверки человеком,
а не как доказательство идентичности. Производные записи и округления не обучают
классификацию по своей категории.

Одна категория в примерах означает `single_category_evidence`, несколько —
`conflicting_category_evidence`, отсутствие — `no_category_evidence`. Это сведения
для предложения, не автоматическое одобрение. Категории, заданные правилом кешбэка
и дохода округления, показываются отдельно. Для расхода округления нужен контекст
покупки. Теги примеров не присваиваются новым операциям по продавцу.

`classification.approved` и общий `ready` остаются `false`. Число профилей не
считается числом вопросов или числом пропусков. Команда не пишет в приложение
или Craft. Полные сведения лежат только в указанном приватном JSON, stdout
содержит сводку. Вход связан `classification_input_sha256`.

### Движение по счетам

`movement-control` сравнивает движения переданного источника и приложения по
счетам и валютам. Можно передать исходные или ожидаемые учётные записи, но
второй вариант использует даты правил учёта, включая сдвиг кешбэка. Это сравнение
движения, а не чтение банковских остатков. Период задаётся датами и часовым
поясом, начало включается, конец — начало следующего дня после `--to-date`.

По каждой стороне отдельно считаются число записей, доходы, расходы и итог для
завершённых и незавершённых операций. Разницы считаются только внутри одного
счёта и валюты. Применяются явные соответствия счетов и единиц из карты счетов.
Ни разные валюты, ни неизвестные курсы не складываются.

Каждая прочитанная строка получает результат в `source_dispositions` или
`ledger_dispositions`: учтена, вне периода, подтверждённое второе отображение,
неуспешная или отменённая, перевод внутри одного счёта приложения либо неясная.
Запланированные и удалённые записи приложения не включаются. Несопоставленные
счета и неизвестная завершённость не исчезают, а остаются с причиной.

Счета приложения вне переданной карты источников показываются отдельно в
`uncovered_ledger_accounts`, не сравниваются с нулевым движением банка. Даже
сопоставленный счёт может покрываться источником лишь частично, например внешняя
карта, оплата с которой видна только в одном сервисе. Поэтому у каждого счёта
`source_coverage_verified: false` до отдельного подтверждения полноты.

`opening_balance` и `closing_balance` остаются `null`, `ready` — `false`, даже
когда разница движения равна нулю. Нужны подтверждённые остатки на один момент
для всех источников объединённого счёта и проверка состава операций. Коррекция
остатка для сокрытия разницы этой командой не создаётся.

`records` содержит сводки счетов, `input_count` — их количество. Количество
исходных строк отдельно в `source_input_count` и `ledger_input_count`, отказы
парсеров и их замечания сохраняются в `input_rejections` и `input_issues`.
Все входы связаны хешами `movement_inputs_sha256`. Команда не меняет приложение.

## Debit & Credit

### Пачка переводов

```sh
python3 lib/cli.py plan-transfers /tmp/expected-source.json --backup /путь/source.dcbackup --accounts /tmp/accounts.json --from-date 2026-07-20 --to-date 2026-10-18 --timezone Europe/Moscow --pair-window-seconds 300 --ledger-window-seconds 129600 --output /tmp/transfers.json
python3 lib/cli.py prepare-backup /путь/source.dcbackup --plan /tmp/transfers.json --target /tmp/prepared.dcbackup --timezone Europe/Moscow --output /tmp/preparation.json
```

`plan-transfers` сама читает полный backup, проверяет его неизменность во время
расчёта и сохраняет хеши исходной базы и WAL. Отчёт содержит `backup_plan`, который
`prepare-backup` принимает напрямую. Если новых пар нет, `backup_plan: null`:
пустая копия для повторного импорта не готовится. Изменившаяся после планирования
база или WAL делают план недействительным. Ни одна команда не регистрирует и
не восстанавливает копию автоматически. Код возврата 1 у планировщика означает
предложение для проверки, а не ошибку подготовки файла.

Библиотечная `build_transfer_plan(source, ledger, mapping, start, end,
pair_window_seconds=..., ledger_window_seconds=...)` готовит новые стороны переводов
для `prepare-backup`. Нужны полный источник с `coverage: snapshot_complete`, полный
нефильтрованный backup без ошибок разбора, явные соответствия счетов, период с
часовыми поясами и два окна в секундах. Счета должны уже существовать однозначно.

Пара выбирается только при взаимно единственном совпадении двух завершённых
сторон с обратными счетами, противоположными суммами, одной сопоставленной единицей
и временем в окне. Это проверяемое сопоставление, а не извлечённая нативная связь
банка. Повторяющиеся ID, несколько вариантов, непарные строки и операции с
замечаниями остаются вне пачки с причиной. Перевод внутри одного счёта приложения
не записывается. Разные валюты без явного соответствия не объединяются.

Метка любой стороны в приложении предотвращает повторное добавление всей пары.
Даже обычная запись с той же суммой на том же счёте в расширенном окне откладывает
пару на проверку. Поиск не ограничивается переводами, отметками завершённости
или выбранным периодом источника. Окно может пересекать границу суток.

`records` хранит результат каждой исходной строки, `selected_pairs` — выбранные
пары индексов, `additions` — явные строки существующего формата редактора копии.
Обе стороны имеют свои ID в заметках, взаимные ключи плана и понятное описание.
Банковские комментарии сохраняются. Категория, тег и контрагент для перевода
пустые. Старые записи, счета и приложение эта функция не меняет.

План для редактора дополняется актуальным `backup_fingerprint` конкретной копии.
Готовность плана не означает согласованность банковских остатков. Сам отчёт
планировщика оставляет `ready: false`: он содержит предложение пачки, а не факт
восстановления. После подготовки проверяются все операции и счета, после
восстановления — новая копия приложения. Перед установкой пакет пересобирается
от свежей копии, если исходное состояние изменилось.

### Резервная копия

`debit-credit-backup` читает SQLite-файл `.dcbackup` и одноимённый `-wal`, если
он есть. Оригинал открывается только для копирования байтов. SQLite работает с
отдельной временной копией в режиме `mode=ro` и `query_only`. Если исходные файлы
изменились во время копирования или схема не поддерживается, чтение прекращается.

Проверено на Debit & Credit 7.9 и копии, показанной приложением как созданной
18 октября 2026 в 01:41: 12 575 транзакций и 28 счетов. Все 4 348 строк за 2026 год
сопоставлены с предоставленным CSV с сохранением кратности. Для сравнения учтены
точность даты CSV до минуты и замена переводов строк заметки пробелами при экспорте.
В самом результате backup переводы строк и исходная точность даты сохраняются.

Дополнительно доступны iCloud-ID приложения, валюта, завершённость,
связанный ID второй стороны перевода, путь категории и отдельные составные
категории с суммами. `source_id` берётся из `ZRECORDNAME`, а `Z_PK` остаётся лишь
локальным указателем. Будущие и помеченные удалёнными записи сохраняются, но
не считаются доступными для автоматического сопоставления.

После восстановления на проверенной копии 18 октября 2026 все iCloud-ID счетов
и операций были пустыми. Чтение таких строк сохраняет `source_id`/`account_id`
как `null`, не подставляет вместо них локальные номера и не теряет операции.
`linked_locator` связывает стороны перевода внутри одного снимка. Его нельзя
переносить между копиями: при восстановлении меняются и эти номера.
`cloud_identity` сообщает количество пустых ID. Наличие ID не доказывает
завершение синхронизации, а сам ID не считается устойчивым к восстановлению.

Мелкая двоичная погрешность SQLite убирается только для явно поддержанных
валют с двумя знаками и только в пределах 0,00000001 от копейки. Исходная сумма
остаётся в `raw`. Настоящая доля копейки и неизвестная точность валюты требуют
проверки. Составные категории не склеиваются в новую категорию.

В `accounts` возвращаются сохранённые остатки с учётом и без учёта незавершённых
операций. Это остатки приложения. Их совпадение с суммами локальной истории не
доказывает совпадения с банком. Отметки `reconciled` и последний сохранённый
остаток сверки не принимаются за дату и подтверждённую точку последней сверки.

Если в backup есть связь операции с повторяющимся шаблоном, адаптер сохраняет
`recurring_template_locator`. Она видна в `review`, включая старые записи без
сопоставления. Это локальный указатель внутри конкретной копии, а не переносимый
ID и не доказательство фактического списания или провайдера. Отсутствие колонки
отмечается `recurring_links_available=false`, а не выдаётся за отсутствие
автоповторов. Неизвестное значение сохраняется с замечанием, финансовая запись
не теряется. Шаблоны и операции при чтении не изменяются.

Свежую копию создаёт Влад перед изменениями и после импорта. Исходные backup,
база приложения и iCloud этим модулем не изменяются.

### CSV

Поддержаны ровно девять колонок предоставленной русской выгрузки, UTF-8 BOM,
даты на русском и ISO, дробные суммы с запятой и пробелы-разделители тысяч.
Описание, заметки, категория, тег и контрагент сохраняются отдельно.
Составная категория пока сохраняется исходной строкой, не превращается
в новую категорию и не раскладывается автоматически.

Строки двух сторон перевода сохраняются отдельно. У валютного перевода суммы
не обязаны быть равны. Объединение сторон в одну запись ещё не реализовано.

Валют и завершённости в предоставленном CSV нет. `currency` и `cleared`
остаются неизвестными. Валюту можно передать явным JSON-файлом `--currencies`,
например `{"Наличные (EUR)": "EUR"}`. Никакие валюты по именам не угадываются.
Начальные/конечные остатки и ID записей приложение этим файлом не передаёт.
Таким экспортом нельзя доказать правильность завершённости или баланса.
Для этих полей используется резервная копия.

## Сопоставление

`compare` читает результаты адаптеров и явную карту счетов. Входные файлы
и приложение не изменяются. Метки связываются по тройке источник, ID, роль.
Несколько записей приложения с одной меткой выводятся конфликтом. Повторный
исходный ID сохраняется отдельными строками и отмечается для проверки.

Для старых записей без меток возвращаются кандидаты с той же суммой, валютой,
счётом и временем в заданном окне. Это поиск, не решение о тождестве операций.
Окно задаётся `--window-seconds`, его границы учитывают точность исходной даты.
На кандидата могут претендовать несколько исходных строк: такая общая запись
отмечается у каждой строки, без назначения по порядку или склейки покупок.
Записи с другими метками в этот поиск не входят и остаются видны отдельно.

Карта счетов имеет вид:

```json
{"yabank":{"Карта":{"account":"Карта Пэй","source_currency":"RUB","currency":"RUB"}}}
```

Никакого сопоставления по похожему имени нет. Единицы источника и приложения
задаются явно. Это обозначение единиц одного числа, не пересчёт валюты.
Для валютного перевода две стороны сравниваются отдельно, объединение в перевод
не реализовано. Роли кешбэка сопоставляются только у уже подготовленной записи
с явным `role`, из `cashback_hint` новый доход здесь не создаётся.

У связи по метке выводятся отличия суммы, единиц, счёта, известного второго
счёта, известного типа, времени и завершённости. Категории, теги и описания
пока не сравниваются. Пустое поле источника не считается известным пустым
значением и не очищает поле приложения. Не найденный кандидат не доказывает
пропуск: сумма, счёт или время старой записи могли быть другими.

Все строки, исходные ошибки разбора, записи приложения и их индексы сохраняются
в результате. `ready` всегда `false`, код выхода CLI — 1: результат предназначен
для разбора агентом с человеком, не для автоматического импорта. Сверки остатков
и подтверждения полноты истории эта команда не выполняет.

## Проверка массового импорта

Официальная инструкция подтверждает CSV, QIF, QFX и OFX. Для CSV приложение
предлагает назначить столбцы, затем сопоставить счета, категории, контрагентов
и теги. Отсутствующие значения этих справочников можно создать при импорте.
Это не подтверждает, что обратная загрузка экспортного CSV сохраняет все поля.

На последнем экране приложение само снимает выбор с предполагаемых повторов.
Перед загрузкой подготовленного пакета нужно сверить выбранные строки с пакетом
по количеству и составу. Две настоящие одинаковые покупки должны остаться двумя
записями. Повторный импорт служебной метки приложение ещё не проверяло.

До первого массового импорта нужен небольшой проверочный пакет и свежая копия
до и после его загрузки. Сравнение должно подтвердить время, счёт и валюту,
сумму, описание, контрагента, заметку с меткой, категорию, тег и завершённость.
Отдельные случаи — одинаковые покупки, перевод между счетами, валютный перевод
и составная категория. У перевода проверяются обе связанные стороны, а не только
общая сумма. Проверка ни одного из этих случаев пока не выполнена в приложении.

Инструкция также описывает превращение импортированных расходов и доходов
в перевод через меню Mac-приложения. Это запасной путь для файла без явных
переводов, а не доказательство их автоматического восстановления при импорте.
Удаление и исправление существующих записей импортом не подтверждены.

Источники проверки от 18 октября 2026:
- [Шаги импорта и выбор повторов](https://debitandcredit.app/help/import-export-importing.html).
- [Преобразование в переводы](https://debitandcredit.app/help/import-export-converting-transactions.html).

### Контроль результата добавления

`verify-import` читает полные резервные копии до и после через тот же читающий
адаптер и сравнивает их с ожидаемыми записями. Список ожиданий содержит поля
общей записи, явную валюту, завершённость и служебные метки. Для стороны перевода
нужна `transfer_peer_marker` — метка ожидаемой второй стороны.

Проверяются все поля импорта, точность времени и единственность совпадения
по меткам. У перевода проверяются взаимные ID приложения и правильные метки
обеих сторон. Это обнаруживает и перепутанные связи двух одинаковых переводов.
Изменение остатков каждого счёта сравнивается с суммами ожидаемых записей,
отдельно с учётом и без учёта незавершённых операций.

Изменения и удаления прежних записей, неожиданные новые записи, смена состава
счетов и ошибки чтения снимков не дают успешной проверки. `ready=true` здесь
означает совпадение только ожидаемых добавлений. Это не сверка с банком и не
проверка механизма исправления или удаления старых операций.

CSV сохраняет заявленную точность ISO-даты: секунды не понижаются до минут.
При проверке файла с двумя сторонами перевода исходные счета, даты, суммы
и метки читаются обратно перед пробой. Импорт самого файла пока требует
отдельной проверки в приложении и нового снимка после неё.

## Яндекс Банк

Адаптер принимает массив снимков открытых карточек. Это чтение DOM, не API
банка. `lib/yandex_bank_capture.js` экспортирует `captureBankDom`: её вызывают
через `tab.playwright.evaluate` в подключённой видимой вкладке CUA. Функция
читает только открытую карточку. Навигации и обращений к сети внутри нет.
Сбор и проверка полноты всего периода пока не реализованы.

К результату DOM-функции вызывающая сторона добавляет URL текущей карточки,
время чтения `captured_at` и явный часовой пояс отображения `timezone`.
`read_cards` и CLI распознают поля `rows`, `transferTitles`, `pointsAmount`
и приводят их к тому же формату, что в примере ниже. Исходные строки сохраняются.
Заголовок кешбэка и его составляющие читаются отдельно, итог не суммируется
повторно с составляющими. Неизвестная разметка вызывает явную ошибку.

На 18 октября 2026 проверены восемь карточек в реальной видимой истории:
покупки в обработке, выполненная покупка, обе стороны округления, самостоятельное
начисление баллов и отменённая покупка. У двух одинаковых покупок совпадают
сумма и показанное время, но различаются ID. Повторное открытие одной покупки
сохранило её ID. Стабильность ID при смене статуса и между сессиями не доказана.
Реальные снимки не включены в репозиторий. Автотесты используют обезличенные поля.

```json
[
  {
    "url": "https://bank.yandex.ru/my/transactions-history/operation?id=example",
    "captured_at": "2026-10-18T12:00:00+03:00",
    "timezone": "Europe/Moscow",
    "title": "Такси",
    "amount": "−306 ₽",
    "date": "5 июля 2026, 16:15",
    "is_points": false,
    "details": [["Статус", "Выполнено"], ["Способ оплаты", "Карта Пэй"], ["Кешбэк", "+31"]],
    "transfer_accounts": []
  }
]
```

`transfer_accounts` заполняется только из явно показанных счетов внутреннего
перевода, в порядке отправитель → получатель. Знак суммы определяет сторону.
У округления сохраняются ID отдельных сторон. Номер покупки не подставляется.

Принимается только HTTPS-URL карточки на `bank.yandex.ru` с одним `id`.
Страницы входа и переводов отвергаются. Это проверка входных данных, а не
техническая блокировка браузера. Действия в браузере выполняются в видимом
Владу окне истории. Отдельно разрешено скриптовое чтение истории запросами.

ID из URL сохраняется непрозрачным после одного URL-декодирования. Его
стабильность между сессиями надо проверить в реальном окне. Даты «сегодня» и
без года разрешаются относительно `captured_at` и отмечаются для проверки.
Часовой пояс отображаемой даты передаётся явно в `timezone`, а не берётся
из системных настроек ноутбука.
Сумма без явного знака отвергается. Новая/неизвестная форма статуса не
принимается за завершённую операцию.

`Выполнено` → `status=completed`, `cleared=true`.
`В обработке` → `status=pending`, `cleared=false`.
`Отмена` / `Не выполнено` → `status=canceled`, `cleared=null`.
Отмена и возврат не смешиваются. Ничего не удаляется автоматически.

Баллы имеют единицу `YPLUS_POINTS` и счёт `ЯПлюс Баллы`. Самостоятельное
начисление не требует покупки. Показанный у покупки кешбэк сохраняется как
`cashback_hint`, без создания второго дохода на этапе чтения.
МСС и банковская категория сохраняются как реквизиты, не назначают категорию
приложения. Неизвестный счёт не заменяется картой по умолчанию.

Полный проход 4–5 июля 2026 дал 30 карточек. Повторное чтение списка сохранило
те же ID и кратность, суммы карточек воспроизвели итоги банка. Это проверка
конкретного периода, а не доказательство полноты любого будущего запуска.
Проверка прямого HTTP-сборщика на этом же периоде остаётся отдельным условием.

## Метки

Реализовано чтение предложенного формата из заметок:
`[dc-sync:v1 source=yabank id=example role=cashback]`.
`role` необязателен. ID кодируется percent-encoding, чтобы пробелы, `]` и
другие символы не ломали формат. Несколько меток сохраняются отдельно,
человеческий текст заметки не меняется. Некорректная метка вызывает явную ошибку.
Генерация метки не означает подтверждённого сопоставления двух операций.

## Проверки и границы

Тесты покрывают одинаковые покупки, повторный снимок того же ID, разные ID
сторон округления, валютные стороны перевода, самостоятельные баллы, pending
и отмены, ошибки полей и чтение меток. CSV дополнительно проверяется на
предоставленной выгрузке локально, без сохранения реальных операций в тестах.

Не реализованы: импорт, исправление и удаление записей, сбор всех карточек из
банка, автоматическое разрешение неоднозначных сопоставлений, проверка полноты
периода и сверка балансов.
Модель сверки ещё обсуждается. Для каждого счёта нужна собственная подтверждённая
дата остатка. Этот модуль пока не объявляет ни один счёт сверенным.

Основания:
- [Парсер SafariScripts](https://github.com/Bonzar/SafariScripts/blob/afa48864d85b6ca159eff399b354a42359871ea9/YandexBankOperationParser.user.js).
- [Незавершённые операции Debit & Credit](https://debitandcredit.app/help/transactions-pending.html).
- [Импорт и экспорт](https://debitandcredit.app/help/import-export.html).

В приложении незавершённые операции не входят в обычный остаток. Можно отдельно
показывать остаток с их учётом. CSV без статуса не позволяет восстановить оба.

## Читающие запросы истории банка

18 октября 2026 в ресурсах открытой страницы истории обнаружен endpoint
`https://bank.yandex.ru/transactions/api/graphql`. Названия операций проверены
по публичному JavaScript версии `web-transactions-ssr/v2019.0`, chunk
`79a78444253e5f8b.js`:

- `TransactionsFeedPfm` / `getTransactionsFeedPfm` — список, `items`, `pendingItems`,
  `cursor`, фильтры и аналитика. В элементах запрашиваются ID, дата и `statusCode`.
- `TransactionOperationDetails` — реквизиты одной операции по ID.

Это GraphQL query, не mutation. Клиент банка передаёт hash запроса параметром
`operationId` и использует POST. По публичному коду есть курсорная подгрузка.
`lib/yandex_bank_queries.js` реализует пагинацию и до четырёх параллельных
запросов карточек по умолчанию. Другие операции и другой origin отвергаются.
Cookies не читаются и не экспортируются: браузер использует уже открытую
сессию того же банка. Незавершённые операции читаются из `pendingItems`.

С версии 0.3.0 этот же скрипт можно вставить в консоль на главной странице
`https://bank.yandex.ru/my`. Он читает видимый остаток плитки «Карта» до и после
сбора истории. Обе суммы, исходный текст, URL и время каждого чтения сохраняются
в `balanceObservations`. Платежи и переводы не открываются. На странице истории
сохраняется прежний режим без остатка. Перед повторным запуском нужно обновить
страницу, чтобы загрузились данные и убралась панель предыдущей версии.

`balanceControl.changed` показывает различие прочитанных сумм. Даже одинаковые
суммы не доказывают свежесть данных банка или единый срез с историей:
`atomic=false`, `freshness=unknown`, `reconciled=false`. Вид остатка на экране
не подписан, поэтому `balance_type=displayed_unspecified`, `blocked_amount=null`.
Отсутствие, скрытое число или несколько плиток дают явную ошибку наблюдения,
а не нулевой остаток. История при этом сохраняется. Эти наблюдения пока остаются
в исходном JSON и автоматически не становятся подтверждёнными точками сверки.

Основной путь при доступном штатном CDP — без панели, Tampermonkey, диалогов
и ручного скачивания. Тот же сборщик собирается с фиксированным периодом:

```sh
python3 lib/build_userscript.py /tmp/bank-reader.js \
  --from-inclusive 2026-10-18T00:00:00+03:00 \
  --to-exclusive 2026-10-20T00:00:00+03:00
```

Полученный код выполняется штатным `Runtime.evaluate` с `awaitPromise=true`
в авторизованной вкладке банка. Возвращается `{ok, snapshot}` либо ошибка
с частичным `snapshot`. Клиент сохраняет результат локально. Вход допустим
только с главной страницы и страницы истории. Прямой остаток читается
GET-запросом к `/my` с `cache: no-store` до и после истории, без чтения
cookies, токенов или скрытого состояния приложения. Редирект на вход — ошибка.
Два представления плитки в серверном HTML должны совпасть. В наблюдение входят
исходные тексты, начало запроса, получение ответа, дата ответа сервера и режим
кеша. Вид остатка и блокировки по этому HTML всё ещё не определены.

Живой прогон 19 октября 2026 дал 47 операций и 47 карточек за 18–19 октября,
полный курсор и два успешных прямых чтения остатка. В том же проходе кнопки,
prompt-диалоги, ручное скачивание и изменение банковских данных не используются.
Запрос передаёт `x-yabank-time-zone` из `Intl.DateTimeFormat`, как штатный
`TransactionsApolloProvider` в chunk `f07c86092e543dc5.js`.
Повторы страниц учитываются отдельно. Разные данные у одного ID, повторный
курсор, отсутствие обязательных массивов или ошибка карточки сохраняют частичный
результат с `complete=false`. Найденные данные не теряются.

`build_userscript.py` собирает один файл для того же способа запуска, которым
запускался прежний Safari/Tampermonkey userscript. В истории появляется кнопка
«Собрать историю в JSON». Период задаётся пользователем, виден ход сбора,
результат скачивается локальным JSON-файлом. При ошибке сохраняется неполный
результат. Скрипт не запускает запись в Debit & Credit и не обращается к платежам.

Запросы и обработка ошибок проверены с подставным транспортом. Реальный запуск
v3 за 4–5 июля 2026 прочитал две страницы и 30 карточек. Для каждого из 30 ID
списка получен один ответ. Курсор исчерпан, ошибок, конфликтов и непрочитанных
карточек нет. С прежними DOM-снимками совпали суммы, валюты, даты до минуты,
названия, известные статусы, банковские категории, MCC и подсказки кешбэка.
Статусы API: 29 завершённых и одна отменённая. Для восьми выплат процентов
API подтвердил завершённость, которой не было в DOM-реквизитах.

`details` хранит собственный `id` банка и `requestedId` из запроса отдельно.
Полнота чтения считается по `requestedId`. Совпадающий native ID сам по себе
не объединяет записи. Исходные ответы без добавленных полей сохраняются
в `detailObservations`. Команда `yandex-bank-api` приводит GraphQL JSON к общему
формату. `source_id` остаётся ID списка, `native_id` хранится отдельно.
Проверка двух дней не доказывает полноту любого другого периода или наличие
в истории всех продуктов банка. Импорта и сверки банковских остатков ещё нет.

При чтении 1 января — 18 октября 2026 получены 237 страниц и 5 919 операций.
902 карточки прочитаны до единичного HTTP 500. Этот частичный файл проверен
как вход продолжения: 902 ответа сохраняются, 5 017 требуют дочитывания.

`resumeHistory(snapshot, options)` и кнопка «Продолжить из JSON» используют
сохранённые страницы вместо повторного запроса списка. До сети список заново
проверяется по исходным страницам, ответы — по `detailObservations`. Для уже
прочитанных `requestedId` запросов нет. Прошлые ошибки остаются отдельно
в `previousDetailErrors`, текущие — в `detailErrors`. Исходный объект не меняется.
Продолжение использует прежний срез списка и не обнаруживает новые операции,
появившиеся после его чтения. Перед окончательной сверкой нужен свежий список.

Временные HTTP 429, 500, 502, 503, 504 и сетевые ошибки получают до трёх повторов
с паузами 1, 3 и 8 секунд. Одна недоступная карточка не мешает читать остальные.
HTTP 401/403 или двадцать ошибок карточек останавливают дальнейшие запросы.
При оставшихся непрочитанных ID скачивается новый частичный результат для
следующего продолжения. Неполный список, конфликтующие страницы и неподтверждённые
сохранённые карточки не принимаются за пригодный вход продолжения.

## Нормализация JSON API

Поле `bank_comment` сохраняет текст банковского комментария как основание для
разбора назначения платежа. Оно видно в `review`, даже когда сырой ответ скрыт.
Комментарий не назначает категорию, тег или заметки приложения. Неизвестная
структура комментария оставляет операцию в результате с замечанием. Производные
кешбэк и встречная сторона перевода не выдают комментарий исходной операции
за собственный комментарий источника.

`source_account_observations` сохраняет счета из `pages[].sourceFilter.options[]`:
идентификатор банка, отображаемое имя, остаток и единицу суммы, номер страницы
и исходные поля. Повторные наблюдения остаются отдельными, включая изменения
имени или остатка. Группы фильтра перечислены в `excluded`, нераспознанные
элементы — в `rejected`. Счёт всех элементов проверяется отдельно от операций.
Доступные замеры карты до/после чтения сохраняются в `balance_observations`,
свойства замера — в `balance_control` без утверждения о завершённой сверке.

Имя счёта в текущем фильтре не подменяет историческое назначение операции.
Конфликт с прежними подписями сохраняется для проверки. Отображаемый остаток
может быть закеширован и не объявляется атомарным с историей операций.

Проверено на полном результате продолжения: 5 919 ID списка и столько же ответов
карточек, без непрочитанных ID и текущих ошибок. Прежние 902 карточки не изменились.
Каждая исходная операция попадает в `records` либо `rejected` с исходными данными.
Лишние ответы карточек остаются в `unmatched_details`. Полнота снимка проверяется
по списку страниц и признакам окончания, отдельно от возможности разобрать поля.

`CLEAR`, `HOLD`, `CANCEL`, `FAIL` различаются как завершённая, незавершённая,
отменённая и неуспешная операция. Направление суммы задаётся явными
`CREDIT`/`DEBIT`. Если у балльной операции направление отсутствует, явное
«Списание баллов» в единственном реквизите «Назначение» определяет списание.
Источник этого определения сохраняется в `direction_evidence`. Остальные
неизвестные направления не угадываются. Валюты, включая BYN,
и самостоятельные балльные операции сохраняются отдельно. Банковская категория
не подставляется в категорию приложения, а кешбэк остаётся подсказкой.

Счёт читается из составного заголовка или реквизитов. Отсутствующая подпись
может быть восстановлена по ID договора из данных квитанции, если этот же ID
однозначно связан с подписью счёта в других операциях снимка. В результате
сохраняются `bank_account_ids`, запись-образец в `account_evidence` и общий индекс
`bank_account_identity_names`. Ссылки квитанций не открываются. Несколько
подписей на одном ID требуют проверки. Это имя счёта банка, не карта соответствия
счетам Debit & Credit. Название внешней карты в способе пополнения не заменяет
счёт получателя, если договор однозначно определяет собственный счёт банка.

В реальном файле разобраны все 5 919 операций. У трёх балльных операций без
направления списание определено по явному реквизиту «Назначение».
Остались девять операций без определённого счёта,
один случай отличия статуса списка от карточки и одна подсказка кешбэка со статусом
`NONE`. На момент исходного разбора эти случаи требовали уточнения. Для `NONE`
теперь действует описанное выше правило предварительного дохода. Разбор не
подтверждает совпадение остатков и не создаёт операции приложения.

### Проверка восстановления изменённой копии

```sh
python3 lib/cli.py verify-restore /путь/prepared.dcbackup /путь/restored.dcbackup --timezone Europe/Moscow --output /tmp/restore-check.json
```

`verify-restore` сравнивает полные копии: подготовленную и созданную приложением
после восстановления. Внутренние iCloud-ID и локальные номера не сравниваются.
Все операции группируются по содержимому с сохранением количества одинаковых
строк. В сравнение входят сумма, валюта, счета, точное время, завершённость,
описание, заметки с метками, категории и составные категории, тег, контрагент,
отметка сверки и признак будущей операции. У перевода дополнительно сравнивается
содержимое связанной стороны и проверяется взаимность локальных ссылок.

Отдельно сравниваются все счета по имени и валюте, их остатки, последний
сохранённый остаток сверки и видимость. Одинаковые имена счетов одной валюты
дают неоднозначность и не позволяют объявить проверку успешной. Ошибки чтения
блокируют результат. В отчёте остаются и пропавшие, и лишние группы с кратностью.
Снимки с `date_filter` для полной сверки не принимаются. Команда читает обе базы
целиком и сохраняет SHA-256 файлов и их WAL. Изменение любого входа во время
проверки прерывает её, а не выдаёт результат для разных состояний файлов.

`ready` этой команды доказывает только совпадение перечисленных полей операций
и счетов. Проверка не подтверждает баланс банка, завершение iCloud-синхронизации,
бюджеты, планы или байты файлов вложений. На реальной паре копий 18 октября 2026
18:13 → 18:43 проверены все 12 577 операций и 28 счетов, отличий нет.
Это проверка результата восстановления, а не готовый редактор резервных копий.

### Подготовка изменённой копии

```sh
python3 lib/cli.py prepare-backup /путь/source.dcbackup --plan /tmp/plan.json --target /tmp/prepared.dcbackup --timezone Europe/Moscow --output /tmp/preparation-report.json
```

`prepare-backup` правит время, описание и заметки существующих операций и добавляет
новые расходы, доходы и связанные стороны переводов. Суммы и классификацию старых
операций он пока не меняет. Имя нового описания создаётся отдельной записью справочника
с обновлением его счётчика Core Data. Существующее описание не переименовывается.

План содержит `schema_version: 1`, `source_sha256` со значениями `database` и `wal`
из `backup_fingerprint(path)`, а также `updates` и необязательный `additions`.
Хотя бы один из списков должен быть непустым. У каждой правки явный `locator`
и объект `set` с полями `timestamp`, `description`, `notes` — только нужными.
Дата передаётся ISO-строкой с часовым поясом. Пустое описание снимает описание.
Заметка передаётся целиком, включая сохраняемый текст и служебные метки.

`locator` действует только внутри зафиксированного хешами снимка. План устарел
после изменения файла или WAL — подготовка прекращается. Для другого снимка
план строится заново. Он не заменяет метки операций и не служит постоянным журналом.

Исходные файлы открываются только для чтения байтов. SQLite работает с временной
копией. На выходе — новый самостоятельный файл с правами 0600, без WAL. Существующий
файл или старые SQLite-файлы рядом с выходом не перезаписываются. Перед публикацией
сравниваются все таблицы: разрешены только правки по плану, новые операции,
их описания, рассчитанные остатки и соответствующие счётчики. Неожиданная правка не позволяет
выдать файл, включая побочный эффект SQL-триггера. Проверяются целостность SQLite,
неизменность остальных операций и счетов и соответствие результата плану.

`ready` означает локальную проверку подготовленного файла. Команда не регистрирует
копию в списке приложения и не восстанавливает её. После восстановления нужна
новая копия приложения и `verify-restore`. Из реальной копии 18 октября 2026 18:07
модуль повторил правки пробного перевода. Все операции и счета результата совпали
с проверенной копией после восстановления 18:43.

Каждая строка `additions` содержит `key`, `peer_key`, `kind`, `account`, `currency`,
`amount`, `timestamp`, `cleared`, `description`, `notes`, `category_path`, `tag`,
`payee`. Поля обязательны, даже когда значение — `null` или пустой список.
У обычного расхода/дохода `peer_key: null`. Две стороны перевода задаются отдельно,
со взаимными `peer_key`, противоположными знаками и своими исходными датами.
В одной валюте суммы перевода должны сходиться. В разных валютах сохраняются
два явно переданных числа, курс не угадывается.

`key` связывает строки только внутри плана. Постоянная связь с источником —
служебные метки в заметках. Каждой новой строке нужна хотя бы одна метка,
отсутствующая в исходной базе, других новых строках и правках заметок этого плана.
Понятное непустое описание обязательно, чтобы длинный служебный ID не заменял
название операции в интерфейсе. Две одинаковые покупки с разными метками остаются
двумя записями.

Для новых операций счета ищутся строго по имени и валюте, категория — по полному
пути, тег и контрагент — по имени. Отсутствующее или неоднозначное значение
останавливает подготовку. Новые счета, категории, теги, контрагенты и составные
категории пока не создаются. Создание описаний поддержано. Суммы должны быть
точными в поддержанных валютах, завершённость — явным логическим значением.

Новые строки получают отдельные ключи Core Data и взаимные ссылки переводов.
Сохранённые остатки меняются только на суммы новых строк: завершённые учитываются
в обоих остатках, незавершённые — только в остатке с их учётом. При SQL-сверке
разрешаются ровно эти новые строки, изменения двух полей остатка и служебной
версии затронутых счетов и соответствующие счётчики. Старые операции и остальные
поля счетов должны сохраниться. В отчёте есть соответствие ключей плана локальным
номерам созданных строк.

На копии 18 октября 2026 18:43 подготовлены четыре подтверждённых обмена баллов
на общую сумму 30 000 ₽: 8 новых сторон переводов. Полное сравнение с отдельно
построенным ожидаемым состоянием прошло для 12 585 операций и 28 счетов.

### Регистрация копии в Mac-приложении

`register-backup` добавляет только новую строку в `BackupList` и отдельный файл
в папку резервных копий. Для вызова нужны подготовленный файл, JSON-отчёт
`prepare-backup`, точный путь к plist настроек, имя исходной копии в списке,
время регистрации ISO с часовым поясом и новый путь для архива реестра:

```sh
python3 lib/cli.py register-backup /tmp/prepared.dcbackup --report /tmp/preparation-report.json --preferences /путь/Data/Library/Preferences/com.mr-brightside.debitandcreditMac.plist --source-filename 2026-10-18T18:43:58+0300.dcbackup --timestamp 2026-10-18T20:00:00+03:00 --registry-archive /tmp/original-backup-list.plist --output /tmp/registration-report.json
```

Приложение должно быть полностью закрыто. Исходная копия должна оставаться
последней в реестре и совпадать с хешами отчёта. Проверяются файл кандидата,
число операций и наличие архивных файлов вложений. Список вложений берётся
из записи исходной копии целиком. Старые копии, записи списка и остальные
настройки не заменяются. Архив содержит только `BackupList`, в бинарном plist
с правами 0600, с сохранением дробных секунд старых дат.

Запись выполняется macOS `defaults` по каноническому пути. Успех команды
сам по себе не считается результатом: plist перечитывается и сравнивается
целиком с ожидаемым состоянием. Неопределённая запись не повторяется автоматически.
В отчёте `ready` означает проверенную запись реестра. Видимость в интерфейсе
и восстановление отчётом не подтверждаются. Само восстановление выполняет Влад.

Два интеграционных теста реальной службы настроек выполняются только на macOS
и пишут исключительно во временные тестовые plist. В песочнице служба может
отказать записи даже в доступный временный файл. Эти проверки нужно запускать
в обычном локальном процессе с доступом к службе preferences. Остальные проверки
не требуют изменения настроек реального приложения.
