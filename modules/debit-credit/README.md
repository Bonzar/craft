# debit-credit

Отдельный библиотечный модуль с читающими адаптерами Яндекс Банка и Debit & Credit.
Python 3.11+, стандартная библиотека. Хуков, запуска Shortcuts и записи в приложение
нет. HTTP-сборщик разрешает только два читающих запроса истории банка.
Установщик переносит `lib` по обычному контракту модуля.
В репозитории не было кода финансовых адаптеров, поэтому существующие библиотеки
агента не расширяются банковскими правилами.

## Запуск

Из каталога модуля:

```sh
python3 lib/cli.py debit-credit '/путь/Все счета.csv' --timezone Europe/Moscow --output /tmp/dc-export.json
python3 lib/cli.py debit-credit-backup /путь/копия.dcbackup --timezone Europe/Moscow --from-date 2026-07-04 --to-date 2026-07-05 --output /tmp/dc-snapshot.json
python3 lib/cli.py yandex-bank /tmp/opened-cards.json --output /tmp/bank-operations.json
PYTHONPATH=lib python3 -m unittest discover -s tests -v
node --test tests/test_capture.js tests/test_queries.js
python3 lib/build_userscript.py /tmp/yandex-bank-history-reader.user.js
```

Команды читают вход, возвращают краткую сводку и при `--output` создают новый
JSON-файл с правами 0600. Существующий файл не перезаписывается. Данные не сохраняются в модуле
и не попадают в Git. Код возврата 0 означает отсутствие ошибок разбора, 1 —
отклонённые карточки/строки или неразрешённые поля, 2 — ошибка входного файла.
`ready` относится только к разбору, не к готовности переноса или сверке счёта.

## Общий результат

`schema_version: 1`, `adapter`, `input_count`, `records`, `rejected`, `issues`,
`coverage`, `ready`, `limitations`, а у CLI ещё `input_sha256`.

Каждая входная строка/карточка попадает либо в `records`, либо в `rejected` с
причиной и исходными данными. Счёт входа проверяется кодом. Совпадающие записи
сохраняются с исходной кратностью. `locator` — позиция в данном входном файле,
не постоянный ID и не часть метки.

Запись содержит `source`, `source_id`, `timestamp` с часовым поясом,
`timestamp_precision`, точную знаковую `amount` строкой без float, `currency`,
`account`, `other_account`, `kind`, `status`, `cleared`, `description`, `notes`,
`category`, `tag`, `markers` и `raw`. Неизвестные значения остаются `null`.

У CSV `kind` описывает запись приложения. У карточки банка смысл расхода или
дохода требует разбора, поэтому `kind` без подтверждённых двух счетов остаётся
`null`. Знак суммы при этом сохранён. Внутренние переводы представлены сторонами
`transfer_leg`, которые ещё предстоит сопоставить, а не двумя готовыми переводами.

Полнота периода не выводится из наличия списка: `coverage` остаётся `unverified`.
Ни пустой список, ни успешный разбор не доказывают полноту банковской истории.
Локальный JSON — переносимый промежуточный результат запуска, не обязательный
журнал. Повторный запуск строит его заново из источников.

## Debit & Credit

### Резервная копия

`debit-credit-backup` читает SQLite-файл `.dcbackup` и одноимённый `-wal`, если
он есть. Оригинал открывается только для копирования байтов. SQLite работает с
отдельной временной копией в режиме `mode=ro` и `query_only`. Если исходные файлы
изменились во время копирования или схема не поддерживается, чтение прекращается.

Проверено на Debit & Credit 7.9 и копии, показанной приложением как созданной
18 октября 2026 в 01:41: 12 575 транзакций и 28 счетов. Все 4 348 строк за 2026 год
сопоставлены с предоставленным CSV с сохранением кратности. Для сравнения учтены
точность даты CSV до минуты и замена переводов строк заметки пробелами при экспорте.
В самом результате backup переводы строк и исходная точность даты сохраняются.

Дополнительно доступны постоянный ID приложения, валюта, завершённость,
связанный ID второй стороны перевода, путь категории и отдельные составные
категории с суммами. `source_id` берётся из `ZRECORDNAME`, а `Z_PK` остаётся лишь
локальным указателем. Будущие и помеченные удалёнными записи сохраняются, но
не считаются доступными для автоматического сопоставления.

Мелкая двоичная погрешность SQLite убирается только для явно поддержанных
валют с двумя знаками и только в пределах 0,00000001 от копейки. Исходная сумма
остаётся в `raw`. Настоящая доля копейки и неизвестная точность валюты требуют
проверки. Составные категории не склеиваются в новую категорию.

В `accounts` возвращаются сохранённые остатки с учётом и без учёта незавершённых
операций. Это остатки приложения. Их совпадение с суммами локальной истории не
доказывает совпадения с банком. Отметки `reconciled` и последний сохранённый
остаток сверки не принимаются за дату и подтверждённую точку последней сверки.

Свежую копию создаёт Влад перед изменениями и после импорта. Исходные backup,
база приложения и iCloud этим модулем не изменяются.

### CSV

Поддержаны ровно девять колонок предоставленной русской выгрузки, UTF-8 BOM,
даты на русском и ISO, дробные суммы с запятой и пробелы-разделители тысяч.
Описание, заметки, категория, тег и контрагент сохраняются отдельно.
Составная категория пока сохраняется исходной строкой, не превращается
в новую категорию и не раскладывается автоматически.

Строки двух сторон перевода сохраняются отдельно. У валютного перевода суммы
не обязаны быть равны. Объединение сторон в одну запись ещё не реализовано.

Валют и завершённости в предоставленном CSV нет. `currency` и `cleared`
остаются неизвестными. Валюту можно передать явным JSON-файлом `--currencies`,
например `{"Наличные (EUR)": "EUR"}`. Никакие валюты по именам не угадываются.
Начальные/конечные остатки и ID записей приложение этим файлом не передаёт.
Таким экспортом нельзя доказать правильность завершённости или баланса.
Для этих полей используется резервная копия.

## Яндекс Банк

Адаптер принимает массив снимков открытых карточек. Это чтение DOM, не API
банка. `lib/yandex_bank_capture.js` экспортирует `captureBankDom`: её вызывают
через `tab.playwright.evaluate` в подключённой видимой вкладке CUA. Функция
читает только открытую карточку. Навигации и обращений к сети внутри нет.
Сбор и проверка полноты всего периода пока не реализованы.

К результату DOM-функции вызывающая сторона добавляет URL текущей карточки,
время чтения `captured_at` и явный часовой пояс отображения `timezone`.
`read_cards` и CLI распознают поля `rows`, `transferTitles`, `pointsAmount`
и приводят их к тому же формату, что в примере ниже. Исходные строки сохраняются.
Заголовок кешбэка и его составляющие читаются отдельно, итог не суммируется
повторно с составляющими. Неизвестная разметка вызывает явную ошибку.

На 18 октября 2026 проверены восемь карточек в реальной видимой истории:
покупки в обработке, выполненная покупка, обе стороны округления, самостоятельное
начисление баллов и отменённая покупка. У двух одинаковых покупок совпадают
сумма и показанное время, но различаются ID. Повторное открытие одной покупки
сохранило её ID. Стабильность ID при смене статуса и между сессиями не доказана.
Реальные снимки не включены в репозиторий. Автотесты используют обезличенные поля.

```json
[
  {
    "url": "https://bank.yandex.ru/my/transactions-history/operation?id=example",
    "captured_at": "2026-10-18T12:00:00+03:00",
    "timezone": "Europe/Moscow",
    "title": "Такси",
    "amount": "−306 ₽",
    "date": "5 июля 2026, 16:15",
    "is_points": false,
    "details": [["Статус", "Выполнено"], ["Способ оплаты", "Карта Пэй"], ["Кешбэк", "+31"]],
    "transfer_accounts": []
  }
]
```

`transfer_accounts` заполняется только из явно показанных счетов внутреннего
перевода, в порядке отправитель → получатель. Знак суммы определяет сторону.
У округления сохраняются ID отдельных сторон. Номер покупки не подставляется.

Принимается только HTTPS-URL карточки на `bank.yandex.ru` с одним `id`.
Страницы входа и переводов отвергаются. Это проверка входных данных, а не
техническая блокировка браузера. Действия в браузере выполняются в видимом
Владу окне истории. Отдельно разрешено скриптовое чтение истории запросами.

ID из URL сохраняется непрозрачным после одного URL-декодирования. Его
стабильность между сессиями надо проверить в реальном окне. Даты «сегодня» и
без года разрешаются относительно `captured_at` и отмечаются для проверки.
Часовой пояс отображаемой даты передаётся явно в `timezone`, а не берётся
из системных настроек ноутбука.
Сумма без явного знака отвергается. Новая/неизвестная форма статуса не
принимается за завершённую операцию.

`Выполнено` → `status=completed`, `cleared=true`.
`В обработке` → `status=pending`, `cleared=false`.
`Отмена` / `Не выполнено` → `status=canceled`, `cleared=null`.
Отмена и возврат не смешиваются. Ничего не удаляется автоматически.

Баллы имеют единицу `YPLUS_POINTS` и счёт `ЯПлюс Баллы`. Самостоятельное
начисление не требует покупки. Показанный у покупки кешбэк сохраняется как
`cashback_hint`, без создания второго дохода на этапе чтения.
МСС и банковская категория сохраняются как реквизиты, не назначают категорию
приложения. Неизвестный счёт не заменяется картой по умолчанию.

Полный проход 4–5 июля 2026 дал 30 карточек. Повторное чтение списка сохранило
те же ID и кратность, суммы карточек воспроизвели итоги банка. Это проверка
конкретного периода, а не доказательство полноты любого будущего запуска.
Проверка прямого HTTP-сборщика на этом же периоде остаётся отдельным условием.

## Метки

Реализовано чтение предложенного формата из заметок:
`[dc-sync:v1 source=yabank id=example role=cashback]`.
`role` необязателен. ID кодируется percent-encoding, чтобы пробелы, `]` и
другие символы не ломали формат. Несколько меток сохраняются отдельно,
человеческий текст заметки не меняется. Некорректная метка вызывает явную ошибку.
Генерация метки не означает подтверждённого сопоставления двух операций.

## Проверки и границы

Тесты покрывают одинаковые покупки, повторный снимок того же ID, разные ID
сторон округления, валютные стороны перевода, самостоятельные баллы, pending
и отмены, ошибки полей и чтение меток. CSV дополнительно проверяется на
предоставленной выгрузке локально, без сохранения реальных операций в тестах.

Не реализованы: импорт, исправление и удаление записей, сбор всех карточек из
банка, сопоставление источников, проверка полноты периода и сверка балансов.
Модель сверки ещё обсуждается. Для каждого счёта нужна собственная подтверждённая
дата остатка. Этот модуль пока не объявляет ни один счёт сверенным.

Основания:
- [Парсер SafariScripts](https://github.com/Bonzar/SafariScripts/blob/afa48864d85b6ca159eff399b354a42359871ea9/YandexBankOperationParser.user.js).
- [Незавершённые операции Debit & Credit](https://debitandcredit.app/help/transactions-pending.html).
- [Импорт и экспорт](https://debitandcredit.app/help/import-export.html).

В приложении незавершённые операции не входят в обычный остаток. Можно отдельно
показывать остаток с их учётом. CSV без статуса не позволяет восстановить оба.

## Читающие запросы истории банка

18 октября 2026 в ресурсах открытой страницы истории обнаружен endpoint
`https://bank.yandex.ru/transactions/api/graphql`. Названия операций проверены
по публичному JavaScript версии `web-transactions-ssr/v2019.0`, chunk
`79a78444253e5f8b.js`:

- `TransactionsFeedPfm` / `getTransactionsFeedPfm` — список, `items`, `pendingItems`,
  `cursor`, фильтры и аналитика. В элементах запрашиваются ID, дата и `statusCode`.
- `TransactionOperationDetails` — реквизиты одной операции по ID.

Это GraphQL query, не mutation. Клиент банка передаёт hash запроса параметром
`operationId` и использует POST. По публичному коду есть курсорная подгрузка.
`lib/yandex_bank_queries.js` реализует пагинацию и до четырёх параллельных
запросов карточек по умолчанию. Другие операции и другой origin отвергаются.
Cookies не читаются и не экспортируются: браузер использует уже открытую
сессию того же банка. Незавершённые операции читаются из `pendingItems`,
повторы страниц учитываются отдельно. Разные данные у одного ID, повторный
курсор, отсутствие обязательных массивов или ошибка карточки сохраняют частичный
результат с `complete=false`. Найденные данные не теряются.

`build_userscript.py` собирает один файл для того же способа запуска, которым
запускался прежний Safari/Tampermonkey userscript. В истории появляется кнопка
«Собрать историю в JSON». Период задаётся пользователем, виден ход сбора,
результат скачивается локальным JSON-файлом. При ошибке сохраняется неполный
результат. Скрипт не запускает запись в Debit & Credit и не обращается к платежам.

Запросы и обработка ошибок проверены с подставным транспортом. Прямые
авторизованные запросы к реальному банку пока не проверены. Первый запуск
делается на уже проверенном периоде 4–5 июля 2026: ожидаются те же 30 ID,
контрольные суммы и реквизиты, что получены через видимые карточки. До такого
сравнения прямой сбор не считается рабочим на реальных данных.
