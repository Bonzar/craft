# Оркестрация облачных сессий

Тело живёт здесь, в репозитории: это механика харнеса, а не правило базы.
Каждый факт помечен источником: «дока» — описание инструментов MCP-сервера
claude-code-remote в сессии, «замер» — проверено прогоном с датой.

## Что умеет и чего не умеет харнес

- Родитель узнаёт о дочерней сессии сам только при падении её хода или
  перезапуске воркера. Чистый финиш, «жду ответа» и блокер до родителя не
  доходят (дока `create_session`).
- У сессии нет `send_message`, а `ListAgents` не видит простаивающие
  облачные сессии (замер 16.09.2026). Единственный канал в обе стороны —
  триггер в конкретную сессию: `create_trigger` с `persistent_session_id`
  (дока, режим 2: сессия того же аккаунта).
- `run_once_at` обязан быть в будущем, планировщик проверяет раз в минуту
  (дока, замер 17.09.2026: «на сейчас» отбивается как прошедшее время).
  Поэтому доставка без ожидания — триггер без расписания плюс `fire_trigger`.
- Триггер, созданный из сессии, не несёт MCP-коннекторов, но при выстреле
  в живую сессию её инструменты остаются: дочерняя сессия после такого
  пробуждения сама создавала триггеры и пушила в git (замер 17.09.2026).
- Классификатор дочерней сессии режет команды с признаками утечки
  учётных данных и флаги обхода безопасности; вход в Codex по коду из
  дочерней сессии не проходит (Cloudflare 403 на auth-домене, замер
  17.09.2026). Такие шаги делает оркестратор у себя.

## Доставка сообщения в сессию: три вызова

Одинаково для «ребёнок → родитель» (отчёт) и «родитель → ребёнок» (поручение).

1. `create_trigger`: `persistent_session_id` = id сессии-адресата,
   `initiation` = `human_schedule`, `name` коротко («Отчёт этапа N»),
   `prompt` = текст целиком. Ни `cron_expression`, ни `run_once_at`.
2. `fire_trigger` с полученным `trigger_id`: доставка немедленная.
3. `delete_trigger` тем же id сразу после выстрела, чтобы список рутин не
   засорялся. Разовый триггер с `run_once_at` после выстрела отключается сам,
   но остаётся в списке — его тоже удалять.

Сообщение приходит адресату обычной репликой пользователя с текстом
`prompt`. Заголовок текста: кто пишет и о чём («Отчёт сессии этапа 2
‹session id›:»), дальше содержимое целиком — отсылок «см. выше» у адресата нет.

## Запуск дочерней сессии

- `create_session`: окружение «Craft» (`env_01GNvQ5T4JU5qvoHsHQZgABq`),
  `model` = `claude-opus-5` для исполнителей и исследователей (решение Влада),
  `source_url` = SafariScripts; репозиторий стройки сессия подключает сама
  через `add_repo` по брифу. `permission_mode` наследуется, `plan` не ставить:
  дочерняя сессия зависнет на одобрении, которого некому дать.
- Бриф самодостаточен: id оркестратора, что делать, что нельзя (Craft не
  писать, на GitHub не комментировать, PR не сливать, секреты не печатать,
  фолбэков нет), как сдать. Разделы Craft, нужные для работы, вкладываются
  текстом: Craft-тулзы у дочерней сессии не в счёт.
- Обязательная сдача двумя способами: финальным сообщением сессии и тремя
  вызовами выше в сессию оркестратора. То же при блокере: сессия доставляет
  отчёт о блокере и останавливается, не ждёт вопроса. Если `create_trigger`
  недоступен — первой строкой финала дословно «create_trigger недоступен»
  и список инструментов claude-code-remote.
- Оркестратор не ставит будильники «проверить через час»: отчёт приходит
  сам. Исключение одно: пока доставка триггером из этого окружения не
  подтверждена хотя бы одним пришедшим отчётом, оркестратор ставит один
  страховочный `send_later`. По нему он проверяет дочернюю сессию через
  `get_session` (статус, `post_turn_summary`) и читает первую строку её
  финала: «create_trigger недоступен» означает, что канала нет, и дальше
  оркестратор ведёт сессию по `get_session` сам. После первого успешного
  отчёта из окружения будильники не ставятся, а поставленный снимается.

## Поручение живой сессии

Сессия, сдавшая отчёт, остаётся жива и простаивает. Решения Влада по её
вопросам и находкам доставляются ей теми же тремя вызовами, той же веткой
и тем же PR: новая сессия не нужна, контекст у старой на месте
(замер 17.09.2026: сессия этапа 2 приняла поручение и запушила заход 2).

## После завершения

Сессию, чья работа слита или отменена, архивировать `archive_session`,
когда Влад подтвердил, что она больше не нужна. Свои триггеры удалять сразу
после выстрела; чужие (созданные сессией-ребёнком в сессию оркестратора)
отключаются сами и удаляются при уборке.
