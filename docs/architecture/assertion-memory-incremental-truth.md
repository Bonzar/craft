# Assertion Memory: замечать конфликт сразу, пересобирать только нужное

Исследовательский проект, не реализация. Основание: канонический runtime ea725fd и локальная ветка релизов e6aee24. Изменения runtime между ними касаются доступности Codex и состояния очереди, не семантики связей.

**Предложение.** Разделить три операции: сохранить новое свидетельство; дешёво показать, что возможен конфликт и старый ответ уже не гарантирован; доказать конфликт или обновить один нужный ответ. Первые две не требуют LLM. Третья ограничена бюджетом. Не строить второй граф и не переписывать историю.

## 1. Типизированное противоречие

Кандидат хранит две точные версии/хеша, спаны и ключ сравнения: subject_id, predicate_id, normalized_value, polarity, modality, scope/actor, condition_signature, valid_interval, time_precision. Это производная карточка, не новый источник. Для начала стабильные идентификаторы только у малого whitelist доменов. FTS/LLM не могут сами объявить одинаковыми людей, устройства, единицы, область, время и условия.

- **contradicts** симметричен: один предмет и предикат, сопоставимые атрибуция и условия, перекрывающееся время, взаимоисключающие значения. Одинаковое значение с противоположной полярностью или несовместимые диапазоны однозначного предиката при одинаковых единицах могут иметь детерминированное доказательство. Неизвестные поля не равны.
- **supersedes** направлен и требует доказанного перехода состояния или явной коррекции. Разные даты сами по себе не отменяют старую мысль. **qualifies**/условное исключение тоже направлено и не является противоречием. Несопоставимые позиции можно оставить вообще без связи.
- Стадии решения: candidate → unresolved / confirmed / rejected. Хранить точные доказательства, причину, версию политики и метод решения. Смена любой головы убирает старый вывод из текущего режима, не переписывая историю. Подтвердить несовместимость не значит выбрать истинную сторону; автоматический retire не нужен.
- Пример: «фильтр заменён 1 ноября» и «фильтр не заменялся в ноябре» для одного устройства требуют проверки источника и интервала. «Не заменён на 28 октября» не спорит с ноябрём. Слова мастера и оценку пользователя сначала показываем как разногласие атрибуций, не два подтверждённых факта.

## 2. Индексы, ревизии и протокол записи

1. При publish/retire и допущенном raw capture существующая транзакция записывает минимальное изменение в truth_changes: монотонный seq, kind, identity, old/new pinned hash, scope, cause. Правка только названия не двигает семантическую ревизию, но потеря доказательства двигает ревизию доказательств, даже если текст прежний.
2. Два обратных индекса. **support_watch**: (kind,id,pinned version/hash) → потребитель, версия и перспектива. Для thought→thought переиспользовать memory_thought_dependencies, дополнить точными raw spans, relation proofs и сохранёнными обзорами/ответами. **candidate_watch**: (scope,subject,predicate,bucket) → потребитель нового свидетельства, которого в основе не было. У широкого обзора допускается scope-wide отметка неизвестного охвата, но не автоматический вызов модели. Ранжирование FTS/embedding только после проверки области доступа.
3. Producer обновляет ключи/ревизии и watermark в своей транзакции, не перебирая весь fan-out. Read path сравнивает checked_revision и актуальный вектор/водяной знак. Пока событие ещё индексируется или ключ неоднозначен, не показывать «актуально»: вернуть coverage_unknown для затронутой перспективы. Для сырого события без установленного subject ключа использовать ограниченный scope-level watermark и существующие сигналы неполной доставки, а не угадывать семантику.
4. Worker читает журнал небольшими страницами и помечает (consumer_id,version,selector,max_seq,reason) dirty. Сдвиг cursor и отметки атомарны, replay идемпотентен. Частичный backfill показывает coverage_unknown, а не видимость свежести. Начать с additive migration и shadow-сверки с действующим поиском/публикацией.

## 3. Что видит пользователь

- Независимые измерения: **freshness** current / stale / coverage_unknown; **conflict** none_seen / candidate / unresolved / confirmed; **generation** idle / queued / waiting_model / failed. none_seen не означает «в мире конфликта нет». Показать причину, ревизию и допустимые доказательства; никаких утечек чужих областей даже через счётчики.
- Текущий stale ответ читается с заметной пометкой; он не авторизует дальнейшее действие как свежий. Historical known_then/pinned revision сохраняет тогда известные факты. Уведомление о новом срезе идёт отдельно, не меняет историческую выдачу. Недоступность модели не считается проверкой.
- Кэш: owner/scope policy + selector/cutoffs + версия артефакта + support fingerprint + вектор ревизий watched buckets + версии правил и модельного маршрута. Не пересчитывать исторический текст. Для начала выводить typed status/proof в карточке и API, не менять бинарные форматы графа; отдельно решать стиль candidate и confirmed.

## 4. Ограничение работы и защита от гонок

- Первый этап: **0 фоновых LLM-вызовов** для инвалидации. Затем стартовые лимиты, не гарантии: 100 dirty-получателей на транзакцию, до 10 кандидатов на изменённый ключ, окно сглаживания 30–120 секунд, один отдельный модельный worker и дневной бюджет токенов. Переполнение хранится с курсором и маркируется partial. Raw capture никогда не ждёт модели.
- Приоритет: запрос владельца → открытый обзор → уверенная пара → остальное. Глубина автоматического LLM-каскада = 0: изменившийся ответ помечает соседа грязным, но не запускает его автоматическую перепроверку. Дедуп target+selector+desired_generation. Checkpoint переиспользуется только с прежним набором точных входов и версией модельного контракта.
- Перед commit повторно проверить heads, support/coverage vector, разрешённую область, версию правил и живую lease. Изменилось что-то из этого → не применить устаревший вердикт, оставить прежний ответ stale и объединить причины. При outage waiting; при исчерпании повторов failed без выдуманного вывода. Измерять lag/очереди, p95 дешёвой инвалидации, LLM-вызовы/токены на изменение, отменённые commit, долю unresolved и ложных кандидатов.

## 5. Доказательство перед включением

1. Golden: отрицание, разный предмет/автор/модальность/условия и время, неизвестная точность, явное исправление, независимые источники, Unicode spans, retired proof и разные области доступа.
2. Property/интеграция: цикл смысловых связей, историческая self-basis, fan-out 10 000, ромб, повтор события, смена головы после claim, гонка поколений, crash/restart, частичный backfill, недоставленный input, outage. Ни один stale ответ не проходит current gate.
3. Synthetic end-to-end: capture → V1 → принятый обзор/ответ → новое противоположное свидетельство → stale/risk до любого модельного вызова → проверка точной пары → пересборка **одного** выбранного ответа. Историческая выдача и чужая область не меняются. Replay не дублирует связи или работу. Измеримый барьер: 0 LLM calls на invalidation и явный предел на выбранную пересборку.
4. Порядок: shadow journal/coverage → freshness API для известных зависимостей → новые кандидаты в одном домене → проверка по запросу владельца. На TEST проверить действующие выдачи и объём LLM перед включением в PROD; выключение feature flag не меняет прежние API.

**Выборы:** первый домен (техника/регламент или задачи); что можно подтверждать строгим правилом, а что оставить unresolved; когда вообще нужен бюджет фоновых проверок; где показывать stale и где запрещать действие. Рекомендую начать с техники/регламента, только строгих подтверждений и выключенных фоновых LLM.
