# Проверка Codex Cloud через отдельный dist

Готовая раскладка живёт только в ветке **`dist/codex-cloud`**. Это собранный
dist, его не редактируют руками и не вливают обратно в `main`.
В source-ветке находятся сборщик `tools/build-cloud-probe`, наблюдатель
`tests/cloud_repo_probe.py`, исходный модуль `probe` и тесты сборки.

Сейчас dist содержит контрольную пробу трёх точек входа Cloud. Полный рабочий
набор переносится через этот канал после реального замера, включая хуки.
Предыдущая проверка игнорируемой `.codex` не проверяла чтение файлов из Git.
По [документации Cloud](https://learn.chatgpt.com/docs/environments/cloud-environments)
репозиторные скиллы доступны облачным задачам. Поддержку проектных command
hooks проверяет сам Cloud, локальный CLI этого не доказывает.

## Сборка

Из source-ветки, где изменения уже закоммичены:

```bash
python3 tools/build-cloud-probe --ref HEAD --output /tmp/craft-cloud-dist --runtime-root /workspace/craft
python3 tools/build-cloud-probe --check /tmp/craft-cloud-dist
```

Каталог результата должен быть пустым или ещё не существовать. Сборщик
отказывается перезаписывать чужое содержимое. Он читает явно перечисленные
исходники через `git show` выбранного коммита. Незакоммиченные изменения,
локальная установка, секреты и журналы не являются входами сборки.
Повторная сборка того же коммита для того же runtime root побайтно совпадает.

Результат содержит:

- `AGENTS.md` с контрольной меткой чтения инструкций.
- `.agents/skills/probe/SKILL.md`, копию части `skill` модуля `probe`.
- `.codex/hooks.json` с пробами `SessionStart`, `PermissionRequest` и
  `SubagentStart`. `SessionStart` включает `source=compact`.
- `.codex/jarvis/cloud-repo-probe.py`, собранную копию наблюдателя.
- `cloud-dist.json`: тип сборки, source commit, runtime root и SHA256 всех
  четырёх артефактов. Manifest не содержит даты сборки и данных среды.

Для публикации дерево source-коммита дополняется **только этими пятью
файлами** и сохраняется коммитом в `dist/codex-cloud`. Исходники остаются
доступны в dist checkout для работы и существующего install script.
Обновление dist — новая сборка из нового source-коммита. Его источник
фиксируется в manifest. Собирать из уже готовой dist-ветки запрещено.
Проверка `--check` подтверждает целостность артефактов, а не запуск Cloud.

Команда хука использует выбранный `--runtime-root` и `python3`. Значение
`/workspace/craft` соответствует наблюдаемому checkout этой среды. Для иной
раскладки нужно пересобрать dist с другим параметром.

## Поведение наблюдателя

Наблюдателя вызывает native hook. Он пишет только событие, источник старта,
ID сессии, cwd, PID и время в `$JARVIS_STATE_DIR/cloud-repo-probe.jsonl`.
На старте дополнительно печатает контрольную метку в контекст. На запросе
разрешения и старте подагента молчит и не меняет решений.

Отсутствие переменной, неверное событие и ошибка записи дают код 1 и текст
причины в stderr. Промпт, транскрипт, вход инструмента и секреты не копируются.
Профиль, `auth.json`, журналы, бинарники и снимки Craft в dist не добавляются.
Наблюдатель не запускает установщик, модули, сборку и отдельный Codex.
Доверие не подделывается и не обходится.

## Реальный замер

1. В подготовленном checkout среды выбрать `dist/codex-cloud` и проверить
   `cloud-dist.json`. Эта ветка должна быть выбрана **до создания нового
   Cloud-чата**. Смена ветки инструментом уже идущего чата не проверяет
   загрузку до первого хода. Слияние dist в `main` для замера не требуется.
2. Сохранить `JARVIS_STATE_DIR=/workspace/craft/.codex/state`.
3. Первым сообщением отправить запрос без ожидаемых значений меток:

   ```text
   До первого инструмента перечисли только уже видимые контрольные метки
   репозиторных инструкций, метаданные скилла-пробы и сообщения стартовых
   хуков. Если чего-то нет, так и скажи. Не угадывай и не читай исходники
   перед этим ответом.

   Затем только чтением проверь git HEAD, текущую ветку и cloud-dist.json.
   Проверь наличие в git ls-files: AGENTS.md, .agents/skills/probe/SKILL.md,
   .codex/hooks.json, .codex/jarvis/cloud-repo-probe.py, cloud-dist.json.
   Прочитай /workspace/craft/.codex/state/cloud-repo-probe.jsonl,
   если он существует. Сообщи CODEX_HOME, JARVIS_STATE_DIR и cwd.
   Не запускай установщик, хуки, тесты или другой Codex. Файлы не меняй.
   ```

4. Сопоставить начальные метки с файлами после первого отчёта. Наличие файлов
   и метка в исходнике не считаются доставкой в модель.
5. Выполнить настоящий compact поддерживаемым действием Cloud. В следующем
   ходе сначала зафиксировать уже видимый контекст, затем прочитать журнал:
   нужен новый `SessionStart` с `source=compact`.
6. Для `SubagentStart` в проверочном чате явно поручить один безопасный
   подагентный запрос, например сообщить cwd без изменения файлов.
7. `PermissionRequest` проверять через поддерживаемый native запрос
   подтверждения безвредного действия по действующей политике. Отсутствие
   такого запроса означает «не проверено». Не менять политику, не обходить
   sandbox и не подставлять JSON событием вручную.
8. Повторить старт второй новой Cloud-сессией из той же публикации. Различать
   их ID и следы. При несовпадении git HEAD/manifest проверяется другой dist.

Если Cloud читает только инструкции и скилл, полный автозапуск Джарвиса
остаётся незавершённым. Ошибка или недоверие регистрации сохраняются как
результат, а не исправляются выдуманным хешем или обходом trust.

## Локальные проверки

`python3 -m unittest tests.test_cloud_probe_dist tests.test_cloud_repo_probe -v`
проверяет воспроизводимость, source commit, контрольные суммы, сохранность
исходников, исключение локального состояния, протокол наблюдателя и ошибки.
Синтетические события используют временные каталоги. Этот прогон не вызывает
существующие модульные хуки и не доказывает автоматический запуск Cloud.
