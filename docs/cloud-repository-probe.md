# Проверка подключения Codex Cloud из Git

Это контрольный эксперимент, а не установка рабочего набора. Предыдущий
замер проверял игнорируемый профиль `/workspace/craft/.codex`. Он не проверял
проектные инструкции, скиллы и конфигурацию хуков, полученные из Git.

По [документации Cloud](https://learn.chatgpt.com/docs/environments/cloud-environments)
скиллы из репозитория доступны в облачных задачах. Проверка применимости
проектных command hooks нужна отдельно: локальный CLI её не заменяет.

## Что закоммичено

- `AGENTS.md`: отдельная контрольная метка чтения инструкций.
- `.agents/skills/probe/SKILL.md`: точная копия части `skill` модуля `probe`.
  Проверка сравнивает её с единственным источником
  `modules/probe/skill/SKILL.md`. При изменении источника копия обновляется
  командой `cp modules/probe/skill/SKILL.md .agents/skills/probe/SKILL.md`.
- `.codex/hooks.json`: проба `SessionStart`, `PermissionRequest` и
  `SubagentStart`. `SessionStart` включает `source=compact`.
- `tests/cloud_repo_probe.py`: наблюдатель, который зовёт сам харнес. Он
  пишет только событие, источник старта, ID сессии, cwd, PID и время. На
  старте дополнительно печатает метку в контекст. На разрешениях и старте
  подагента молчит и не меняет решений.

Конфигурация рассчитана на наблюдаемый путь этой среды `/workspace/craft`
и доступный `python3`. Для среды с другим путём нужно изменить команду.
Это ограничение диагностической пробы, не переносимый рецепт установки.

Записи уходят только в `$JARVIS_STATE_DIR/cloud-repo-probe.jsonl`.
Отсутствие переменной, неверное событие и ошибка записи дают код 1 и текст
причины в stderr. Промпт, транскрипт, вход инструмента и секреты не копируются.
Журналы, профиль, `auth.json`, бинарники и снимки Craft не коммитятся.

Проба не запускает установщик, модули, сборку и отдельный Codex. Доверие не
подделывается и не обходится. Если Cloud требует review регистрации, но не
предоставляет поддерживаемого способа, это результат проверки, а не повод
проставить выдуманный хеш. Поддержка CLI не объявляется поддержкой Cloud.

## Порядок реального замера

1. Использовать новую Cloud-сессию, в чей checkout уже входит этот коммит.
   Checkout ветки внутри уже начатого чата не проверяет загрузку до первого
   хода. Для среды, которая берёт только `main`, сначала нужен merge, затем
   обновление подготовленного checkout и новая задача.
2. В настройках среды сохранить `JARVIS_STATE_DIR=/workspace/craft/.codex/state`.
   Старый install script может оставаться, но новый замер не должен выдавать
   его сохранённые артефакты за след запуска закоммиченной пробы.
3. Первым сообщением отправить следующий запрос, без ожидаемых значений меток:

   ```text
   До первого инструмента перечисли только уже видимые контрольные метки
   репозиторных инструкций, метаданные скилла-пробы и сообщения стартовых
   хуков. Если чего-то нет, так и скажи. Не угадывай и не читай исходники
   перед этим ответом.

   Затем только чтением проверь git HEAD и наличие в git ls-files:
   AGENTS.md, .agents/skills/probe/SKILL.md, .codex/hooks.json,
   tests/cloud_repo_probe.py. Прочитай
   /workspace/craft/.codex/state/cloud-repo-probe.jsonl, если он существует.
   Сообщи CODEX_HOME, JARVIS_STATE_DIR и cwd. Не запускай установщик,
   хуки, тесты или другой Codex. Файлы не меняй.
   ```

4. Сопоставить начальные метки с файлами только после первого отчёта.
   Наличие файлов и метка в исходнике не считаются доставкой в модель.
5. Выполнить настоящий compact поддерживаемым действием Cloud. В следующем
   ходе сначала зафиксировать уже видимый контекст, затем прочитать журнал:
   нужен новый `SessionStart` с `source=compact`, а не повтор старого ответа.
6. Для `SubagentStart` в проверочном чате явно поручить один безопасный
   подагентный запрос, например сообщить cwd без изменения файлов. До этого
   подагентов ради пробы не запускать.
7. `PermissionRequest` проверять через поддерживаемый native запрос
   подтверждения безвредного действия по действующей политике. Отсутствие
   такого запроса означает «не проверено». Не менять политику, не обходить
   sandbox и не подставлять JSON событием вручную.
8. Повторить старт второй новой Cloud-сессией из той же публикации. Отличить
   её ID от первой сессии. Доставку и журнал проверять для каждой отдельно.

Если Cloud читает инструкции и скилл, но не запускает хуки, путь из Git
подтверждён только для первых двух частей. Полный автозапуск Джарвиса этим
не закрывается. Следующая реализация переносит рабочие модули лишь через
подтверждённые точки входа и сохраняет весь согласованный объём задачи.

## Локальная проверка пробы

`python3 -m unittest tests.test_cloud_repo_probe -v` проверяет протокол,
ошибки и проектные файлы. Синтетические события используют временные каталоги.
Этот прогон не запускает существующие модульные хуки и не является реальным
замером Cloud. Ни один файл его журнала не попадает в state облачного агента.
