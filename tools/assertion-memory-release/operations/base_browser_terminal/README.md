# Exact Base terminal proof, offline candidate

The native boundary adapter calls the existing release_core validation
and reads the exact journal/current and manifest digest against **already
independently admitted** identities. Neither the deploy-owned journal nor
the deploy-owned SHA256SUMS can become a source of authority. The kernel
and smoke observation bindings are callable interfaces, not stand-ins
for real process or HTTP probes. Nothing is added to the startup path.

The checked-in current configured PROD authorizer issues exact v1/v2 OIDC
one-use promotion authorization; its permit returns only status, scope,
revision, and archive. It does not bind manifest/mode or predecessor and
cannot be mapped directly to Admission. Reuse exactly its issuer/actor/
workflow/runner/nonce policy for additive v3 canonical signed envelope
with sealed manifest+mode; maintain prior active identity and pending
witness using the existing independently owned authorizer state/scope.
No new roles/keys/cookies or application DB/schema. Keep v1/v2 nonterminal.

The existing protected owner of the native controller must choose the
exact phase before collection. Run under the existing release lease, retain
the existing transition fence sequence (avoid a lease across a reentrant
protected smoke), and pass the native journal completion as its own
existing continuation. Candidate selection uses same installed archive;
rollback must call the original restore/smoke for historical release.
Use exact kernel PIDs, start ticks, UID and real listener ownership plus
before/after authenticated smoke; do not substitute a copied deploy success
string. Only the separately trusted controller may record precommit and
settle the authorizer's independent witness after native journal completion.
With no precommit after journal disappearance, fail closed and do not repeat
the native mutation.

No host I/O, releases or production activation are done by this suite.

Release boundary seam: once journal unlink succeeds, sync/publication
failure is explicitly pending, not rollback or candidate retention.
On absent native journal, the exact independently protected precommit
may prepare a no-argument publication continuation. Core first re-fsyncs
the directory under the existing lease; only then may the continuation
freshly observe and settle the exact run. Absent journal by itself is
not proof; neither branch repeats a native mutation. An opted-in
witness has no bootstrap authority and requires a verified predecessor.

Observer and authorizer transport: kernel_observer.py consumes existing
protected MainPID lookup and exact native package metadata; can only map
the Base/old Graph fixed role and three fixed ports. It verifies boot and
PID start ticks, UID, cgroup, physical cwd, protected module/config, network
namespace and loopback TCP inode/FD ownership. It does not authenticate the
application or mutate service state. root_terminal_publisher.py retains
the existing UID986 v1/v2 exact handler and defines a separate root-only
terminal receipt on the existing fixed AF_UNIX socket. Client verifies
actual UID980 bytes via Linux SCM_CREDENTIALS; root listener-creator
SO_PEERCRED alone would be insufficient. Its UID980 exact record compare-
and-set is independent of app/SQLite. Both ends require a trustworthy
preexisting pending transaction. Protected signed v3 admission, owned
process observers and reviewed versioned operations
bundle are gating. Both TEST and PROD stay unchanged.

## TEST / PROD recovery order for operators

1. On disposable TEST, prove runtime-only observer success and exact inverse
   package/socket/edge restore. Native release smoke stays native and no
   new login or permission is added. Verify ordinary same-origin Visual
   using only an existing authenticated owner tab, no read of credentials,
   cookies, or session endpoint CSRF. Inspect normal Graph/render and queue
   actions read-only; deny pass for login screen, stale generation or
   anonymous readiness alone. Prove no hidden PROD alias in either route.
2. On PROD, confirm exact operator and configured authorizer protections,
   initial approved prior archive+edge pair, known recovery availability,
   and existing owner tab before an actual cutover. Runtime receipt is
   typed immutable release/controller phase, not user-visible feature pass.
   Coordinate native feature activation and existing route switch under the
   reviewed protocol; do not enable a second public alias.
3. If normal owner tab fails or expected generation is unprovable, do not
   report Visual healthy or add a login. Revert managed ingress to its
   exact previously verified boundary with guarded recovery, stop the
   affected new route/service and restore the exact predecessor native
   package/role pair, verify trusted before/after listener state and old
   ordinary UI. Keep nonmutating native receipt retries separate: on
   already-fsynced candidate recovery do not repeat start/restore.
4. If valid preexisting owner session is missing, defer this feature
   readback/cutover; cannot replace with alternate credentials, an inject-
   browser-auth method, a fabricated runtime signal or an anonymous check.
